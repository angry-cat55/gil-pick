## Clarifications

- Q: 같은 여행을 두 요청이 동시에 수정하려고 하면 시스템이 어떻게 처리해야 하나요? → A: (수정) 버전 비교. `docs/design/er-schema.md`(`trips.version`)와 `docs/design/api-spec.md`(TRIP-004, `409 VERSION_CONFLICT`)에 이미 버전 기반 동시성 제어가 설계되어 있어 기존 문서를 따른다. last-write-wins로 처음 답변했던 내용은 기존 설계와 충돌해 철회한다.
- Q: 여행명이 공백으로만 이루어져 있거나 앞뒤에 공백이 붙어 있으면 어떻게 처리해야 하나요? → A: 앞뒤 공백을 trim한 뒤 2~30자 검증을 적용하고, trim 후 2자 미만이면 거부한다

### Session 2026-08-28

- Q: 완료된 여행도 삭제할 수 있어야 하나요? → A: 사용자의 데이터 통제권을 위해 완료 상태를 포함한 모든 상태의 여행을 논리 삭제할 수 있도록 허용한다. 완료 여행 삭제를 막던 2026-08-26의 결정 중 삭제 제한만 철회하며, 완료 여행의 기간 수정 제한은 유지한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 여행 생성 (Priority: P1)

로그인한 사용자가 여행명과 여행 기간을 입력해 새 여행을 만든다.

**Why this priority**: 여행 생성이 없으면 이후 일정·경로·진행 기능(F004~F011)이 시작될 수 없는 전체 서비스의 진입점이다.

**Independent Test**: 인증된 사용자로 여행명과 기간을 입력해 생성 요청을 보내고, 생성된 여행이 목록·상세에서 조회되는지 확인하는 것으로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 로그인한 사용자가 여행 생성 화면에 있다, **When** 2~30자 여행명과 7일 이하 기간을 입력해 생성을 요청한다, **Then** 여행이 생성되고 목록·상세에서 즉시 조회된다.
2. **Given** 로그인한 사용자가 여행 생성 화면에 있다, **When** 여행명을 1자 이하 또는 31자 이상으로 입력한다, **Then** 생성이 거부되고 이유가 안내된다.
3. **Given** 로그인한 사용자가 여행 생성 화면에 있다, **When** 여행 기간을 8일 이상으로 입력한다, **Then** 생성이 거부되고 이유가 안내된다.
4. **Given** 사용자가 이미 동일한 이름의 여행을 가지고 있다, **When** 같은 이름으로 새 여행을 생성한다, **Then** 여행명 중복은 허용되어 생성이 성공한다.
5. **Given** 사용자가 생성 요청을 전송했다, **When** 네트워크 재시도 등으로 동일한 생성 요청이 중복 전송된다, **Then** 여행은 한 건만 생성된다.

---

### User Story 2 - 여행 목록 조회·검색·필터 (Priority: P1)

사용자가 자신의 여행 목록을 상태별로 확인하고, 이름으로 검색하거나 상태로 걸러본다.

**Why this priority**: 생성한 여행을 다시 찾고 관리하는 기본 진입점이며, 여러 여행을 만든 뒤에도 서비스를 계속 쓰기 위한 핵심 기능이다.

**Independent Test**: 서로 다른 상태의 여행 여러 건을 만든 뒤 목록 조회, 이름 검색, 상태 필터, 스크롤 추가 조회를 각각 단독으로 확인할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사용자가 여행 중·예정·완료 상태의 여행을 각각 가지고 있다, **When** 여행 목록을 연다, **Then** 여행 중 → 예정 → 완료 그룹 순으로 표시된다.
2. **Given** 사용자가 이름이 다른 여러 여행을 가지고 있다, **When** 여행명 일부로 검색한다, **Then** 검색어를 포함하는 여행만 표시된다.
3. **Given** 사용자가 여러 상태의 여행을 가지고 있다, **When** 특정 상태로 필터를 적용한다, **Then** 해당 상태의 여행만 표시된다.
4. **Given** 사용자의 여행이 한 화면에 다 표시되지 않을 만큼 많다, **When** 목록을 끝까지 스크롤한다, **Then** 이어지는 여행이 추가로 로드된다.
5. **Given** 다른 사용자가 소유한 여행이 존재한다, **When** 사용자가 자신의 목록을 조회한다, **Then** 다른 사용자의 여행은 표시되지 않는다.

---

### User Story 3 - 여행 상세 조회 (Priority: P2)

사용자가 목록에서 여행을 선택해 이름, 기간, 상태 등 상세 정보를 확인한다.

**Why this priority**: 목록에서 한 단계 더 들어가 실제로 여행 정보를 확인·관리하기 위한 진입점이며, 이후 F004(일정 구성) 진입 화면이기도 하다.

**Independent Test**: 생성된 여행 하나를 상세 조회 요청으로 열어 이름·기간·상태가 정확히 표시되는지 단독으로 확인할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사용자가 소유한 여행이 존재한다, **When** 해당 여행의 상세를 조회한다, **Then** 여행명, 기간, 현재 상태가 표시된다.
2. **Given** 사용자가 소유하지 않은 여행 식별자를 안다, **When** 해당 여행의 상세를 조회한다, **Then** 조회가 거부된다.
3. **Given** 사용자가 논리 삭제된 자신의 여행 식별자를 안다, **When** 해당 여행의 상세를 조회한다, **Then** 조회가 거부된다.

---

### User Story 4 - 여행 기간 수정 (Priority: P2)

사용자가 이미 만든 여행의 이름이나 기간을 수정한다. 기간을 줄이면 범위 밖으로 밀려나는 일정이 있는지 미리 안내받는다.

**Why this priority**: 여행 계획은 자주 바뀌므로 생성 이후 조정 수단이 필요하지만, 생성·조회보다는 사용 빈도가 낮다.

**Independent Test**: 일정이 있는 여행과 없는 여행 각각에 대해 기간을 축소하는 수정 요청을 보내 안내와 결과를 단독으로 확인할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사용자가 소유한 예정 또는 여행 중 여행이 존재한다, **When** 여행명만 2~30자 범위 내로 수정한다, **Then** 여행명이 변경된다.
2. **Given** 여행 기간 안에 저장된 일정이 있다, **When** 사용자가 그 일정 날짜를 벗어나도록 기간을 축소 요청한다, **Then** 삭제될 일정 수를 먼저 안내하고 사용자 확인을 기다린다.
3. **Given** 삭제 안내를 받은 사용자, **When** 사용자가 확인하지 않고 요청을 중단한다, **Then** 기존 기간과 일정이 그대로 유지된다.
4. **Given** 삭제 안내를 받은 사용자, **When** 사용자가 축소를 확인한다, **Then** 기간이 변경되고 범위 밖 일정만 삭제된다.
5. **Given** 사용자가 여행 기간을 8일 이상으로 늘리려 한다, **When** 수정을 요청한다, **Then** 수정이 거부되고 이유가 안내된다.
6. **Given** 사용자가 소유한 완료 상태 여행이 존재한다, **When** 여행명만 수정을 요청한다, **Then** 여행명이 변경된다.
7. **Given** 사용자가 소유한 완료 상태 여행이 존재한다, **When** 여행 기간 수정을 요청한다, **Then** 수정이 거부되고 완료된 여행은 기간을 수정할 수 없다는 이유가 안내된다.
8. **Given** 사용자가 다른 요청으로 이미 변경된 여행의 이전 버전 값을 가지고 있다, **When** 그 버전으로 수정을 요청한다, **Then** 수정이 거부되고 최신 정보를 다시 조회한 뒤 재시도하라는 안내를 받는다.

---

### User Story 5 - 여행 삭제 (Priority: P3)

사용자가 더 이상 필요 없는 여행을 목록에서 제거한다.

**Why this priority**: 정리 기능으로서 필요하지만 생성·조회·수정 없이도 서비스 핵심 가치는 이미 성립하므로 우선순위가 가장 낮다.

**Independent Test**: 여행 하나를 삭제 요청한 뒤 목록·상세 조회에서 더 이상 나타나지 않는지 단독으로 확인할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사용자가 소유한 여행이 존재한다, **When** 해당 여행을 삭제 요청한다, **Then** 상태와 무관하게 여행은 논리 삭제되어 목록과 상세 조회에서 더 이상 보이지 않는다.
2. **Given** 사용자가 이미 논리 삭제한 여행이 있다, **When** 동일한 삭제 요청을 다시 보낸다, **Then** 추가 부작용 없이 삭제된 상태가 유지된다.
3. **Given** 사용자가 소유하지 않은 여행 식별자를 안다, **When** 그 여행의 삭제를 요청한다, **Then** 삭제가 거부된다.
4. **Given** 사용자가 소유한 완료 상태 여행이 존재한다, **When** 해당 여행의 삭제를 요청한다, **Then** 여행은 논리 삭제되어 일반 조회에서 더 이상 보이지 않는다.

---

### Edge Cases

- 여행 생성·수정 중 인증이 만료되면 어떻게 되는가? (F001의 세션 관리 결과에 따라 인증 오류로 거부되고, 클라이언트는 재로그인·재발급 흐름으로 유도한다.)
- 검색어와 상태 필터를 동시에 적용했을 때 결과가 없으면 어떻게 표시되는가?
- 여행이 하나도 없는 사용자가 목록을 조회하면 어떻게 되는가?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 인증된 사용자가 2~30자 여행명과 최대 7일 기간으로 새 여행을 생성하도록 허용해야 한다.
- **FR-001a**: 시스템은 종료일이 시작일보다 빠른 여행 생성·수정 요청을 거부하고 이유를 안내해야 한다.
- **FR-001b**: 시스템은 여행명의 앞뒤 공백을 제거(trim)한 뒤 길이를 검증해야 하며, trim 후 2자 미만(공백만 입력한 경우 포함)이면 요청을 거부해야 한다.
- **FR-002**: 시스템은 동일 사용자 내에서 여행명 중복을 허용해야 한다.
- **FR-003**: 시스템은 동일한 생성 요청이 재전송되어도 여행이 중복 생성되지 않도록 해야 한다.
- **FR-004**: 시스템은 사용자가 소유한 여행만 목록과 상세에서 조회하도록 제한해야 한다.
- **FR-005**: 시스템은 여행 목록을 여행 중 → 예정 → 완료 그룹 순으로 정렬하여 제공해야 한다.
- **FR-006**: 시스템은 여행 상태를 Asia/Seoul 기준 현재 날짜와 여행 기간을 비교해 예정·여행 중·완료 중 하나로 산정해야 한다.
- **FR-007**: 시스템은 여행명 일부 검색을 지원해야 한다.
- **FR-008**: 시스템은 여행 상태별 필터를 지원해야 한다.
- **FR-009**: 시스템은 여행 목록 조회 시 cursor 기반 추가 조회(무한 스크롤)를 지원해야 한다.
- **FR-010**: 시스템은 사용자가 자신이 소유한 여행의 이름을 상태와 무관하게 수정하도록 허용해야 한다.
- **FR-010a**: 시스템은 예정 또는 여행 중 상태의 여행에 한해 기간 수정을 허용해야 하며, 완료 상태 여행의 기간 수정 요청은 거부하고 이유를 안내해야 한다.
- **FR-011**: 시스템은 수정 후 기간에도 여행명 2~30자, 기간 최대 7일 제약을 동일하게 적용해야 한다.
- **FR-011a**: 시스템은 여행 수정 요청에 사용자가 조회했던 버전 값을 함께 받아, 저장된 현재 버전과 다르면 요청을 거부하고 사용자가 최신 정보를 다시 조회한 뒤 재시도하도록 안내해야 한다(버전 기반 동시성 제어).
- **FR-012**: 시스템은 기간 축소로 범위 밖에 놓이는 일정이 있으면 삭제될 일정 수를 사용자에게 먼저 안내하고, 사용자 확인 후에만 기간 변경과 해당 일정 삭제를 적용해야 한다.
- **FR-013**: 시스템은 사용자가 확인하기 전까지 기존 여행 기간과 일정을 그대로 유지해야 한다.
- **FR-014**: 시스템은 사용자가 자신이 소유한 여행을 예정·여행 중·완료 상태와 무관하게 논리 삭제하도록 허용해야 한다.
- **FR-015**: 시스템은 논리 삭제된 여행을 일반 목록 조회와 상세 조회에서 제외해야 한다.
- **FR-016**: 시스템은 이미 논리 삭제된 여행에 대한 반복 삭제 요청을 부작용 없이 동일한 결과로 처리해야 한다(멱등).
- **FR-017**: 시스템은 소유하지 않은 여행에 대한 조회·수정·삭제 요청을 거부해야 한다.
- **FR-018**: MVP 범위에서 시스템은 논리 삭제된 여행의 복구 기능과 자동 물리 삭제 기능을 제공하지 않는다.

### Key Entities

- **여행 (Trip)**: 사용자가 만드는 여행 단위. 여행명(2~30자), 시작일·종료일(최대 7일), 상태(예정/여행 중/완료는 파생값), 동시 수정 감지를 위한 버전 값, 논리 삭제 여부, 소유 사용자를 가진다.
- **일정 (Itinerary Item, 참조)**: 여행에 속한 날짜별 방문 계획. 본 feature에서는 여행 기간 축소 시 삭제 대상 수 계산과 삭제 처리를 위한 참조로만 다루며, 일정 자체의 생성·편집은 F004(일정 구성) 범위다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 여행 생성 요청 후 3초 이내에 생성 결과(성공 또는 거부 사유)를 확인할 수 있다.
- **SC-002**: 여행 100건을 가진 사용자도 목록 최초 화면을 2초 이내에 확인할 수 있다.
- **SC-003**: 여행명 검색과 상태 필터 결과는 1초 이내에 반영된다.
- **SC-004**: 여행 기간 축소로 일정이 삭제되는 경우, 사용자는 확인 없이 일정이 사라지는 경험을 100% 겪지 않는다.
- **SC-005**: 사용자는 자신이 소유하지 않은 여행의 정보를 어떤 경로로도 확인할 수 없다.
- **SC-006**: 삭제한 여행은 삭제 직후부터 목록·상세·검색 결과 어디에도 다시 나타나지 않는다.

## Assumptions

- F001(인증)이 먼저 완료되어 유효한 사용자 인증·세션 검증 수단이 존재한다고 가정한다. 이 feature는 별도의 인증 방식을 정의하지 않는다.
- 여행 시작일이 결정되지 않은 상태(임시/초안 여행)는 MVP 범위에 포함하지 않으며, 생성 시 시작일·종료일을 모두 입력하는 것을 기본으로 한다.
- 일정(Itinerary)의 생성·편집·순서 관리 자체는 F004(일정 구성)에서 다루며, 본 feature는 여행 기간 변경이 기존 일정에 미치는 영향(삭제 대상 안내·삭제)만 다룬다.
- 여행 삭제·복구 정책은 `docs/planning/requirements.md`의 TRIP-05를 따르며, MVP에서는 사용자 화면에 별도 복구 진입점을 제공하지 않는다.
- 지도 위 경로 표시, 이동수단, 체류시간 등은 F004~F005 범위이며 본 feature의 여행 상세 조회에는 포함하지 않는다.
