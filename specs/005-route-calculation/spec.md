## Clarifications

### Session 2026-09-06

- Q: 일정 저장과 경로 계산을 어떻게 연결하는가? → A: 일정 저장이 성공하면 같은 요청 흐름에서 경로를 자동 계산한다. 사용자는 최초 계산을 별도로 시작하지 않고, 최종 실패한 경우에만 `다시 시도`를 선택한다.
- Q: 날짜에 장소가 0곳 또는 1곳이면 경로 상태를 어떻게 표현하는가? → A: 0곳은 경로가 없는 빈 상태로 유지하고, 1곳은 외부 경로 계산 없이 총 이동시간 0분·총 이동거리 0m인 완료 경로로 취급한다.
- Q: 사용자가 정상 경로를 임의로 다시 계산하거나 다른 후보 경로를 선택할 수 있는가? → A: 제공하지 않는다. 일정·순서·이동수단 변경에 따른 자동 계산과 최종 실패 후 같은 입력으로 `다시 시도`하는 복구만 제공한다.
- Q: 일정 저장은 성공했지만 자동 경로 계산이 최종 실패하면 사용자는 어디로 이동하는가? → A: 일정 저장을 완료하고 여행 상세로 이동한다. 여행 상세의 해당 날짜 경로 영역에서 실패 안내와 `다시 시도`를 제공한다.
- Q: 길찾기 제공자가 한 구간에 여러 후보 경로를 반환하면 어느 경로를 사용하는가? → A: 각 제공자가 지정한 기본 추천 경로 한 개를 사용하며, 제공자 간 또는 후보 간 별도 비교·정렬은 하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 저장한 일정의 경로 계산 (Priority: P1)

인증된 사용자가 날짜별 일정에 장소 순서와 구간별 이동수단을 저장하면, 각 장소 사이의 실제 이동 경로와 구간별 이동시간·거리를 계산하여 확인한다. 도보·자동차·대중교통이 섞인 일정도 저장한 이동수단 그대로 계산한다.

**Why this priority**: 일정의 장소 목록만으로는 실제 이동 가능성과 하루 이동 부담을 판단하기 어렵다. 경로 계산 결과는 이후 여행 진행의 도착 예정 시각과 대체 장소 경로 비교가 사용하는 기준이기도 하다.

**Independent Test**: 좌표가 있는 장소 세 곳과 서로 다른 구간 이동수단을 저장한 뒤 경로 계산을 수행하면, 저장된 순서와 이동수단에 맞는 두 구간의 이동시간·거리와 전체 합계가 반환되는지로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사용자가 소유한 여행 날짜에 좌표가 있는 장소가 두 곳 이상 저장되어 있다, **When** 경로 계산이 시작된다, **Then** 저장된 장소 순서와 각 구간의 이동수단에 맞춰 모든 구간을 계산하고 전체 이동시간·거리와 함께 제공한다.
2. **Given** 도보·대중교통·자동차가 섞인 일정이다, **When** 경로를 계산한다, **Then** 각 구간은 사용자가 저장한 이동수단으로 계산되고 결과의 구간 순서는 일정 순서와 일치한다.
3. **Given** 한 구간에 여러 후보 경로가 반환됐다, **When** 계산 결과를 확정한다, **Then** 해당 제공자가 지정한 기본 추천 경로 한 개만 사용하고 사용자에게 후보 선택을 요구하지 않는다.
4. **Given** 경로 계산이 완료됐다, **When** 사용자가 같은 날짜의 일정을 다시 조회한다, **Then** 현재 일정 버전에 해당하는 최신 경로 상태와 구간별 이동시간·거리를 확인할 수 있다.
5. **Given** 다른 사용자의 여행 또는 삭제된 여행이다, **When** 경로 계산이나 조회를 요청한다, **Then** 요청은 거부되고 경로 정보가 노출되거나 변경되지 않는다.
6. **Given** 경로를 계산한 뒤 일정의 장소·순서·이동수단이 변경됐다, **When** 변경된 일정이 저장된다, **Then** 이전 계산 결과를 현재 경로로 표시하지 않고 새 일정 버전에 맞는 결과만 현재 경로로 취급한다.
7. **Given** 일정 저장은 성공했지만 자동 경로 계산이 최종 실패했다, **When** 저장 흐름이 끝난다, **Then** 여행 상세로 이동하고 해당 날짜의 경로 영역에 저장 완료와 구분되는 실패 안내 및 `다시 시도` 행동을 표시한다.

### User Story 2 - 지도에서 날짜별 경로 확인 (Priority: P2)

사용자가 여행 상세에서 원하는 날짜의 경로를 열어 장소 순서와 이동 경로를 지도에서 확인하고, 지도만 보지 않아도 구간별 이동수단·이동시간·거리를 목록으로 함께 확인한다.

**Why this priority**: 계산 결과가 있어도 사용자가 방문 순서와 이동 부담을 이해할 수 없으면 계획을 검토할 수 없다. 지도와 목록을 함께 제공해야 경로의 공간적 형태와 정확한 수치를 모두 확인할 수 있다.

**Independent Test**: 계산이 완료된 날짜의 경로 화면을 열어 지도 마커와 경로 선의 순서가 일정과 같고, 같은 구간 정보가 목록에도 제공되는지로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 현재 일정 버전의 경로 계산이 완료됐다, **When** 사용자가 날짜별 경로 화면을 연다, **Then** 장소를 방문 순서 번호로 구분한 지도 마커와 구간 경로가 표시된다.
2. **Given** 지도에 경로가 표시됐다, **When** 사용자가 구간 정보를 확인한다, **Then** 지도 밖 목록에서도 출발·도착 장소, 이동수단, 이동시간과 이동거리를 확인할 수 있다.
3. **Given** 경로에 여러 이동수단이 섞여 있다, **When** 지도와 목록을 본다, **Then** 각 구간의 이동수단이 아이콘과 문구로 구분되고 색만으로 의미를 전달하지 않는다.
4. **Given** 경로 조회가 1초를 넘긴다, **When** 결과를 기다린다, **Then** 대기 중임을 표시하고 완료되면 같은 화면에서 경로 내용으로 전환한다.
5. **Given** 저장된 일정이 없거나 경로를 만들 수 없는 날짜다, **When** 경로 화면을 연다, **Then** 현재 상태의 이유와 일정을 추가하거나 돌아갈 수 있는 다음 행동을 제공한다.
6. **Given** 경로 조회에 실패했다, **When** 오류 상태가 표시된다, **Then** 원인과 `다시 시도` 행동을 제공하며 저장된 일정은 그대로 유지된다.
7. **Given** 일정 저장 뒤 자동 경로 계산만 실패했다, **When** 여행 상세가 표시된다, **Then** 장소·순서·체류시간·이동수단은 저장된 값으로 표시되고 경로 영역만 독립적인 오류 상태가 된다.

### User Story 3 - 실패한 경로 계산 다시 시도 (Priority: P3)

외부 경로 제공자의 일시적 장애나 시간 초과로 계산에 실패한 경우, 사용자는 일정이 보존됐음을 확인하고 같은 입력으로 경로 계산을 다시 시도할 수 있다. 정상 계산된 경로를 마음에 들지 않는다는 이유로 다시 계산하거나 다른 후보를 선택하는 기능은 제공하지 않는다.

**Why this priority**: 외부 서비스 실패가 사용자가 작성한 일정을 손상시키면 안 되며, 앱을 떠나거나 일정을 다시 입력하지 않고 복구할 수 있어야 한다.

**Independent Test**: 최초 경로 계산을 최종 실패시키고 일정과 실패 상태가 유지되는지 확인한 다음 `다시 시도`를 실행해 같은 일정 입력의 성공 결과로 교체되는지로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 한 구간의 경로 제공자가 일시적으로 응답하지 않는다, **When** 자동 재시도까지 실패한다, **Then** 날짜의 경로 상태는 실패로 표시되고 일정 장소·순서·체류시간·이동수단은 유지된다.
2. **Given** 경로 계산이 실패했다, **When** 사용자가 `다시 시도`를 선택한다, **Then** 현재 일정 버전의 같은 일정 입력을 기준으로 전체 날짜 경로 계산을 다시 요청한다.
3. **Given** 사용자가 계산을 다시 요청한 뒤 일정이 다른 곳에서 변경됐다, **When** 요청의 일정 버전이 현재 버전과 다르다, **Then** 오래된 일정으로 결과를 저장하지 않고 최신 일정을 다시 확인하도록 안내한다.
4. **Given** 동일한 다시 시도 요청이 중복 전달됐다, **When** 서버가 요청을 처리한다, **Then** 같은 요청으로 현재 경로가 중복 생성되거나 여러 번 교체되지 않는다.
5. **Given** 현재 일정 버전에 해당하는 성공 경로가 있다, **When** 사용자가 경로 화면을 확인한다, **Then** 다른 후보 탐색이나 임의 재계산 행동을 제공하지 않는다.
6. **Given** 일정 변경으로 새 경로를 자동 계산하고 있다, **When** 변경 전 경로의 일정 버전이 현재와 다르다, **Then** 이전 경로를 현재 경로로 표시하지 않고 계산 중 또는 실패 상태를 표시한다.

### Edge Cases

- 날짜에 저장된 장소가 0곳이면 경로가 없는 빈 상태로 유지하고 일정 추가 행동을 제공한다.
- 날짜에 저장된 장소가 1곳이면 외부 경로 제공자를 호출하지 않고 총 이동시간 0분·총 이동거리 0m인 완료 경로로 취급한다.
- 구간 하나라도 최종 계산에 실패하면 일부 구간만 성공으로 표시하지 않고 날짜 전체를 실패로 처리한다.
- 경로 제공자가 반환한 구간 순서나 이동수단이 요청한 일정과 맞지 않으면 성공 결과로 사용하지 않는다.
- 경로 제공자가 후보를 여러 개 반환해도 해당 제공자가 기본 추천으로 지정한 경로 한 개만 사용하고 나머지는 저장하거나 사용자에게 노출하지 않는다.
- 계산 도중 일정 버전이 바뀌면 오래된 계산 결과를 현재 경로로 저장하거나 표시하지 않는다.
- 같은 날짜를 여러 번 계산해도 현재 일정 버전에 적용되는 현재 경로는 하나뿐이다.
- 장소 좌표가 유효 범위를 벗어나거나 두 장소가 같은 좌표이면 계산 불가능한 입력을 구분해 안내하고 저장된 일정은 유지한다.
- 이동시간 또는 거리가 누락되거나 음수인 구간은 성공 결과로 취급하지 않는다.
- 매우 짧은 구간에서도 사용자가 저장한 이동수단을 임의로 다른 이동수단으로 바꾸지 않는다.
- 네트워크가 끊긴 상태에서 계산을 다시 시도하면 즉시 실패 이유와 재시도 행동을 제공한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 인증된 사용자가 소유한 여행 날짜의 저장된 장소 순서, 좌표와 구간별 이동수단을 기준으로 경로를 계산해야 한다.
- **FR-002**: 시스템은 도보·자동차 구간을 TMAP으로, 대중교통 구간을 ODsay로 계산해야 한다.
- **FR-003**: 시스템은 각 구간에 출발·도착 일정 항목, 이동수단, 이동시간, 이동거리와 지도 표시용 경로 정보를 제공해야 한다.
- **FR-004**: 시스템은 날짜 전체의 총 이동시간과 총 이동거리를 구간 결과에서 계산해 제공해야 한다.
- **FR-005**: 시스템은 계산 결과의 구간 순서가 저장된 일정 순서와 일치하도록 보장해야 하며, 사용자 이동수단을 임의로 변경해서는 안 된다.
- **FR-005a**: 시스템은 각 경로 제공자가 지정한 기본 추천 경로 한 개만 구간 결과로 채택해야 하며, 제공자 간 또는 후보 간 별도 비교·정렬을 수행해서는 안 된다.
- **FR-006**: 시스템은 장소가 두 곳 이상인 일정의 저장이 성공하면 같은 요청 흐름에서 현재 일정 버전의 경로 계산을 자동으로 실행해야 한다.
- **FR-007**: 시스템은 외부 경로 제공자의 시간 초과 또는 일시적 오류에 대해 한 번 자동 재시도하고, 최초 호출부터 최종 결과까지 10초 안에 성공 또는 실패를 반환해야 한다.
- **FR-008**: 시스템은 하나 이상의 필수 구간이 최종 실패하면 날짜 전체 경로를 실패 상태로 기록하고, 실패 원인을 사용자에게 구분 가능한 형태로 제공해야 한다.
- **FR-009**: 시스템은 경로 계산이 실패해도 저장된 일정의 장소·순서·체류시간·이동수단을 변경하거나 삭제해서는 안 된다.
- **FR-009a**: 일정 저장 성공 뒤 자동 경로 계산이 최종 실패해도 일정 저장은 성공으로 완료되어야 하며, 사용자는 여행 상세로 이동해 저장된 일정과 독립된 경로 실패 상태를 확인할 수 있어야 한다.
- **FR-010**: 사용자는 실패한 날짜에서 현재 일정 버전의 같은 입력을 기준으로 경로 계산을 `다시 시도`할 수 있어야 한다.
- **FR-011**: 시스템은 다시 시도 요청의 일정 버전이 현재 버전과 다르면 오래된 입력으로 계산 결과를 적용하지 않아야 한다.
- **FR-012**: 시스템은 같은 다시 시도 요청이 반복 전달돼도 현재 경로를 중복 생성하거나 여러 번 교체하지 않아야 한다.
- **FR-013**: 시스템은 한 날짜에서 현재 일정 버전에 적용되는 현재 경로를 최대 하나만 제공해야 한다.
- **FR-014**: 시스템은 일정 변경 전 계산된 경로를 현재 일정의 경로로 표시해서는 안 되며, 현재 일정 버전과 계산 기준 버전을 구분해야 한다.
- **FR-015**: 시스템은 다른 사용자의 여행, 삭제된 여행 또는 여행 기간 밖 날짜의 경로 조회·계산을 거부해야 한다.
- **FR-016**: 시스템은 지도에 표시되는 장소·구간과 목록의 장소·구간이 동일한 순서와 값으로 대응되도록 제공해야 한다.
- **FR-017**: 시스템은 경로 제공자별 필수 attribution을 경로 결과에 포함하고 화면에서 확인 가능하게 표시해야 한다.
- **FR-018**: F005는 계획 경로와 구간별 이동시간·거리까지만 책임지며, 여행 시작, 현재 위치 기반 첫 장소 경로, 장소별 도착 예정 시각, 진행 상태 전환은 F006 범위로 제외해야 한다.
- **FR-019**: F005의 실패 복구용 `다시 시도`는 해당 날짜 전체의 같은 계획 입력을 대상으로 해야 하며, 정상 경로의 다른 후보 탐색·선택과 사용자 임의 재계산은 범위에서 제외해야 한다. 진행 상태를 기준으로 일부 남은 구간을 다시 계산하는 기능은 F006 이후 범위다.
- **FR-020**: 시스템은 장소가 없는 날짜를 경로 빈 상태로 유지하고, 장소가 한 곳인 날짜는 외부 경로 계산 없이 총 이동시간 0분·총 이동거리 0m인 완료 경로로 제공해야 한다.
- **FR-021**: 시스템은 일정·순서·이동수단이 변경된 경우에만 성공한 계획 경로를 자동으로 다시 계산해야 하며, 정상 경로를 대상으로 한 복수 후보 조회·선택 또는 사용자 임의 재계산 기능을 제공해서는 안 된다.

### UI Requirements *(include if feature contains user-facing UI)*

- **UI-001**: 날짜별 경로 화면의 모양은 Figma Make `DayRouteScreen`을 정본으로 삼되, F005에서는 진행 전 계획 경로만 표시하고 F006 전에는 `완료`·`이동 중` 상태, 현재 위치, 장소별 도착 예정 시각을 지어내지 않아야 한다.
- **UI-002**: 여행 상세의 날짜별 일정에는 경로 계산이 완료된 경우 구간별 이동시간과 날짜 전체 이동시간을 표시하고, 사용자가 해당 날짜의 경로 화면으로 이동할 수 있는 행동을 제공해야 한다.
- **UI-002a**: 일정 저장 뒤 경로 계산만 실패한 경우 여행 상세의 일정 내용은 정상 표시하고, 해당 날짜의 경로 영역에 실패 원인과 `다시 시도`를 독립적으로 표시해야 한다.
- **UI-003**: 경로 화면은 `loading`, `empty`, `error`, `content` 상태를 구분해야 한다. 1초 이내 응답에는 대기 표시를 생략하고, `empty`에는 일정 추가 또는 돌아가기, `error`에는 원인과 `다시 시도`를 제공해야 한다.
- **UI-004**: 일정 변경에 따른 자동 계산 중에는 사용자가 보고 있던 일정을 유지하며 계산 중임을 별도로 표시해야 한다. 일정 버전이 다른 이전 경로를 현재 경로처럼 표시해서는 안 되며, 최종 실패 시 실패 안내와 `다시 시도`를 제공해야 한다.
- **UI-005**: 지도에 표시한 방문 순서, 구간 이동수단, 이동시간과 이동거리를 지도 밖 목록에서도 같은 순서로 제공해야 한다.
- **UI-006**: 지도는 이동·확대·축소할 수 있어야 하며, 장소 마커나 경로 선만으로 의미를 전달하지 않고 방문 순서 번호와 구간 목록을 함께 제공해야 한다.
- **UI-007**: 모든 터치 영역은 최소 48×48dp이고 서로 8dp 이상 떨어져야 하며, 아이콘 전용 버튼에는 접근 가능한 설명을 둬야 한다. 이동수단·성공·실패 상태는 색만으로 구분하지 않고 아이콘과 문구를 병기해야 한다.
- **UI-008**: 화면 너비 360dp와 시스템 글자 최대 배율에서도 장소명, 이동수단, 이동시간·거리, 오류 원인과 재시도 행동이 가로 스크롤이나 잘림 없이 확인 가능해야 한다.
- **UI-009**: 전체 화면 지도는 시스템 상태 영역과 하단 제스처 영역을 침범하지 않아야 하며, 지도 위에 겹치는 경로 정보가 주요 지도 조작이나 뒤로가기 행동을 가리지 않아야 한다.
- **UI-010**: Figma `DayRouteScreen`과 F005 범위가 충돌하는 진행 상태·현재 위치·도착 예정 시각 요소는 F006 구현 전에는 숨기거나 `정보 없음`으로 두고, Figma 정본에도 F005 계획 상태를 추가한 뒤 구현과 대조해야 한다.

### Key Entities *(include if feature involves data)*

- **날짜별 경로**: 특정 여행 날짜와 일정 버전을 기준으로 계산된 전체 이동 결과. 현재 적용 여부, 성공·실패 상태, 총 이동시간·거리, 계산 시각과 실패 이유를 가진다.
- **경로 구간**: 연속한 두 일정 장소 사이의 이동 결과. 출발·도착 일정 항목, 사용자가 선택한 이동수단, 이동시간·거리, 지도 표시용 경로와 제공자 정보를 가진다.
- **현재 경로**: 해당 날짜의 현재 일정 버전에 적용되는 유일한 경로. 일정이 변경되면 이전 결과는 현재 경로로 표시되지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 장소가 두 곳 이상인 날짜에서 일정 저장이 완료되어 경로 계산 단계가 시작된 뒤 10초 안에 경로 결과나 명확한 실패 안내를 확인할 수 있다. 일정 입력 검증과 DB 저장 시간은 이 10초에 포함하지 않는다.
- **SC-002**: 지원되는 이동수단으로 구성된 경로 계산 성공 사례의 100%에서 지도와 구간 목록의 장소 순서·이동수단이 저장된 일정과 일치한다.
- **SC-003**: 경로 제공자 실패 검증 사례의 100%에서 저장된 일정이 변경되지 않고 실패 원인과 `다시 시도` 행동이 제공된다.
- **SC-004**: 같은 다시 시도 요청을 반복 전송하는 검증 사례의 100%에서 현재 경로는 한 번만 교체되고 중복 결과가 노출되지 않는다.
- **SC-005**: 360dp 화면과 시스템 글자 최대 배율에서 경로 상태, 장소 순서, 구간 이동수단·시간·거리와 복구 행동을 가로 스크롤이나 잘림 없이 확인할 수 있다.
- **SC-006**: 지도 경로를 보지 않는 검증에서도 사용자는 목록만으로 모든 장소의 방문 순서와 각 구간의 이동수단·이동시간·거리를 확인할 수 있다.

## Assumptions

- F004가 저장한 일정에는 날짜별 최대 10곳의 장소, 유효한 좌표, 연속 구간별 이동수단과 일정 버전이 존재한다.
- F004의 `NOT_CALCULATED` 상태는 F005에서 계산 성공 시 `READY`, 최종 실패 시 `FAILED`로 확장된다.
- 일정 저장 성공 뒤 경로 계산을 자동으로 실행하며, 최초 계산이 최종 실패한 경우에만 사용자가 `다시 시도`를 선택한다.
- 자동 경로 계산 실패는 일정 저장 성공을 취소하지 않는다. 저장 흐름은 여행 상세로 이동하며 해당 날짜의 경로 영역만 실패 상태가 된다.
- 장소가 없는 날짜는 경로 빈 상태이고, 장소가 한 곳인 날짜는 이동 구간이 없으므로 총 이동시간 0분·총 이동거리 0m인 완료 경로다.
- 정상 경로의 복수 후보 조회·선택과 사용자 임의 재계산은 제공하지 않는다. 일정 입력이 변경되면 자동으로 계산하고, 최종 실패한 경우에만 같은 입력으로 `다시 시도`할 수 있다.
- 길찾기 제공자가 여러 후보를 반환해도 각 제공자의 기본 추천 경로 한 개만 사용하며 후보 비교·정렬·선택 기능은 제공하지 않는다.
- F005는 계획 단계 경로를 다루며 현재 위치를 사용하는 여행 시작·진행 경로와 장소별 도착 예정 시각은 F006이 담당한다.
- 일정 변경 후 계산한 새 경로가 준비되기 전에는 이전 경로를 현재 일정에 맞는 결과처럼 표시하지 않는다.
- TMAP·ODsay 실제 연동 검증에는 별도의 공유 dev/staging 환경과 test credential 준비가 필요하며, 준비 전에는 mock·local 검증만 수행한다.
- 비동기 계산 작업 조회, 서버 cache, message queue와 분산 작업 중복 방지는 MVP 범위에서 제외한다.
- 화면 배치·색상·글자·간격의 정본은 Figma Make `Design UI from Reference`의 관련 화면이며, 화면 상태와 접근성 최저선은 `docs/design/ui-guidelines.md`를 따른다.
