# Feature Specification: 대체 장소 추천

**Feature Branch**: `009-alternative-places`

**Created**: 2026-09-09

**Status**: Draft

**Input**: User description: "F009 대체 장소 추천: F008이 만든 감지 결과(계획대로 방문하기 어려운 남은 장소)에 대해, 기존 장소를 기준으로 반경을 0.5km→1km→2km로 넓혀 가며 같은 성격의 운영 중인 장소를 찾아 거리·평점·혼잡·날씨 점수로 정렬한 대체 후보를 최대 10개 추천하고, 사용자가 후보를 보고 고르거나 직접 검색으로 대체 장소를 찾을 수 있게 한다. F003의 장소·Google 보강 계약을 재사용한다. 선행 Feature는 F003(장소 검색)·F008(여행 변수 감지)이며 Feature Owner는 jy다. 변경 경로 미리보기·일정 변경·되돌리기는 F010, 장소 변경 제안 푸시 알림은 F011 범위다."

## Clarifications

### Session 2026-09-09

- Q: 대체 장소 화면으로 들어가는 진입점을 F009가 어디까지 만드나? → A: 진행 화면(ActiveTravelScreen)의 변수 경고 배너만 F009가 만든다. 감지 결과 목록 화면(Figma `VariableMonitorScreen`)과 푸시 알림 진입은 F011 범위다.
- Q: 대체 장소 화면의 `기존 일정 그대로 진행`은 무엇을 뜻하나? → A: 감지 결과를 거절(`DISMISSED`)하는 사용자 결정이다. F009가 감지 거절 계약을 새로 정의하고, F010의 미리보기 거절(REPL-003)과는 별개다.
- Q: 반경 확장(0.5→1→2km)과 카테고리 비교(소→중→대분류)의 결합 순서는? → A: 각 반경 안에서 소분류→중분류→내부 카테고리 순으로 비교하고, 그 반경에 내부 카테고리까지 후보가 0개일 때만 다음 반경으로 넓힌다.
- Q: 운영 종료 장소 제외를 위한 운영시간 조회를 반경 안 후보 전체에 하나, 점수 상위부터 하나? → A: 운영시간·평점 없이 거리·혼잡·날씨로 예비 점수를 매기고, 예비 점수 상위부터 운영 상태(와 같은 조회로 얻는 평점)를 확인해 운영 중인 후보 10개가 채워지면 멈춘다. 최종 순위는 확인된 후보로 다시 계산한다. 확인 상한은 plan에서 정한다.
- Q: Google 평점 매칭을 모든 후보 카테고리에 적용하나, F003처럼 음식·카페·쇼핑에만 적용하나? → A: 모든 카테고리에 적용한다(requirements ALT-03). F003의 카테고리 제한은 검색 결과 보완 규칙이며 평점 병합에는 적용하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 방문이 어려워진 장소의 대체 후보를 추천받는다 (Priority: P1)

여행을 진행 중인 사용자가 "이 장소는 계획대로 방문하기 어렵다"는 감지 결과(F008)를 확인하면, 시스템은 그 장소 근처에서 같은 성격의 운영 중인 장소를 찾아 거리·평점·혼잡·날씨를 종합한 점수 순으로 대체 후보를 최대 10개 제시한다. 가까운 곳(0.5km)에 후보가 없으면 1km, 다시 없으면 2km까지 넓혀 찾고, 2km 안에도 없으면 "추천할 장소가 없다"고 알린다.

**Why this priority**: F008까지는 "이 장소가 위험하다"는 사실만 알 수 있다. 위험을 알게 된 사용자가 다음에 할 일은 "그럼 어디로 가지"이며, 이 질문에 답하는 것이 이 Feature의 존재 이유다. 후보 목록만으로도 사용자는 스스로 계획을 바꿀 수 있어 F010(일정 변경) 없이도 단독 가치가 있다.

**Independent Test**: F008 감지 결과가 하나 있는 여행에서 그 감지 결과의 대체 후보를 조회해, 기존 장소와 같은 카테고리이고 도착 예정 시각에 운영 중인 장소가 거리 순이 아닌 종합 점수 순으로 최대 10개 반환되는지, 0.5km에 후보가 없을 때 1km·2km로 반경이 넓어지는지, 2km에도 없으면 후보 없음으로 응답하는지 확인하면 된다. F010·F011 없이 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사용자 결정 전(`ACTIVE`) 감지 결과가 있고 기존 장소 0.5km 안에 같은 카테고리의 운영 중인 장소가 3곳 있다, **When** 대체 후보를 조회한다, **Then** 그 3곳이 종합 점수 순으로 반환되고 탐색 반경은 0.5km로 표시된다.
2. **Given** 기존 장소 0.5km 안에는 후보가 없고 1km 안에 후보가 있다, **When** 대체 후보를 조회한다, **Then** 1km 반경의 후보가 반환되고 탐색 반경은 1km로 표시된다.
3. **Given** 기존 장소 2km 안에 같은 카테고리의 운영 중인 장소가 없다, **When** 대체 후보를 조회한다, **Then** 후보 목록이 비어 있고 최종 탐색 반경 2km가 표시되며 오류로 처리되지 않는다.
4. **Given** 반경 안에 같은 카테고리 장소가 12곳 있다, **When** 대체 후보를 조회한다, **Then** 종합 점수 상위 10곳만 반환된다.
5. **Given** 반경 안의 어떤 장소가 기존 장소의 도착 예정 시각에 폐점 이후이거나 임시휴업이다, **When** 대체 후보를 조회한다, **Then** 그 장소는 후보에서 제외된다.
6. **Given** 두 후보의 종합 점수가 같다, **When** 후보를 정렬한다, **Then** 거리가 짧은 후보, 그다음 보정 평점이 높은 후보, 그다음 리뷰 수가 많은 후보 순으로 앞에 온다.
7. **Given** 감지 결과가 이미 처리·거절·무효화되었다, **When** 대체 후보를 조회한다, **Then** 이미 처리된 감지임을 알리고 후보를 만들지 않는다.
8. **Given** 다른 사용자의 감지 결과다, **When** 대체 후보를 조회한다, **Then** 요청이 거절된다.

### User Story 2 - 후보를 한눈에 비교하고 하나를 고른다 (Priority: P2)

사용자는 대체 장소 화면에서 위험이 감지된 기존 장소와 그 이유를 위쪽에서 확인하고, 아래 목록에서 각 후보의 이름·카테고리·거리·평점·운영 마감 시각·추천 근거를 비교한다. 지도에는 기존 장소와 후보 위치가 함께 표시된다. 후보 하나를 선택하면 그 후보로 일정을 바꾸는 흐름(F010 변경 경로 미리보기)으로 넘어가고, 어느 후보도 고르지 않으면 "기존 일정 그대로 진행"을 선택할 수 있다.

**Why this priority**: US1의 후보 계약을 사용자가 실제로 보고 비교할 수 있어야 한다. 화면이 없으면 후보는 존재하지만 사용자에게 닿지 않는다. US1 계약이 확정된 뒤에 만들 수 있어 P2다.

**Independent Test**: 감지 결과가 있는 진행 중 여행에서 대체 장소 화면을 열어, 감지 요약(장소명·이유·변수 칩)과 후보 목록(순위·이름·카테고리·거리·평점·마감·근거)이 표시되는지, 1위 후보가 강조되는지, 후보 없음·불러오기 실패 상태가 각각 표시되는지, 후보 선택 시 선택한 후보 정보가 다음 흐름으로 전달되는지 확인하면 된다. F010 화면이 없어도 전달 값까지 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 대체 후보가 4곳 반환되었다, **When** 대체 장소 화면을 연다, **Then** 위쪽에 기존 장소명과 감지 이유·변수 칩이, 아래에 "추천 후보 4곳"과 순위대로 나열된 후보가 표시되고 1위 후보에는 `TOP` 표시와 강조 배경이 있다.
2. **Given** 후보 목록이 표시되어 있다, **When** 한 후보의 `경로 비교`(1위) 또는 `비교` 버튼을 누른다, **Then** 그 후보(장소 식별자·후보 식별자·이름·점수)가 F010 변경 경로 미리보기 흐름으로 전달된다.
3. **Given** 후보 목록이 표시되어 있다, **When** `기존 일정 그대로 진행`을 누른다, **Then** 그 감지 결과는 사용자가 거절한 상태(`DISMISSED`)가 되고 대체 장소 화면을 떠나 진행 화면으로 돌아가며, 진행 화면의 경고 배너에서 그 감지가 사라진다.
4. **Given** 감지 결과가 이미 거절·처리·무효화되었다, **When** 다시 `기존 일정 그대로 진행`을 요청한다, **Then** 오류 없이 현재 상태를 그대로 돌려주고 상태를 바꾸지 않는다.
5. **Given** 2km 안에 후보가 없다, **When** 대체 장소 화면을 연다, **Then** "2km 안에 추천할 장소가 없어요" 빈 상태와 함께 `기존 일정 그대로 진행`·`직접 검색해서 고르기` 두 행동이 표시된다.
6. **Given** 후보 조회가 외부 장소 데이터 장애로 실패했다, **When** 대체 장소 화면을 연다, **Then** 오류 상태와 `다시 시도하기`가 표시되고 기존 일정은 그대로 유지된다.
7. **Given** 후보 목록이 표시되어 있다, **When** 지도를 본다, **Then** 기존 장소는 경고 표식으로, 각 후보는 순위 번호 표식으로 표시되고 같은 정보가 목록으로도 제공된다.

### User Story 3 - 추천이 마음에 안 들면 직접 검색한다 (Priority: P3)

추천 후보가 없거나 마음에 들지 않을 때, 사용자는 대체 장소 화면의 `직접 검색`으로 장소를 검색해 대체 장소를 직접 고른다. 검색 결과에는 F003 장소 검색과 같은 정보에 더해 기존 장소로부터의 거리와 방문 가능 여부(임시휴업·영업 종료 확인 시 방문 불가)가 함께 표시되고, 하나를 선택하면 추천 후보를 골랐을 때와 같은 변경 흐름으로 넘어간다.

**Why this priority**: 추천이 사용자의 취향이나 상황을 다 알 수는 없다. 사용자가 최종 통제권을 갖게 하는 안전망이라 US1·US2 다음에 둔다.

**Independent Test**: 감지 결과가 있는 상태에서 키워드로 직접 검색해 각 결과에 기존 장소 기준 거리와 방문 가능 여부가 붙어 나오는지, 검색 결과 하나를 선택하면 추천 후보 선택과 같은 형식으로 다음 흐름에 전달되는지 확인하면 된다.

**Acceptance Scenarios**:

1. **Given** 감지 결과가 있다, **When** 키워드로 직접 검색한다, **Then** F003 장소 검색과 같은 장소 정보에 기존 장소로부터의 거리와 방문 가능 여부가 추가되어 페이지 단위로 반환된다.
2. **Given** 검색 결과 중 어떤 장소가 임시휴업·영업 종료로 확인된다, **When** 결과를 본다, **Then** 그 장소는 결과에서 빠지지 않고 "방문 불가"로 표시된다. 운영 상태를 확인할 수 없는 장소는 방문 가능으로 본다.
3. **Given** 검색 결과가 표시되어 있다, **When** 방문 가능한 장소 하나를 선택한다, **Then** 그 장소가 추천 후보 선택과 같은 형식으로 F010 변경 경로 미리보기 흐름에 전달된다.
4. **Given** 검색어가 2글자 미만이다, **When** 검색한다, **Then** 검색이 실행되지 않고 입력 안내가 표시된다.

### User Story 4 - 외부 데이터가 빠져도 추천은 계속된다 (Priority: P4)

평점·혼잡·날씨 중 일부 데이터를 얻지 못해도 시스템은 그 변수만 점수에서 빼고 나머지 변수의 가중치를 비례 재분배해 추천을 계속한다. 후보를 찾는 장소 데이터 자체를 받지 못하면 추천 실패를 숨기지 않고 알리며, 어느 경우에도 기존 일정은 바뀌지 않는다.

**Why this priority**: 선택적 데이터의 실패를 해당 변수에만 격리하고 핵심 결과를 줄 수 없을 때는 실패와 다음 행동을 명확히 제공해야 한다는 constitution IV의 요구다. 앞 story가 모두 외부 데이터에 의존하므로 결손 시 보장 범위를 별도 story로 못 박는다.

**Independent Test**: Google 평점 조회가 실패하도록 두고 거리·혼잡·날씨만으로 점수가 계산되어 후보가 반환되는지, 후보 응답의 점수 구성에서 평점이 빠져 있는지, 관광 장소 데이터 조회 자체가 실패하면 후보 없음이 아닌 실패로 응답하는지 확인하면 된다.

**Acceptance Scenarios**:

1. **Given** 후보 장소들의 Google 평점을 확보하지 못했다, **When** 대체 후보를 조회한다, **Then** 평점을 제외한 거리·혼잡·날씨 가중치를 비례 재분배한 점수로 후보가 정렬되고 각 후보의 점수 구성에는 평점 항목이 없다.
2. **Given** 후보 장소 근처에 혼잡 지원 지점이 없거나 혼잡 예보를 받지 못했다, **When** 대체 후보를 조회한다, **Then** 혼잡을 제외한 나머지 변수로 점수가 계산된다.
3. **Given** 관광 장소 데이터 조회가 재시도 후에도 실패했다, **When** 대체 후보를 조회한다, **Then** 후보 없음이 아니라 추천 실패로 응답하고 사용자는 다시 시도하거나 기존 일정을 유지할 수 있다.
4. **Given** 후보의 운영시간 정보를 확인할 수 없다, **When** 후보를 선별한다, **Then** 그 후보는 운영 중으로 보아 제외하지 않고 운영 상태는 "확인 불가"로 표시된다.

### Edge Cases

- 기존 장소가 Google 전용 장소(TourAPI 분류가 없는 음식·카페·쇼핑)면 내부 카테고리로만 비교하고, 소·중분류 비교 단계는 건너뛴다.
- 기존 장소 자신은 후보에서 제외한다. 같은 날짜 일정에 이미 들어 있는 다른 장소도 후보에서 제외한다.
- 감지 결과가 조회 도중 처리·무효화되면(사용자 결정, 장소 완료, 날짜 완료) 후보를 반환하지 않고 이미 처리된 감지로 안내한다.
- 후보 장소의 혼잡·날씨 판정은 기존 장소의 도착 예정 시각을 기준으로 한다. 후보까지의 실제 이동 시간으로 보정한 도착 시각은 F010 미리보기가 계산한다.
- 반경 안의 후보가 10개보다 많으면 점수 상위부터 운영 상태를 확인해 운영 중인 10개를 채운다. 운영 종료 제외나 확인 상한으로 10개 미만이 되어도 다음 반경으로 넓히지 않는다(반경 확장은 카테고리 비교까지 마친 후보가 0개일 때만). 확인 상한에 걸려 확인하지 못한 후보는 반환하지 않는다.
- 후보 조회는 요청 때마다 다시 계산하며 저장하지 않는다. 같은 감지 결과를 다시 조회하면 그 시점의 데이터로 결과가 달라질 수 있다.
- 사용자가 화면을 떠났다가 돌아오면 후보를 다시 조회한다. 갱신 중에는 기존 목록을 유지하고 1초 넘게 걸릴 때만 대기 표시를 한다.
- 직접 검색 결과에는 기존 장소 자신과 같은 날짜 일정의 다른 장소도 포함되지만 "이미 일정에 있음"으로 표시하고 선택할 수 없다.
- 후보 식별자(candidateId)는 짧은 수명을 가지며, 만료된 식별자로 다음 흐름(F010)에 넘어가면 F010이 거부하고 후보를 다시 조회하도록 안내한다. 수명 값은 plan에서 정한다.

## Requirements *(mandatory)*

### Functional Requirements

#### 후보 탐색

- **FR-001**: 시스템은 사용자 결정 전(`ACTIVE`) 상태인 감지 결과에 대해서만 대체 후보를 만들어야 한다. 이미 처리·거절·무효화된 감지 결과에 대한 후보 요청은 후보 없이 이미 처리된 감지임을 알리는 응답으로 거절해야 한다.
- **FR-002**: 시스템은 감지 결과의 기존 장소 좌표를 기준점으로 0.5km, 1km, 2km 순서로 반경을 넓혀 후보를 찾아야 한다. 어떤 반경에서 후보가 하나라도 있으면 그 반경에서 멈추고 더 넓히지 않으며, 2km 안에도 후보가 없으면 후보 없음으로 응답해야 한다. 응답에는 최종 탐색 반경을 포함한다.
- **FR-003**: 시스템은 기존 장소와 같은 성격의 장소만 후보로 삼아야 한다. TourAPI 분류를 서버 고정 매핑으로 `자연`, `문화·역사`, `음식`, `카페`, `쇼핑`, `기타` 6개 내부 카테고리로 변환하고, 각 반경 안에서 소분류가 같은 장소, 없으면 중분류가 같은 장소, 없으면 내부 카테고리(대분류)가 같은 장소 순으로 비교한다. 기존 장소에 TourAPI 분류가 없으면 내부 카테고리로만 비교한다.
- **FR-004**: 시스템은 기존 장소의 도착 예정 시각 기준으로 폐점 이후이거나 임시휴업·영업 종료가 확인되는 장소를 후보에서 제외해야 한다. 운영 상태 확인은 운영시간·평점을 확인하기 전의 예비 점수(거리·혼잡·날씨)로 후보를 정렬한 뒤 상위 후보부터 순서대로 수행하고, 운영 중인 후보 10개가 채워지면 나머지 후보는 확인하지 않는다(확인 상한은 plan에서 정한다). 최종 점수와 순위는 확인을 마친 후보에 대해 평점까지 포함해 다시 계산한다. 운영시간을 확인할 수 없는 장소는 운영 중으로 보아 제외하지 않고 운영 상태를 "확인 불가"로 표시한다. 운영시간·영업 상태 확보 방법과 실패 처리는 F008이 확립한 장소 데이터 provider 상세 조회(5초, 1회 재시도, 최종 실패 시 해당 변수 제외)를 재사용한다.
- **FR-005**: 시스템은 기존 장소 자신과 같은 날짜 일정에 이미 포함된 장소를 후보에서 제외해야 한다.
- **FR-006**: 시스템은 후보 장소의 이름·좌표·주소·카테고리·평점·리뷰 수를 F003이 확정한 장소 DTO와 제공자 규칙(TourAPI 기준, Google 평점·영업정보만 병합, 사진·리뷰 미사용)으로 제공해야 하며, 후보를 위한 새로운 장소 DTO 형식을 만들지 않는다.
- **FR-007**: 시스템은 후보 장소와 Google 장소의 매칭을 50m 이내 좌표, 장소명 유사도, 주소 부분 일치의 조합으로 판정하고, 동일 장소 여부가 모호하면 그 후보에 Google 데이터를 사용하지 않아야 한다. 이 매칭은 기존 장소의 카테고리와 무관하게 모든 후보에 적용한다.

#### 점수와 정렬

- **FR-008**: 시스템은 각 후보에 거리, 보정 평점, 혼잡, 날씨 네 변수를 종합한 점수를 산출해야 한다. 기본 가중치는 거리 35%, 평점 30%, 혼잡 20%, 날씨 15%다. 가중치와 정규화 규칙은 한곳에서 관리하며 이 명세는 값을 다시 정하지 않는다.
- **FR-009**: 시스템은 평점에 베이지안 보정을 적용해야 한다. `보정 평점 = (v/(v+m))×R + (m/(v+m))×C`이며 `R`은 장소 평점, `v`는 리뷰 수, `C`는 현재 후보 평균 평점, `m`은 현재 후보 리뷰 수 중앙값이고 후보가 5개 미만이면 `m=20`을 사용한다.
- **FR-010**: 시스템은 후보의 혼잡·날씨 변수를 F008이 확립한 판정 규칙(혼잡 지원지역 500m·카테고리 민감도, 강수확률 70%·강수량 1mm/h·강수성 상태, 실내·실외 분류)으로 기존 장소의 도착 예정 시각 시점에 대해 평가해야 하며, 판정 규칙을 새로 정의하지 않는다.
- **FR-011**: 시스템은 어떤 후보의 변수 데이터를 확보하지 못하면(Google 미매칭·평점 없음, 혼잡 지원지역 밖·예보 없음, 날씨 예보 없음) 그 변수만 점수에서 제외하고 나머지 변수의 가중치를 비례 재분배해야 한다. 각 후보 응답에는 점수에 실제로 쓰인 변수별 기여 값만 포함한다.
- **FR-012**: 시스템은 후보를 종합 점수 내림차순으로 정렬하고, FR-004의 운영 상태 확인을 통과한 상위 10개만 반환해야 한다. 동점은 거리 짧은 순, 보정 평점 높은 순, 리뷰 수 많은 순으로 정렬한다. 정렬에는 반올림 전 원점수를 쓰고, 화면 표시용 점수만 정수로 반올림해 별도로 제공한다.

#### 후보 응답과 선택 전달

- **FR-013**: 시스템은 각 후보에 장소 식별자, 이름, 카테고리, 기존 장소로부터의 거리, 평점·리뷰 수·보정 평점, 원점수·표시 점수·변수별 기여, 도착 예정 시각 기준 운영 상태(운영 중·폐점 임박·확인 불가)와 마감 시각, 그리고 다음 흐름(F010)에서 이 후보를 지목할 짧은 수명의 후보 식별자를 담아야 한다.
- **FR-014**: 시스템은 후보 목록을 저장하지 않고 요청 때마다 계산해야 한다. 후보 식별자는 감지 결과·장소·평가 시각을 포함해 위조할 수 없어야 하며, 만료 후에는 F010이 거부할 수 있어야 한다.
- **FR-015**: 사용자가 후보 또는 직접 검색 결과를 선택하면 앱은 선택한 장소(장소 식별자, 후보 식별자 또는 직접 검색 표시, 이름, 거리, 표시 점수)를 F010 변경 경로 미리보기 흐름에 전달해야 한다. F009는 선택만 전달하고 일정을 바꾸지 않는다.

#### 감지 거절

- **FR-016**: 사용자는 대체 장소 화면에서 `기존 일정 그대로 진행`을 선택해 그 감지 결과를 거절할 수 있어야 한다. 거절하면 감지 결과는 사용자가 결정한 거절 상태(`DISMISSED`)가 되고, 이후 그 감지 결과에 대한 후보 조회·직접 검색·거절 요청은 이미 처리된 감지로 처리된다. 거절은 멱등해야 하며, 이미 거절·처리·무효화된 감지 결과에 대한 거절 요청은 오류 없이 현재 상태를 돌려주고 상태를 바꾸지 않는다. 거절은 일정·경로를 바꾸지 않는다.
- **FR-017**: 거절 이후 같은 장소에 대해 새 감지 결과가 만들어지는지는 F008의 중복 억제 규칙을 따르며 F009는 정의하지 않는다. 거절 사실과 시각은 감지 결과에 추적 가능하게 남는다.

#### 직접 검색

- **FR-018**: 사용자는 감지 결과를 기준으로 키워드 직접 검색을 할 수 있어야 한다. 검색어는 공백 제거 후 2글자 이상이어야 하고, 결과는 F003 장소 검색과 같은 장소 DTO에 기존 장소로부터의 거리와 방문 가능 여부를 더해 cursor 페이지네이션으로 반환한다.
- **FR-019**: 직접 검색은 반경·카테고리 제한을 두지 않으며 임시휴업·영업 종료가 확인되는 장소를 제외하지 않고 "방문 불가"로 표시한다. 직접 검색 결과에는 폐점 시각 정보가 없으므로 도착 예정 시각 기준 폐점 판정은 적용하지 않고, 확인할 수 없으면 방문 가능으로 본다(FR-004와 같은 원칙). 기존 장소 자신과 같은 날짜 일정의 다른 장소는 "이미 일정에 있음"으로 표시하고 선택할 수 없어야 한다.
- **FR-020**: 직접 검색의 제공자 규칙(TourAPI 우선, 음식·카페·쇼핑에서 결과 부족 시 Google 보완, Google 실패 시 TourAPI 결과 유지)은 F003 장소 검색과 동일하게 적용해야 한다.

#### 실패 격리

- **FR-021**: 시스템은 후보를 찾는 관광 장소 데이터 조회가 재시도 후에도 실패하면 후보 없음이 아닌 추천 실패로 응답해야 하며, 실패를 빈 결과로 위장해서는 안 된다. 제한 시간·재시도 정책은 `docs/planning/requirements.md` 3절(TourAPI 5초, 1회 재시도)을 따른다.
- **FR-022**: 시스템은 평점(Google)·혼잡(서울시)·날씨(기상청)·운영시간(장소 데이터 provider) 조회의 실패를 해당 변수에만 격리하고, 한 변수의 실패가 다른 후보나 추천 전체를 실패시켜서는 안 된다.
- **FR-023**: 후보 조회·직접 검색·후보 선택은 어떤 경우에도 일정·경로·감지 결과 상태를 변경해서는 안 된다. F009에서 감지 결과 상태를 바꾸는 유일한 동작은 FR-016의 거절이다.

#### 소유권과 기록

- **FR-024**: 시스템은 후보 조회·직접 검색·거절 요청에서 사용자와 감지 결과가 속한 여행의 소유권을 검증하고, 다른 사용자의 감지 결과에 대한 요청을 거절해야 한다.
- **FR-025**: 시스템은 후보 조회마다 기준 감지 결과, 최종 탐색 반경, 카테고리 비교 단계, 후보 수, 각 외부 데이터의 사용 가능 여부를 추적 가능하게 기록해야 한다. 정밀 위치 등 민감정보는 기록하지 않는다.

#### 범위 경계

- **FR-026**: F009는 대체 후보 생성·조회, 직접 검색, 감지 거절, 대체 장소 화면과 선택 전달, 진행 화면의 변수 경고 배너 진입점까지만 책임진다. 변경 경로 미리보기·이동 시간 비교·일정 장소·경로 변경·되돌리기는 F010, 장소 변경 제안 푸시 알림과 알림 ON/OFF 설정은 F011 범위로 제외한다.
- **FR-027**: F009는 감지 결과의 생성·갱신·종료 규칙과 변수 판정 규칙을 F008이 정의한 대로 재사용하며, 장소 DTO·제공자 규칙을 F003이 정의한 대로 재사용한다. 두 계약을 바꿔야 하면 해당 Feature 문서와 같은 변경 범위에서 동기화한다.
- **FR-028**: 대체 장소 화면의 진입점은 진행 화면(ActiveTravelScreen)의 변수 경고 배너다. 진행 중 날짜에 사용자 결정 전(`ACTIVE`) 감지 결과가 있으면 진행 화면에 배너를 표시하고, 배너를 누르면 그 감지 결과의 대체 장소 화면을 연다. 감지 결과 목록 화면(Figma `VariableMonitorScreen`)과 푸시 알림에서의 진입은 F011 범위이며, 대체 장소 화면은 감지 결과 식별자 하나로 열 수 있어야 한다.

### UI Requirements *(include if feature contains user-facing UI)*

화면 모양의 정본은 Figma Make `AlternativePlacesScreen`(후보 있음)·`alternativesEmpty`(후보 없음)이고, 진입 배너는 `ActiveTravelScreen`의 변수 경고 영역과 `docs/design/ui-guidelines.md` 9절 "변수 경고" 형식을, 직접 검색은 F003 장소 검색 화면(`MapSearchScreen`)을 따른다. 아래는 사용자가 할 수 있어야 하는 일과 상태·접근성·검증 기준만 적는다.

- **UI-001**: 진행 화면에서 사용자는 진행 중 날짜에 사용자 결정 전(`ACTIVE`) 감지 결과가 있을 때 변수 경고 배너(장소명·감지 이유·도착 예정 시각·감지 경과 시간)를 보고, 배너를 눌러 그 감지 결과의 대체 장소 화면을 열 수 있어야 한다. 감지 결과가 여럿이면 도착 예정 시각이 가장 이른 것 하나만 배너에 보인다(Figma 배너는 단일 항목이며 나머지는 F011 감지 목록에서 다룬다). 감지 결과가 없거나 당일이 완료되었으면 배너를 표시하지 않는다(빈 상태를 만들지 않는다).
- **UI-002**: 대체 장소 화면에서 사용자는 기존 장소명, 감지 이유, 위험 변수 칩을 보고 어떤 장소가 왜 어려운지 알 수 있어야 한다. 이 값은 F008 감지 상세의 값을 그대로 사용하며 지어내지 않는다.
- **UI-003**: 사용자는 후보 목록에서 각 후보의 순위, 이름, 카테고리, 기존 장소로부터의 거리, 평점, 도착 예정 시각 기준 운영 상태·마감 시각, 추천 근거를 비교하고 1위 후보를 한눈에 구분할 수 있어야 한다. 평점이 없으면 평점 항목을 생략하고, 운영 상태가 확인 불가면 `운영시간 확인 불가`로 표시한다. 추천 근거는 F009가 가진 값(거리, 혼잡 수준, 날씨 영향, 실내·실외, 운영 상태)으로만 만들며 Figma의 `이동 시간 N분 증가` 같은 이동 시간 비교 문구는 F010 범위이므로 표시하지 않는다.
- **UI-004**: 사용자는 지도에서 기존 장소와 후보 위치를 구분해 볼 수 있어야 하며, 지도가 보여주는 정보는 목록으로도 모두 제공된다.
- **UI-005**: 사용자는 각 후보의 선택 버튼으로 그 후보를 F010 변경 경로 미리보기 흐름에 넘길 수 있고, `직접 검색`으로 직접 검색 화면을 열 수 있으며, `기존 일정 그대로 진행`으로 감지를 거절하고 진행 화면으로 돌아갈 수 있어야 한다. 거절 요청 중에는 버튼을 중복 실행할 수 없고, 실패하면 오류를 알리고 화면에 남는다.
- **UI-006**: 화면 상태는 ui-guidelines 9절을 따른다. `loading`은 1초를 넘길 때만 대기 표시, `empty`(2km 안 후보 없음)는 Figma `alternativesEmpty` 형식으로 `기존 일정 그대로 진행`·`직접 검색해서 고르기` 두 행동을 제공, `error`(추천 실패)는 `다시 시도하기`와 돌아가기를 제공하고 기존 일정은 그대로 유지, `content`는 후보 목록이다. 재조회 중에는 기존 목록을 유지한다. 이미 처리된 감지로 거절되면 그 사실을 알리고 진행 화면으로 돌아가는 행동을 제공한다.
- **UI-007**: 직접 검색 결과에서 사용자는 F003 검색 결과와 같은 정보에 더해 기존 장소로부터의 거리와 방문 가능 여부를 보고, 방문 가능한 장소만 선택할 수 있어야 한다. `방문 불가`·`이미 일정에 있음`은 문구와 비활성 표시를 병기한다.
- **UI-008**: ui-guidelines 10절 접근성 최저선을 지킨다. 터치 대상 48dp 이상·간격 8dp 이상, 아이콘 전용 버튼의 설명 문구, 폐점 임박·방문 불가·1위 후보는 색 단독이 아니라 문구·배지·테두리 병기, 화면 너비 360dp와 시스템 글자 최대 배율에서 가로 스크롤·잘림 없음.
- **UI-009**: 검증은 Compose screenshot(360dp 기본 배율, 360dp 최대 배율)으로 진행 화면 배너, 대체 장소 화면의 후보 있음·후보 없음·추천 실패·처리된 감지 상태를 남기고, 실제 서버 연동 검증은 감지 결과가 있는 진행 중 여행에서 배너→후보 조회→선택 전달, 배너→거절→배너 소멸까지 확인한다.

### Key Entities *(include if feature involves data)*

- **대체 후보**: 한 감지 결과에 대해 요청 시점에 계산되는 후보 장소 하나. 장소(F003 장소 DTO), 기존 장소로부터의 거리, 평점·리뷰 수·보정 평점, 원점수·표시 점수·변수별 기여, 도착 예정 시각 기준 운영 상태·마감 시각, 짧은 수명의 후보 식별자를 가진다. 저장하지 않는다.
- **후보 조회 결과**: 한 번의 후보 조회 응답. 최종 탐색 반경, 카테고리 비교 단계, 후보 목록(최대 10개, 점수 순), 평가 시각을 가진다.
- **후보 식별자**: 감지 결과·장소·평가 시각을 담은 위조 불가·단기 만료 토큰. F010 미리보기 생성 요청에서 검증된다.
- **직접 검색 결과**: F003 장소 검색 결과 항목에 기존 장소로부터의 거리, 방문 가능 여부(영업 상태 기준), 이미 일정 포함 여부를 더한 것.
- **감지 결과(F008 재사용)**: 후보 조회의 기준. 기존 장소, 도착 예정 시각, 변수 판정, 상태를 F008 정의대로 사용한다. F009는 이 중 `ACTIVE`→`DISMISSED` 전이(거절)만 일으킨다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `ACTIVE` 감지 결과에 대한 후보 조회의 100%가 종합 점수 내림차순으로 정렬된 최대 10개 후보 또는 명시적 후보 없음(최종 반경 2km)으로 응답한다.
- **SC-002**: 반환된 후보 중 기존 장소와 내부 카테고리가 다르거나, 도착 예정 시각 기준 폐점이 확인되는 장소가 포함되는 사례가 0건이다.
- **SC-003**: 0.5km 안에 후보가 있는 경우 탐색 반경이 0.5km로 응답하고, 0.5km에 없고 1km에 있으면 1km로 응답하는 비율이 100%다.
- **SC-004**: Google·서울시·기상청·장소 데이터 provider 중 하나 이상이 응답하지 않아도 나머지 변수로 후보가 반환되며, 선택적 데이터 실패로 추천 전체가 실패하는 사례가 0건이다.
- **SC-005**: 관광 장소 데이터 조회가 실패했을 때 빈 후보 목록으로 응답하는 사례가 0건이다.
- **SC-006**: 후보 조회·직접 검색·후보 선택으로 일정·경로·감지 결과 상태가 바뀌는 사례가 0건이다.
- **SC-010**: `기존 일정 그대로 진행` 선택의 100%가 그 감지 결과를 거절 상태로 바꾸고, 같은 요청을 반복해도 상태가 두 번 바뀌거나 오류가 나는 사례가 0건이다.
- **SC-007**: 다른 사용자의 감지 결과에 대한 후보 조회·직접 검색 요청의 100%가 거절된다.
- **SC-008**: 사용자는 대체 장소 화면을 연 뒤 3번 이하의 탭으로 후보 하나를 골라 다음 흐름(F010)에 전달할 수 있다.
- **SC-009**: 대체 장소 화면의 후보 있음·후보 없음·실패·처리된 감지 상태가 360dp·최대 글자 배율에서 잘림 없이 표시된다.

## Assumptions

- 반경 0.5km·1km·2km, 6개 내부 카테고리와 소·중·대분류 비교, Google 매칭 50m, 가중치 35/30/20/15, 베이지안 보정과 `m=20`, 상위 10개, 동점 규칙은 `docs/planning/requirements.md`(ALT-01~ALT-05, 3절), `docs/planning/functional-spec.md` 5.1·5.2, `docs/design/api-spec.md` 7.2가 확정한 값을 그대로 사용한다. 이 명세는 값을 다시 정하지 않고 한곳에서 조정 가능해야 한다는 요구만 둔다.
- 카테고리 비교와 반경 확장의 순서는 원 문서에 없어 Clarifications(2026-09-09)로 확정했다: 각 반경 안에서 소→중→내부 카테고리 순, 후보 0개일 때만 다음 반경.
- 후보 탐색용 관광 장소 데이터는 F003이 사용하는 TourAPI의 위치 기반 조회를 서버가 직접 호출해 얻는다. F003 장소 검색 API(PLACE-001)는 반경 검색을 제공하지 않으므로 화면이 F003 검색을 조합해 후보를 만들지 않는다.
- Google 평점 매칭은 `requirements.md` ALT-03에 따라 기존 장소 카테고리와 무관하게 모든 후보에 적용한다(Clarifications 2026-09-09 확정). F003의 "관광지·자연 유형은 Google 검색 결과로 보완하지 않는다"는 검색 결과 보완 규칙이며, 이미 확보한 TourAPI 후보에 평점을 병합하는 것과는 구분한다. F008이 운영시간 확인을 위해 이미 수행하는 Google 상세 조회 결과를 재사용할 수 있으면 재사용한다.
- 후보의 혼잡·날씨는 기존 장소의 도착 예정 시각 시점을 기준으로 후보 좌표에 대해 평가한다. 후보까지의 이동 시간을 반영한 도착 시각은 F010 미리보기가 계산한다.
- 감지 결과와 기존 장소의 도착 예정 시각·변수 판정·이유 문구는 F008 감지 상세(DETECT-002)에서 가져온다. F009는 이를 다시 계산하지 않는다.
- 후보 조회·직접 검색 API의 경로·응답 형태는 `docs/design/api-spec.md` ALT-001·ALT-002를 기준으로 하되, 후보 식별자(`candidateId`)·운영 상태·마감 시각·카테고리 비교 단계 필드는 현재 예시에 없으므로 plan 단계에서 확정하고 같은 변경 범위에서 api-spec을 동기화한다.
- 후보 식별자의 수명과 서명 방식은 `docs/design/er-schema.md` 8.1(감지·장소·평가시각을 포함한 짧은 수명의 서명 토큰, `alternative_candidates` 테이블 없음)을 따르며 구체 값은 plan에서 정한다.
- 대체 장소 화면의 진입점은 진행 화면의 변수 경고 배너다(2026-09-09 Owner 결정). 감지 목록 화면(Figma `VariableMonitorScreen`)과 푸시 알림 진입은 F011 범위다. 화면 자체는 감지 결과 식별자 하나로 열 수 있어야 한다.
- `기존 일정 그대로 진행`은 감지 결과를 거절(`DISMISSED`)하는 사용자 결정이다(2026-09-09 Owner 결정). 이를 위한 감지 거절 계약은 `docs/design/api-spec.md`에 아직 없으므로 plan 단계에서 정의하고 api-spec·er-schema를 같은 변경 범위에서 동기화한다. F010의 미리보기 거절(REPL-003)은 미리보기 단위의 거절이며 이와 별개다.
- 직접 검색 화면은 F003 장소 검색 화면을 재사용하고 거리·방문 가능 표시만 더한다. 새 검색 화면을 만들지 않는다.
- 직접 검색 결과의 방문 가능 여부는 F003 장소 DTO의 영업 상태(임시휴업·영업 종료)로만 판정한다. F003 DTO에는 폐점 시각이 구조화되어 있지 않아 도착 예정 시각 기준 판정은 후보 추천(FR-004)에만 적용한다. F008이 요청한 F003 장소 상세 계약 확장(구조화된 운영시간)이 반영되면 같은 판정을 직접 검색에도 넓힐 수 있다.
- Google Places·TourAPI·서울시·기상청의 실제 연동 검증은 G001 공유 dev/staging 환경과 credential에 의존한다. 그 전에는 mock·계약 테스트로 검증한다.
- 서버 캐시와 후보 저장은 MVP 범위 밖이므로(`docs/planning/mvp.md` 3절) 후보는 요청마다 계산한다. 운영 상태 확인은 점수 상위부터 운영 중 10개를 채울 때까지만 수행하며(Clarifications 2026-09-09), 확인 상한과 외부 호출 수 상한은 plan에서 정한다.

## Dependencies

- **F008 여행 변수 감지**(DONE, 2026-09-09 PR #319 병합): 감지 결과(`ACTIVE` 상태, 기존 장소, 도착 예정 시각, 변수 판정, 이유), 혼잡·날씨·운영시간 평가 규칙과 장소 데이터 provider 상세 조회. F009는 이 결과와 규칙을 재사용한다.
- **F003 장소 검색**(DONE): 장소 DTO, TourAPI·Google 제공자 규칙, 6개 내부 카테고리 매핑, 장소 검색 화면. F009는 이를 재사용하고 새 DTO를 만들지 않는다.
- **F006 여행 진행**(DONE): 진행 중 날짜, 남은 장소, 도착 예정 시각. F008을 통해 간접 의존한다.
- **F004 일정 구성**(DONE): 같은 날짜 일정에 포함된 장소 목록(후보 제외용).
- **G001 외부 연동 검증 Gate**: TourAPI·Google Places credential(F003에서 확보), 서울시·기상청 credential(F008에서 확보)과 공유 dev/staging 환경. 실제 연동 검증 task만 이 Gate에 의존한다.
- **F010 일정 변경·F011 알림**(미착수): F009가 전달한 선택과 후보 식별자를 소비한다. F009는 이들 없이도 후보 조회·화면·선택 전달까지 완결되어야 한다.

## Out of Scope

- 변경 경로 미리보기, 이동 시간 비교, 일정 장소·경로 변경, 승인·거절·되돌리기(F010)
- 장소 변경 제안 푸시 알림 전달과 알림 ON/OFF 설정(F011)
- 후보 결과 저장·캐시, `alternative_candidates` 테이블(`er-schema.md` 8.1)
- 사용자별 추천 가중치 조절, 추천 근거의 개인화
- 한국관광공사의 관광지 집중률·지역별 관광 수요 관련 추가 API
- Google 사진·리뷰 표시(F003 규칙 유지)
- 감지 결과 목록 화면(Figma `VariableMonitorScreen`)과 푸시 알림에서의 진입(F011)
