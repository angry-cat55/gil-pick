## Clarifications

### Session 2026-08-24

- Q: 현재 기기 로그아웃 요청이 네트워크 단절이나 서버 오류로 실패해도 앱은 즉시 로컬 로그아웃을 완료해야 합니까? → A: 로컬 로그아웃을 즉시 완료하고 서버 폐기는 연결 복구 후 재시도한다.
- Q: 같은 기기에서 거의 동시에 두 건의 유효한 Refresh Token 갱신 요청이 도착하면 몇 건을 성공시켜야 합니까? → A: 정확히 한 요청만 성공하고 나머지는 이미 교체된 Token으로 거절한다.
- Q: Refresh Token을 갱신할 때 새 Token의 만료 시각은 어떻게 계산해야 합니까? → A: 갱신할 때마다 새 Refresh Token을 발급 시점부터 30일간 유효하게 한다.
- Q: 앱 시작 중 Access Token이 만료되어 갱신을 시도했지만 네트워크 장애로 결과를 확인할 수 없으면 사용자를 어떻게 처리해야 합니까? → A: 로그인 상태를 보존하고 재시도 화면을 표시하며, Token이 무효로 확인될 때만 재로그인을 요구한다.
- Q: 카카오 인가 코드 교환이나 사용자 정보 조회가 시간 초과되면 자동 재시도를 어떻게 처리해야 합니까? → A: 인가 코드 교환 시간 초과 시 새 인증을 요구하고, 사용자 정보 조회만 한 번 자동 재시도한다.

### Session 2026-08-25

- Q: 카카오 공식 지원 범위와 충돌하는 앱 직접 인가 코드 전달 계약을 어떤 흐름으로 대체합니까? → A: Backend HTTPS callback이 인가 코드를 교환하고 Android에는 verified App Link로 짧은 수명의 일회용 login ticket만 전달한다.
- Q: 공모전 MVP에서 로그인 완료 시간과 Refresh 신뢰성을 어떻게 검증합니까? → A: App Link 수신부터 인증 완료 화면까지 mock 반복 20회 중 19회 이상을 10초 이내로 확인하고, 서로 다른 유효 session 100건의 Refresh가 모두 성공하는지 검증한다.
- Q: AndroidKeyStore key가 손실되어 pending logout 자격을 복호화할 수 없으면 어떻게 처리합니까? → A: 읽을 수 없는 local envelope를 제거하고 local logout을 유지하며, 서버 자격은 최대 30일 만료 또는 같은 기기 재로그인 시 교체에 의존하는 MVP 잔여 위험으로 허용한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 카카오 계정으로 로그인 (Priority: P1)

로그인하지 않은 Android 사용자는 카카오 계정으로 본인 확인을 마치고 길픽에 로그인하여 여행 목록으로 진입한다. 처음 방문한 사용자와 기존 사용자 모두 같은 흐름을 사용한다.

**Why this priority**: 인증은 모든 개인 여행 기능에 접근하기 위한 선행 조건이며, F002 여행 관리·F003 장소 검색·F012 사용자 설정을 시작할 수 있게 한다.

**Independent Test**: 로그아웃 상태에서 유효한 카카오 인증을 완료했을 때 로그인 상태와 사용자 정보가 제공되고 여행 목록 진입이 가능함을 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 길픽을 처음 사용하는 사용자가 로그아웃 상태이고, **When** 앱이 제공한 카카오 인증 화면에서 인증을 완료하고 verified App Link로 돌아오면, **Then** 앱은 일회용 login ticket을 교환하여 길픽 사용자와 현재 기기 세션을 생성하고 여행 목록으로 진입한다.
2. **Given** 기존 길픽 사용자가 로그아웃 상태이고, **When** 같은 흐름으로 기존에 연결한 카카오 계정 인증을 완료하면, **Then** 중복 사용자 생성 없이 기존 사용자로 로그인한다.
3. **Given** 사용자가 다른 기기에서 이미 로그인한 상태이고, **When** 현재 기기에서도 같은 카카오 계정으로 인증을 완료하면, **Then** 기존 기기의 로그인 상태를 유지하면서 현재 기기에도 별도 로그인 상태가 생성된다.
4. **Given** 카카오 인증 정보가 유효하지 않거나 만료되었고, **When** 사용자가 로그인을 시도하면, **Then** 로그인되지 않으며 다시 인증할 수 있는 오류 안내를 받는다.
5. **Given** 카카오 인증 서비스를 일시적으로 이용할 수 없고, **When** 사용자가 로그인을 시도하면, **Then** 로그인되지 않으며 잠시 후 재시도할 수 있다는 안내를 받는다.
6. **Given** 인가 코드 교환 결과를 시간 안에 확인하지 못했고, **When** 로그인 처리를 계속할 수 없으면, **Then** 같은 인가 코드를 자동으로 다시 사용하지 않고 사용자에게 새 카카오 인증을 안내한다.
7. **Given** 인가 코드 교환은 성공했지만 카카오 사용자 정보 조회가 시간 초과되었고, **When** 시스템이 복구를 시도하면, **Then** 사용자 정보 조회만 한 번 자동 재시도하고 최종 실패 시 사용자나 기기 로그인 상태를 생성하지 않는다.

### User Story 2 - 로그인 상태 갱신 (Priority: P2)

로그인한 사용자는 짧은 유효기간의 접근 자격이 만료되어도, 현재 기기의 장기 로그인 자격이 유효한 동안 다시 카카오 로그인을 하지 않고 서비스를 계속 이용한다.

**Why this priority**: 반복 로그인을 줄이면서도 접근 자격의 유효기간을 제한하여 사용성과 보안을 함께 유지한다.

**Independent Test**: 접근 자격만 만료된 현재 기기에서 유효한 갱신 자격으로 새 로그인 자격을 받고 보호된 기능을 계속 이용할 수 있는지 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 현재 기기의 Access Token은 만료되었지만 Refresh Token은 유효하고, **When** 앱이 로그인 상태 갱신을 요청하면, **Then** 새 Access Token과 발급 시점부터 30일간 유효한 새 Refresh Token이 발급되어 사용자가 중단 없이 서비스를 계속 이용한다.
2. **Given** Refresh Token이 만료되었거나 이미 폐기되었고, **When** 앱이 로그인 상태 갱신을 요청하면, **Then** 갱신되지 않고 사용자는 다시 카카오 로그인을 하도록 안내받는다.
3. **Given** Refresh Token을 발급받은 기기와 요청 기기가 다르고, **When** 로그인 상태 갱신을 요청하면, **Then** 갱신이 거절되고 다른 기기의 로그인 상태는 변경되지 않는다.
4. **Given** 같은 기기의 동일한 유효 Refresh Token으로 두 갱신 요청이 거의 동시에 도착하고, **When** 시스템이 두 요청을 처리하면, **Then** 정확히 한 요청만 새 로그인 자격을 받고 나머지 요청은 이미 교체된 Token 재사용으로 거절된다.
5. **Given** Access Token이 만료되었고 Refresh Token의 유효 여부는 확인되지 않았으며, **When** 네트워크 장애로 갱신 결과를 확인할 수 없으면, **Then** 앱은 로그인 상태를 보존하되 보호된 기능 접근을 중단하고 재시도 화면을 표시한다.

### User Story 3 - 현재 기기에서 로그아웃 (Priority: P3)

로그인한 사용자는 현재 사용 중인 기기에서만 로그아웃하고, 같은 계정으로 로그인한 다른 기기의 이용 상태는 유지한다.

**Why this priority**: 다중 기기 사용을 보장하면서 분실·공용 기기 등에서 특정 기기의 장기 로그인 상태를 종료할 수 있어야 한다.

**Independent Test**: 두 기기에 같은 계정으로 로그인한 뒤 한 기기에서 로그아웃했을 때 해당 기기만 재로그인이 필요하고 다른 기기는 계속 이용 가능한지 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 같은 계정이 두 기기에 로그인되어 있고, **When** 한 기기에서 로그아웃하면, **Then** 현재 기기의 로그인 자격만 제거되고 다른 기기의 로그인 상태는 유지된다.
2. **Given** 현재 기기에서 로그아웃을 완료했고, **When** 앱을 다시 실행하면, **Then** 저장된 로그인 상태로 보호된 기능에 진입하지 못하고 로그인 화면이 표시된다.
3. **Given** 같은 기기와 같은 로그인 자격으로 이미 로그아웃했고, **When** 동일한 로그아웃 요청을 다시 보내면, **Then** 다른 상태를 변경하지 않고 성공으로 처리한다.
4. **Given** 다른 기기에 속한 로그인 자격으로, **When** 로그아웃을 요청하면, **Then** 다른 기기의 상태를 변경하지 않고 요청이 거절된다.
5. **Given** 네트워크 단절이나 서버 오류가 발생한 상태이고, **When** 사용자가 로그아웃하면, **Then** 앱은 즉시 로그인 상태를 종료하고 로그인 화면으로 전환하며 연결 복구 후 현재 기기의 서버 로그인 자격 폐기를 재시도한다.

### Edge Cases

- 사용자가 카카오 인증 화면에서 동의를 취소하면 길픽 사용자를 생성하거나 로그인 상태를 만들지 않고 로그인 화면으로 돌아간다.
- 같은 login ticket이 반복 전달되어도 최초 한 번만 로그인에 성공하고 동일 사용자·동일 기기의 활성 로그인 상태가 중복 생성되지 않는다.
- 카카오 callback의 `state`가 로그인 시작 시 발급한 값과 일치하지 않거나 만료되었으면 인가 코드를 교환하거나 로그인 상태를 생성하지 않는다.
- 카카오 계정에는 닉네임이나 프로필 이미지가 없을 수 있으며, 이 경우에도 로그인은 가능하고 누락 정보는 빈 값으로 표시한다.
- 네트워크가 최초 로그인 도중 끊기면 불완전한 로그인 상태를 성공으로 표시하지 않고 로그인 재시도 경로를 제공한다.
- 카카오 인가 코드 교환이 시간 초과되면 소비 여부를 확인할 수 없는 같은 인가 코드를 자동으로 재사용하지 않고 새 카카오 인증을 요구한다.
- 인가 코드 교환 후 카카오 사용자 정보 조회만 시간 초과되면 한 번 자동 재시도하며, 다시 실패하면 부분 로그인 상태를 남기지 않고 최종 실패로 처리한다.
- 네트워크가 로그인 상태 갱신 도중 끊기면 기존 로그인 상태를 보존하되 보호된 기능 접근을 잠시 중단하고 갱신 재시도 경로를 제공한다. 통신 실패만으로 로그아웃해서는 안 된다.
- 같은 Refresh Token을 사용한 두 갱신 요청이 거의 동시에 도착하면 정확히 한 요청만 성공하며, 나머지는 이미 교체된 자격의 재사용으로 거절한다.
- 기기 식별자가 누락되거나 올바르지 않으면 로그인 상태를 생성·갱신·종료하지 않는다.
- 로그아웃 이후 기존 Access Token의 남은 유효기간이 있더라도 앱은 해당 기기의 로그인 자격을 활성 로그인 상태에서 제거하고 보호된 화면에 진입하지 않는다.
- 서버 로그아웃에 실패한 뒤 앱이 종료되거나 기기가 재시작되어도 폐기 대기 상태를 보존하고, 다음 연결 시 현재 기기의 서버 로그인 자격 폐기를 다시 시도한다.
- Refresh 성공 응답이 유실된 직후 로그아웃하면 앱이 보유한 이전 Refresh Token으로 서버 세션을 폐기하지 못할 수 있다. MVP에서는 해당 자격이 최대 30일 후 만료되거나 같은 기기 재로그인 시 교체되는 잔여 위험을 허용한다.
- AndroidKeyStore key가 손실·무효화되어 pending logout 자격을 복호화할 수 없으면 앱은 해당 envelope를 제거하고 local logout을 유지한다. 이때 서버 자격의 최대 30일 만료 또는 같은 기기 재로그인 교체에 의존하는 잔여 위험을 허용한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 Android 사용자가 카카오 계정 인증 결과를 이용해 길픽에 로그인할 수 있도록 해야 한다.
- **FR-002**: 시스템은 현재 기기에 결합된 로그인 transaction과 카카오 인증 URL을 발급해야 한다. 카카오는 인가 코드를 등록된 Backend HTTPS callback으로 전달해야 하며, Backend는 요청별 `state`를 검증한 뒤 인가 코드를 카카오 Token으로 교환하고 사용자를 확인해야 한다. Android 앱에는 카카오 인가 코드나 Token 대신 짧은 수명의 일회용 login ticket만 verified App Link로 전달해야 한다.
- **FR-003**: 시스템은 처음 확인된 카카오 계정에는 길픽 사용자를 생성하고, 이미 연결된 계정에는 기존 사용자를 재사용해야 한다.
- **FR-004**: 앱이 현재 기기에 결합된 유효한 login ticket을 한 번 교환하면 시스템은 사용자 식별자, 표시 가능한 프로필 정보, Access Token 및 Refresh Token과 각각의 유효기간을 제공해야 한다.
- **FR-005**: Access Token은 발급 후 1시간 동안 유효해야 한다. Refresh Token은 최초 로그인과 각 갱신에서 새로 발급되며 발급 시점부터 30일 동안 유효해야 하고, 최초 로그인 시점을 기준으로 한 별도의 절대 만료 상한은 MVP에서 적용하지 않아야 한다.
- **FR-006**: 시스템은 같은 카카오 계정의 다중 기기 로그인을 허용하고 기기별 로그인 상태를 서로 독립적으로 관리해야 한다.
- **FR-007**: 유효한 현재 기기 Refresh Token으로 갱신을 요청하면 시스템은 새 Access Token과 새 Refresh Token을 발급하고 이전 Refresh Token을 더 이상 사용할 수 없게 해야 한다. 동일한 Refresh Token을 사용한 갱신 요청이 겹치면 정확히 한 요청만 성공해야 한다.
- **FR-008**: 시스템은 만료·무효·폐기된 Refresh Token 또는 발급 기기와 일치하지 않는 요청을 거절해야 하며 다른 기기의 로그인 상태를 변경해서는 안 된다.
- **FR-009**: 사용자는 네트워크나 서버 상태와 관계없이 현재 기기에서 즉시 로그아웃할 수 있어야 하며, 다른 기기의 로그인 상태는 유지되어야 한다.
- **FR-010**: 로그아웃한 앱은 Access Token과 Refresh Token을 활성 로그인 상태에서 즉시 제거하고 로그인 화면으로 전환해야 한다. 서버의 현재 기기 Refresh Token 폐기에 실패하면 폐기 요청별 자격을 안전한 대기 큐에 격리하여 연결 복구 후 서버가 폐기 완료 또는 해당 자격의 무효를 확정할 때까지 재시도하고, 폐기 대기 자격을 인증이나 로그인 상태 갱신에 사용해서는 안 된다. 단, AndroidKeyStore key 손실로 자격을 복호화할 수 없으면 읽을 수 없는 envelope를 제거하고 local logout을 유지하며 서버 자격의 자연 만료 또는 같은 기기 재로그인 교체에 의존한다.
- **FR-011**: 시스템은 유효하지 않은 인가 코드, 카카오 인증 실패, 외부 서비스 장애, 자격 만료, 기기 불일치를 사용자가 다음 행동을 선택할 수 있는 구분된 실패 결과로 제공해야 한다. 인가 코드 교환 시간 초과에는 같은 코드의 자동 재사용 없이 새 카카오 인증을 안내하고, 교환 후 사용자 정보 조회 시간 초과에는 한 번만 자동 재시도해야 한다. 앱은 갱신 중 통신 실패와 확인된 Token 무효를 구분하여, 통신 실패에는 로그인 상태 보존과 재시도를 제공하고 확인된 만료·폐기·기기 불일치에는 재로그인을 요구해야 한다.
- **FR-012**: 인증 실패 또는 외부 서비스 장애가 발생해도 사용자나 기기 로그인 상태를 부분적으로 생성·변경해서는 안 되며, 카카오 사용자 정보 조회의 한 차례 재시도까지 실패하면 로그인 시도를 최종 실패로 종료해야 한다.
- **FR-013**: Refresh Token 원문과 인증 비밀정보는 불필요하게 노출하거나 기록하지 않아야 하며, 현재 기기의 로그인 자격은 다른 앱이나 권한 없는 사용자가 읽을 수 없도록 보호해야 한다.
- **FR-014**: 시스템은 로그인·갱신·로그아웃 처리 결과를 요청 단위로 추적할 수 있어야 하되, Token 원문이나 불필요한 개인정보를 추적 정보에 포함해서는 안 된다.
- **FR-015**: 이메일 회원가입, 다른 소셜 로그인, 모든 기기 일괄 로그아웃, 계정 탈퇴 및 내 정보 조회는 이 Feature 범위에 포함하지 않아야 한다.

### Key Entities

- **사용자**: 카카오 계정과 연결된 길픽 이용자다. 고유 식별자, 카카오 제공자 식별 정보, 선택적인 닉네임과 프로필 이미지를 가진다.
- **기기 로그인 상태**: 한 사용자와 한 Android 기기의 로그인 관계다. 기기 식별자, Refresh Token의 검증 정보, 만료 시각, 폐기 여부를 가지며 사용자당 여러 기기 상태가 존재할 수 있다.
- **로그인 자격**: 보호된 기능 접근에 사용하는 1시간 유효 Access Token과 로그인 상태 갱신에 사용하는 Refresh Token의 묶음이다. Refresh Token은 회전할 때마다 발급 시점부터 30일간 유효하며, 각 자격은 대상 사용자와 기기를 가진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: mock 환경에서 verified App Link 수신부터 인증 완료 후 빈 여행 목록 shell 표시까지 반복한 20회 중 19회 이상이 10초 이내에 완료되고, 실제 카카오 test 계정 종단간 로그인이 한 번 이상 성공한다.
- **SC-002**: 외부 장애가 없는 test 환경에서 서로 다른 유효 session 100건의 Refresh Token 갱신이 모두 성공하고, 동일한 Refresh Token의 동시 요청에서는 정확히 한 요청만 성공한다.
- **SC-003**: 만료되었거나 서명·issuer·audience·type이 유효하지 않은 Access Token을 사용한 검증 시도의 100%가 보호 API handler 실행 전에 거절된다.
- **SC-004**: 두 기기에 로그인한 계정으로 한 기기에서 로그아웃하는 검증 시나리오의 100%에서 현재 기기만 재로그인이 필요하고 다른 기기는 계속 이용할 수 있다.
- **SC-005**: 로그인·갱신·로그아웃의 정의된 정상 및 오류 acceptance scenario가 모두 통과하며, 실패한 경우 사용자가 재시도 또는 재로그인 중 다음 행동을 식별할 수 있다.
- **SC-006**: 인증 관련 검증 로그와 사용자에게 제공되는 오류 정보에서 Token 원문과 인증 비밀정보 노출 건수가 0건이다.
- **SC-007**: 만료·무효·폐기되었거나 다른 기기에 속한 Refresh Token을 사용한 갱신·로그아웃 요청의 100%가 거절되고 다른 기기 session은 변경되지 않는다.

## Assumptions

- MVP 클라이언트는 Android 앱이며, 카카오 계정 인증에 필요한 앱 등록과 사용자 동의 화면은 사용할 수 있다고 가정한다. Backend HTTPS callback과 Android verified App Link는 공모전용 HTTPS domain 하나에 대해 debug·제출용 release fingerprint와 `assetlinks.json`을 구현 단계에서 확정한다.
- 로그인·갱신 시 사용자는 네트워크에 연결되어 있고 카카오 인증 서비스가 정상일 때의 흐름을 기본으로 하며, 일시적 장애는 명시된 실패 흐름으로 처리한다.
- 앱이 생성한 기기 식별자는 앱 설치 단위로 안정적으로 유지되며 사용자가 앱 데이터를 삭제하면 새 기기로 취급한다.
- 닉네임과 프로필 이미지는 선택 정보이며, 제공되지 않아도 로그인과 핵심 여행 기능 이용을 제한하지 않는다.
- Access Token 만료 전 즉시 서버에서 폐기하는 기능은 MVP 로그아웃 범위에 포함하지 않는다. 로그아웃 시 앱이 현재 기기의 활성 로그인 자격을 즉시 제거하고, 서버의 Refresh Token 폐기가 실패하면 연결 복구 후 재시도하여 재사용을 차단한다.
- 카카오 계정 연결 해제, 길픽 계정 탈퇴, 사용자 프로필 수정 및 내 정보 조회는 별도 Feature에서 다룬다.
- 카카오 인증 서비스의 이용 정책, 장애 및 응답 지연은 외부 의존성으로 본다.
- F002 여행 목록 구현 전에는 인증 성공 후 빈 여행 목록 shell을 표시하고, F002가 구현되면 같은 navigation destination에 실제 목록을 연결한다.
