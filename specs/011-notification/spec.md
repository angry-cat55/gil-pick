## User Scenarios & Testing *(mandatory)*

### User Story 1 - 이 기기로 알림을 받도록 등록한다 (Priority: P1)

로그인한 사용자의 앱은 이 기기의 푸시 토큰을 서버에 등록해, 이후 서버가 이 사용자에게 보낼 알림이 이 기기에 도달할 수 있게 한다. 토큰이 갱신되면 등록 정보를 새로 맞추고, 로그아웃하면 이 기기의 토큰을 해제해 더 이상 이 기기로 알림이 가지 않게 한다. 서버는 전송 중 더 이상 유효하지 않은 토큰을 발견하면 그 기기의 토큰을 스스로 비운다.

**Why this priority**: 어떤 알림도 받을 기기가 등록돼 있어야 도달한다. 이 story가 없으면 이후 모든 알림 story가 "생성은 되지만 사용자에게 닿지 않는" 상태가 된다. 등록·해제·정리만으로도 독립적으로 검증 가능하다.

**Independent Test**: 로그인한 기기에서 푸시 토큰 등록을 요청하면 그 기기 세션에 토큰이 저장되고, 같은 기기가 토큰을 바꿔 다시 등록하면 이전 값이 대체되며, 로그아웃 시 그 기기의 토큰이 비워지고, 서버가 무효 토큰을 확인하면 해당 기기의 토큰만 비워지는지 확인하면 된다. 실제 알림 발송 없이 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 로그인된 기기이고 저장된 푸시 토큰이 없다, **When** 앱이 이 기기의 푸시 토큰을 등록한다, **Then** 그 기기 세션에 토큰·플랫폼이 저장되고 등록 성공이 반환된다.
2. **Given** 이미 푸시 토큰이 등록된 기기다, **When** 새 토큰 값으로 다시 등록한다, **Then** 같은 기기 세션의 토큰이 새 값으로 교체되고 중복 세션이 생기지 않는다.
3. **Given** 푸시 토큰이 등록된 기기다, **When** 그 기기에서 로그아웃한다, **Then** 그 기기의 푸시 토큰이 비워지고 다른 기기의 토큰은 그대로다.
4. **Given** 한 사용자가 두 기기에 로그인해 각각 토큰을 등록했다, **When** 서버가 그 사용자에게 알림을 보낸다, **Then** 두 기기 모두 대상이 된다.
5. **Given** 어떤 기기의 등록된 토큰이 발송 시점에 무효로 확인된다, **When** 서버가 그 사용자에게 알림을 보낸다, **Then** 그 기기의 토큰만 비워지고 알림 생성·다른 기기 전송은 실패하지 않는다.
6. **Given** 다른 사용자의 기기 식별자다, **When** 그 기기의 토큰 해제를 요청한다, **Then** 요청이 거절된다.

### User Story 2 - 장소 변경 제안 알림을 받고 대체 장소로 들어간다 (Priority: P1)

여행을 진행 중인 사용자에게 "남은 일정 중 계획대로 방문하기 어려운 장소가 있다"는 감지 결과가 새로 생기면, 시스템은 그 사용자에게 장소 변경을 검토하라는 알림을 보낸다. 앱이 꺼져 있거나 다른 화면을 보고 있어도 알림이 도달하며, 알림을 누르면 그 감지 결과의 대체 장소 화면이 열린다. 알림에는 어떤 화면을 다시 불러올지에 필요한 식별자만 담기고 장소 정보 본문은 담기지 않는다.

**Why this priority**: F008이 위험을 감지해도 사용자가 앱을 보고 있지 않으면 소용이 없다. 진행 중 사용자가 다른 일에 집중하는 동안 "지금 봐야 할 것이 생겼다"를 알리는 것이 이 Feature의 핵심 절반이다. 감지 결과 하나만 있으면 독립적으로 검증할 수 있다.

**Independent Test**: 진행 중 여행에 `ACTIVE` 감지 결과가 새로 생기도록 하고, 등록된 기기에 장소 변경 제안 알림이 1건 전달되는지, 알림 본문에 장소 상세가 아니라 재조회 식별자(여행·감지)만 있는지, 알림을 눌러 그 감지 결과의 대체 장소 화면(F009)이 열리는지, 같은 감지 결과에 대해 사용자가 결정하기 전까지 같은 알림이 다시 오지 않는지 확인하면 된다.

**Acceptance Scenarios**:

1. **Given** 진행 중 날짜에 장소 변경 제안 알림이 켜져 있고 감지 결과가 하나도 없다, **When** 재평가로 어떤 장소에 `ACTIVE` 감지 결과가 처음 생성된다, **Then** 그 사용자의 등록된 기기에 "장소 변경" 유형 알림 1건이 전달되고 알림 목록에도 1건 적재된다.
2. **Given** 방금 장소 변경 제안 알림을 받은 감지 결과가 있다, **When** 같은 장소의 같은 감지 결과가 재평가로 갱신된다(사용자 결정 전), **Then** 새 알림을 보내지 않는다.
3. **Given** 장소 변경 제안 알림을 받았다, **When** 알림을 누른다, **Then** 그 감지 결과 식별자로 대체 장소 화면(F009)이 열린다.
4. **Given** 장소 변경 제안 알림의 payload를 살펴본다, **When** 내용을 확인한다, **Then** 여행 식별자와 감지 결과 식별자, 알림 유형, 짧은 제목·본문 문구만 있고 후보 목록·좌표·평점 같은 도메인 데이터는 없다.
5. **Given** 사용자가 그 감지 결과를 이미 거절(`DISMISSED`)했거나 장소가 처리되어 감지가 무효화(`INVALIDATED`)됐다, **When** 뒤늦게 알림을 누른다, **Then** 대체 장소 화면은 "이미 처리된 감지"로 안내하고 진행 화면으로 돌아가는 행동을 제공한다.
6. **Given** 감지 결과가 생성됐지만 그 사용자의 등록된 기기 토큰이 하나도 없다, **When** 알림을 보낸다, **Then** 전송 대상이 없어 실패로 처리하지 않고 알림 목록 적재는 정상 수행되어 다음 접속 때 확인할 수 있다.

### User Story 3 - 도착·출발 확인과 자동 처리 알림을 받는다 (Priority: P2)

여행 진행 중 자동 위치 감지가 도착 또는 출발 후보를 만들면, 시스템은 사용자에게 "도착했는지 / 출발했는지" 확인을 요청하는 알림을 보낸다. 사용자가 응답하지 않아 자동으로 처리되면 "자동으로 처리했고 되돌릴 수 있다"는 알림을 보낸다. 도착 확인에 "아직이에요"로 답한 뒤 다시 물을 때도 알림으로 알린다. 알림을 누르면 진행 화면의 해당 확인 위치로 이동한다.

**Why this priority**: 도착·출발 확인은 F006/F007이 만든 확인 후보를 사용자가 제때 봐야 동작한다. 앱을 보고 있지 않은 사용자에게 이를 알리는 것이 이 Feature의 나머지 절반이다. US2(장소 변경 제안)와 알림 파이프라인을 공유하므로 그 뒤에 둔다.

**Independent Test**: 진행 중 여행에서 도착 후보가 생성되면 도착 확인 알림이 전달되는지, 5분 무응답으로 자동 확정되면 자동 처리 알림이 전달되는지, "아직이에요" 후 재질문 시점에 알림이 한 번 더 오는지, 각 알림을 눌러 진행 화면이 열리는지, 마지막 장소 도착으로 당일이 완료되면 이후 확인 알림이 발송되지 않는지 확인하면 된다.

**Acceptance Scenarios**:

1. **Given** 진행 중 항목에 도착 확인 후보가 새로 생성됐다, **When** 알림을 보낸다, **Then** "도착 확인" 유형 알림 1건이 등록된 기기에 전달되고 알림 목록에 적재되며 payload에는 여행·항목·전환 식별자만 있다.
2. **Given** 도착 확인 후보에 사용자가 5분간 응답하지 않아 자동 확정됐다, **When** 자동 확정이 처리된다, **Then** "자동 도착 처리" 유형 알림 1건이 전달되고 본문에 되돌리기 가능 시간 안내가 포함된다.
3. **Given** 도착 확인에 "아직이에요"로 답해 10분 뒤 재질문이 예정됐다, **When** 재질문 시점이 된다, **Then** 도착 확인 알림이 한 번 더 전달되고, 같은 장소 총 알림 횟수는 최초 포함 2회를 넘지 않는다.
4. **Given** 출발 확인 후보가 생성됐다, **When** 알림을 보낸다, **Then** "출발 확인" 유형 알림이 전달된다. `아직 머무는 중`으로 자동 출발 감지가 중단된 장소에는 추가 출발 확인 알림을 보내지 않는다.
5. **Given** 도착·출발 확인 알림을 받았다, **When** 알림을 누른다, **Then** 그 여행의 진행 화면이 해당 날짜로 열린다.
6. **Given** 마지막 장소 도착이 확정되어 당일 일정이 완료됐다, **When** 이후 위치 이벤트가 들어온다, **Then** 그 날짜에 대한 도착·출발 확인 알림을 더 이상 보내지 않는다.
7. **Given** 장소 변경 제안 알림을 끈 사용자다, **When** 도착·출발 확인 후보가 생성된다, **Then** 도착·출발 확인 알림은 설정과 무관하게 정상 전달된다.

### User Story 4 - 알림 목록 화면에서 지난 알림을 확인하고 이동한다 (Priority: P2)

사용자는 알림 목록 화면에서 자신이 받은 알림을 최신순으로, 날짜 구간(오늘·어제·그 이전)으로 묶어 본다. 읽지 않은 알림은 구분되어 보이고, 한 건을 누르면 읽음으로 바뀌며 그 알림이 가리키는 화면(대체 장소 화면 또는 진행 화면)으로 이동한다. "모두 읽음"으로 안 읽은 알림을 한 번에 정리할 수 있다.

**Why this priority**: 푸시를 놓쳤거나 지운 사용자도 앱 안에서 다시 확인할 수 있어야 한다. US2·US3이 만든 알림이 쌓이는 대상 화면이며, 알림이 하나라도 있으면 독립적으로 검증할 수 있다.

**Independent Test**: 알림이 여러 건 있는 사용자로 알림 목록 화면을 열어 최신순·날짜 그룹으로 표시되는지, 안 읽은 알림이 시각적으로 구분되는지, 한 건을 누르면 읽음 처리되고 대상 화면으로 이동하는지, "모두 읽음"이 안 읽은 알림을 모두 읽음으로 바꾸는지, 알림이 없을 때 빈 상태가, 불러오기 실패 시 오류 상태가 표시되는지 확인하면 된다.

**Acceptance Scenarios**:

1. **Given** 오늘 2건·어제 1건의 알림이 있다, **When** 알림 목록 화면을 연다, **Then** "오늘" 아래 2건, "어제" 아래 1건이 각각 최신순으로 표시된다.
2. **Given** 안 읽은 알림과 읽은 알림이 섞여 있다, **When** 목록을 본다, **Then** 안 읽은 알림은 색만이 아니라 표식(점·배경)으로도 구분된다.
3. **Given** 안 읽은 알림 한 건이 있다, **When** 그 알림을 누른다, **Then** 그 알림이 읽음으로 바뀌고, 유형에 따라 대체 장소 화면(감지 식별자) 또는 진행 화면(여행·날짜)으로 이동한다.
4. **Given** 안 읽은 알림이 여러 건 있다, **When** "모두 읽음"을 누른다, **Then** 그 사용자의 안 읽은 알림이 모두 읽음으로 바뀐다.
5. **Given** 받은 알림이 하나도 없다, **When** 알림 목록 화면을 연다, **Then** 빈 상태 문구가 표시되고 오류로 처리되지 않는다.
6. **Given** 알림 목록 조회가 실패했다, **When** 화면을 연다, **Then** 오류 상태와 다시 시도 행동이 표시된다.
7. **Given** 대상 여행이 논리 삭제됐거나 대상 감지가 무효화됐다, **When** 그 알림을 누른다, **Then** 이동한 화면이 "더 이상 볼 수 없는 대상"임을 안내하고 목록으로 돌아갈 수 있다.

### User Story 5 - 장소 변경 제안 알림을 끈다 (Priority: P3)

사용자는 장소 변경 제안 알림을 전체 끄거나 켤 수 있다. 꺼 두면 장소 변경 제안 알림은 기기로 전달되지 않고 알림 목록에도 새로 쌓이지 않는다. 도착·출발 확인처럼 여행 진행에 필요한 알림은 이 설정과 무관하게 계속 동작한다.

**Why this priority**: 알림 과다를 사용자가 통제할 수 있어야 한다(constitution I). 핵심 알림 전달(US2·US3)이 동작한 뒤에 얹는 통제 장치라 P3이다.

**Independent Test**: 설정을 끈 사용자에게 `ACTIVE` 감지 결과가 생겨도 장소 변경 제안 알림·알림 목록 적재가 발생하지 않는지, 같은 사용자에게 도착 확인 후보가 생기면 도착 확인 알림은 그대로 전달되는지, 설정을 다시 켜면 이후 감지부터 알림이 재개되는지 확인하면 된다.

**Acceptance Scenarios**:

1. **Given** 장소 변경 제안 알림이 켜져 있다, **When** 사용자가 설정을 끈다, **Then** 설정이 꺼짐으로 저장되고 응답으로 확인된다.
2. **Given** 장소 변경 제안 알림이 꺼져 있다, **When** 어떤 장소에 `ACTIVE` 감지 결과가 생성된다, **Then** 장소 변경 제안 알림을 보내지 않고 알림 목록에도 적재하지 않는다. 감지 결과 자체의 생성·조회는 영향받지 않는다.
3. **Given** 장소 변경 제안 알림이 꺼져 있다, **When** 도착·출발 확인 후보가 생성된다, **Then** 도착·출발 확인 알림은 정상 전달된다.
4. **Given** 장소 변경 제안 알림을 껐다가 다시 켠다, **When** 이후 새 감지 결과가 생성된다, **Then** 장소 변경 제안 알림이 다시 전달된다. 꺼져 있던 동안 건너뛴 알림은 소급 전송하지 않는다.

### User Story 6 - 감지 결과 목록을 훑어본다 (Priority: P3)

사용자는 진행 화면에서 감지 결과 목록 화면으로 들어가 당일 남은 일정 중 감지된 위험을 한 화면에서 시간순·위험순으로 훑어보고, 각 항목에서 대체 장소 화면으로 넘어간다. 진행 화면의 변수 경고 배너(F009 범위)는 가장 이른 감지 하나만 보여 주므로, 여러 건을 함께 보려면 이 목록이 필요하다.

**Why this priority**: 진입 배너 하나로는 다건 감지를 다 보여 줄 수 없다. 다만 감지 결과 조회 계약(F008 `DETECT-001`)을 그대로 소비하는 목록 화면이라 핵심 알림 전달(US1~US5)과 독립적이어서 마지막에 둔다.

**Independent Test**: `ACTIVE` 감지 결과가 여러 건 있는 진행 중 여행에서 감지 결과 목록 화면을 열어, 감지 건수·각 항목의 장소명·요약·변수별 수준·방문 예정 시각·감지 경과가 표시되는지, 시간순↔위험순 정렬이 바뀌는지, 항목의 "대체 장소 보기"가 그 감지의 대체 장소 화면으로 이동하는지, 감지가 없을 때 빈 상태가 표시되는지 확인하면 된다.

**Acceptance Scenarios**:

1. **Given** 진행 중 날짜에 `ACTIVE` 감지 결과가 3건 있다, **When** 감지 결과 목록 화면을 연다, **Then** 3건이 목록으로 표시되고 각 항목에 장소명·요약·변수별 수준·방문 예정 시각·감지 경과가 보인다.
2. **Given** 감지 결과 목록이 시간순으로 정렬돼 있다, **When** 정렬을 위험순으로 바꾼다, **Then** 종합 위험이 높은 순으로 다시 정렬된다.
3. **Given** 어떤 감지 결과의 한 변수가 데이터 없음으로 제외됐다, **When** 그 항목을 본다, **Then** 제외 사유 안내가 표시되고 없는 값을 지어내지 않는다.
4. **Given** 감지 결과 목록의 한 항목을 본다, **When** "대체 장소 보기"를 누른다, **Then** 그 감지 결과 식별자로 대체 장소 화면(F009)이 열린다.
5. **Given** 진행 중 날짜에 `ACTIVE` 감지 결과가 없다, **When** 화면을 연다, **Then** "모든 일정이 예정대로예요" 빈 상태와 진행 화면으로 돌아가는 행동이 표시된다.

### Edge Cases

- 앱이 종료된 상태에서 도착·출발 확인 알림이 왔고, 사용자가 한참 뒤 알림을 누른다: 그 사이 후보가 자동 확정됐거나 만료됐을 수 있으므로 진행 화면은 서버의 현재 상태를 다시 조회해 표시하고, 알림이 가리키던 후보가 없으면 그 사실을 안내한다.
- 같은 감지 결과·같은 확인 후보에 대해 재평가·재시도로 알림 생성이 여러 번 시도된다: 중복 방지 키로 한 대상당 한 건만 생성한다(도착 재질문 등 명세가 2회로 허용한 경우는 그 횟수까지).
- 사용자가 두 기기에서 같은 알림을 받고 한 기기에서 읽음 처리한다: 읽음 상태는 사용자 단위이므로 다른 기기에서도 읽음으로 보인다.
- 등록된 FCM 토큰이 만료·교체되어 전송이 무효 토큰으로 실패한다: 그 기기 토큰만 비우고 알림 레코드·다른 기기 전송은 유지한다. 이력은 별도로 남기지 않는다.
- 장소 변경 제안 알림이 꺼져 있는 동안 여러 감지 결과가 쌓였다가 사용자가 설정을 켠다: 지난 감지에 대한 알림을 소급 전송하지 않고 이후 새 감지부터 전송한다.
- 여행이 논리 삭제되거나 계정이 탈퇴 처리된다: 그 이후 해당 대상에 대한 알림을 생성하지 않는다. 이미 쌓인 알림의 정리 정책은 plan에서 정한다.
- 도착 확인에 "아직이에요"로 두 번째(마지막) 재질문까지 소진됐다: 이후 같은 장소의 도착 확인 알림을 보내지 않는다.
- 알림 목록에 대상이 삭제된 알림이 포함된다: 목록에서는 표시하되 누르면 이동한 화면이 "볼 수 없는 대상"임을 안내한다.
- 하나의 위치 이벤트가 이전 장소 완료와 다음 장소 도착을 동시에 일으킨다(가까운 다음 장소): 그 전환에 대한 알림은 한 건으로 보낸다.

## Requirements *(mandatory)*

### Functional Requirements

#### 알림 생성과 유형

- **FR-001**: 시스템은 아래 알림 유형을 생성·전달할 수 있어야 한다. 각 유형은 재조회에 필요한 식별자(여행, 그리고 유형에 따라 감지 결과 또는 진행 전환 또는 일정 항목)와 사람이 읽을 짧은 제목·본문을 가진다.
  - 장소 변경 제안: `ACTIVE` 감지 결과가 새로 생성됐을 때(F008 재평가 결과).
  - 도착 확인 / 출발 확인: 진행 중 자동 위치 감지가 도착·출발 확인 후보를 만들었을 때(F007).
  - 자동 도착 처리 / 자동 출발 처리: 확인 후보가 무응답으로 자동 확정됐을 때(F006/F007).
  - 도착 재질문: 도착 확인에 "아직이에요" 후 재질문 시점이 됐을 때(같은 장소 최초 포함 최대 2회).
- **FR-002**: 시스템은 한 대상(감지 결과 하나, 확인 후보 하나)에 대해 알림을 중복 생성하지 않아야 한다. 재평가·재시도·동시 요청이 있어도 중복 방지 키로 한 대상당 한 건만 만들며, 명세가 복수 알림을 허용하는 경우(도착 재질문)는 그 횟수까지만 만든다.
- **FR-003**: 시스템은 장소 변경 제안 알림을 사용자의 "장소 변경 제안 알림" 설정이 켜져 있을 때만 생성·전달해야 한다. 설정이 꺼져 있으면 알림을 만들지도 보내지도 않으며, 감지 결과 자체의 생성·갱신·조회에는 영향을 주지 않는다.
- **FR-004**: 시스템은 도착·출발 확인, 자동 처리, 도착 재질문 알림을 "장소 변경 제안 알림" 설정과 무관하게 항상 생성·전달해야 한다. 이 알림들은 여행 진행에 필요한 알림이다.
- **FR-005**: 시스템은 대상 날짜의 진행이 완료된 뒤에는 그 날짜에 대한 도착·출발 확인·자동 처리·재질문 알림을 생성하지 않아야 한다. 감지가 `DISMISSED`·`RESOLVED`·`INVALIDATED`가 된 뒤에는 그 감지에 대한 장소 변경 제안 알림을 생성하지 않아야 한다.

#### 알림 전달(FCM)

- **FR-006**: 시스템은 생성된 알림을 그 사용자의 등록된 모든 기기로 전달해야 한다. 전달 payload에는 알림 유형과 재조회 식별자, 짧은 제목·본문만 포함하고 도메인 객체 전체나 민감정보(정밀 위치, 토큰 등)를 포함하지 않아야 한다.
- **FR-007**: 시스템은 전달 대상 기기가 하나도 없어도 알림 생성을 실패로 처리하지 않아야 한다. 알림은 목록 조회로 확인할 수 있어야 한다.
- **FR-008**: 시스템은 전달 중 무효로 확인된 기기 토큰을 그 기기에서만 제거하고, 한 기기의 전달 실패가 다른 기기 전달이나 알림 생성을 실패시키지 않도록 격리해야 한다.
- **FR-009**: 시스템은 알림 전달 자체(외부 푸시 제공자 호출)의 실패를 그 알림을 유발한 도메인 처리(감지 결과 생성, 확인 후보 생성·자동 확정)와 분리해, 전달 실패가 도메인 상태 변경을 되돌리거나 막지 않도록 해야 한다.

#### 기기 토큰 등록

- **FR-010**: 사용자는 로그인한 기기의 푸시 토큰을 등록·갱신할 수 있어야 한다. 등록은 기기 단위이며 같은 기기의 재등록은 기존 등록을 대체하고 중복을 만들지 않아야 한다(멱등).
- **FR-011**: 시스템은 로그아웃 시 그 기기의 푸시 토큰을 제거해야 한다. 이후 그 기기는 알림 전달 대상에서 빠진다. 다른 기기의 등록은 유지된다.
- **FR-012**: 시스템은 기기 토큰 등록·해제 요청에서 사용자와 기기 소유권을 검증하고, 다른 사용자의 기기에 대한 요청을 거절해야 한다.

#### 알림 목록과 읽음

- **FR-013**: 사용자는 자신이 받은 알림을 최신순으로, cursor 페이지네이션으로 조회할 수 있어야 한다. 각 알림은 유형, 재조회 식별자, 제목·본문, 읽음 여부, 생성 시각을 가진다.
- **FR-014**: 사용자는 알림 한 건을 읽음으로 처리할 수 있어야 하고, 안 읽은 알림을 모두 읽음으로 처리할 수 있어야 한다. 읽음 상태는 사용자 단위이며 기기 간에 공유된다.
- **FR-015**: 시스템은 알림 조회·읽음 처리 요청에서 사용자 소유권을 검증하고, 다른 사용자의 알림에 대한 요청을 거절해야 한다.
- **FR-016**: 알림이 가리키는 대상(여행·감지·전환·항목)이 삭제·무효화되어도 알림 목록 조회는 실패하지 않아야 한다. 그 알림을 열면 대상을 볼 수 없다는 안내를 제공한다.

#### 화면과 이동

- **FR-017**: 앱은 알림 목록 화면에서 알림을 날짜 구간(오늘·어제·그 이전)으로 묶어 최신순으로 보여 주고, 안 읽은 알림을 색이 아닌 표식으로도 구분하며, "모두 읽음" 행동을 제공해야 한다. 화면 상태는 `loading`·`empty`·`error`·`content`를 가진다.
- **FR-018**: 사용자가 알림을 누르면 앱은 그 알림을 읽음으로 처리하고 유형에 맞는 화면으로 이동해야 한다. 장소 변경 제안은 그 감지 결과의 대체 장소 화면(F009), 도착·출발·자동 처리·재질문은 그 여행의 진행 화면(해당 날짜)으로 이동한다.
- **FR-019**: 앱은 푸시 알림을 눌러 앱에 진입한 경우에도 FR-018과 같은 대상으로 이동해야 한다. 이동 전 서버의 현재 상태를 다시 조회해, 알림 시점과 진입 시점 사이에 대상이 바뀌었으면 현재 상태를 표시한다.
- **FR-020**: 앱은 로그인 성공과 토큰 재발급 후 이 기기의 푸시 토큰을 등록해야 하고, 로그아웃 시 해제를 요청해야 한다. 푸시 권한이 없거나 토큰을 얻지 못해도 앱의 다른 기능은 계속 동작해야 한다.

#### 설정

- **FR-021**: 시스템은 장소 변경 제안 알림 생성·전달 전에 그 사용자의 "장소 변경 제안 알림" 설정 값(기본 켜짐)을 확인하고, 꺼져 있으면 생성·전달하지 않아야 한다. F011은 이 설정을 발송 시 읽어 존중할 뿐이며, 설정을 조회·변경하는 계약(`PREF-001`·`PREF-002`)과 설정 화면 UI는 F012(사용자 설정) 범위다(Clarifications 2026-09-10).
- **FR-022**: 설정 변경은 이후 생성되는 알림부터 적용되며, 꺼져 있던 동안 건너뛴 장소 변경 제안 알림을 소급 전송하지 않아야 한다.

#### 소유권·기록·범위

- **FR-023**: 시스템은 알림 생성·전달·조회·읽음·기기 등록 전 과정에서 인증된 사용자와 대상 여행의 소유권을 검증해야 한다(constitution V).
- **FR-024**: 시스템은 알림 생성과 전달에 대해 요청 식별자, 알림 유형, 대상 식별자, 전달 대상 기기 수, 전달 결과 요약을 추적 가능하게 기록하되, 토큰 원문·정밀 위치·본문의 개인정보는 기록하지 않아야 한다(constitution V, 관찰 가능성).
- **FR-025**: F011은 알림 생성 규칙, FCM 전달, 기기 토큰 등록·해제, 알림 목록·읽음, 알림에서의 화면 이동, "장소 변경 제안 알림" 설정의 발송 시 존중, 그리고 감지 결과 목록 화면(Figma `VariableMonitorScreen`)까지 책임진다. 감지 결과의 생성·갱신·종료·변수 판정과 `DETECT-001`~`DETECT-003` 계약(F008), 확인 후보 생성·자동 확정·되돌리기(F006/F007), 대체 후보 생성·조회·직접 검색·감지 거절과 대체 장소 화면·진행 화면의 변수 경고 배너 진입점(F009), 변경 경로 미리보기·일정 변경·되돌리기(F010), 설정 화면 UI와 `PREF-001`·`PREF-002` 계약(F012)은 F011 범위가 아니다.
- **FR-026**: F011은 F006·F007·F008이 정의한 도메인 이벤트(확인 후보 생성, 자동 확정, 감지 결과 생성)에 알림 생성을 연결하며, 그 도메인 규칙 자체를 새로 정의하거나 바꾸지 않는다. 연결에 필요한 훅·계약이 없으면 해당 Feature 문서와 같은 변경 범위에서 추가한다.

### UI Requirements *(include if feature contains user-facing UI)*

화면 모양의 정본은 Figma Make `NotificationsScreen`(알림 목록)과 `VariableMonitorScreen`(`hasAlerts` 있음·없음, 감지 결과 목록)이다. 아래는 사용자가 할 수 있어야 하는 일과 상태·접근성·검증 기준만 적는다. 배치·색·간격·아이콘은 Figma와 `com.gilpick.ui.theme` 토큰을 따른다.

- **UI-001**: 사용자는 알림 목록 화면에서 받은 알림을 최신순으로, "오늘"·"어제"·그 이전 날짜 구간 라벨로 묶어 보고, 각 알림의 제목·본문·상대 시각·읽음 여부를 확인할 수 있어야 한다.
- **UI-002**: 안 읽은 알림은 `surfaceTint` 배경과 점 표식 등 색 단독이 아닌 수단으로 구분되어야 한다(ui-guidelines 3·10절). 헤더의 "모두 읽음" 아이콘 버튼에는 설명 문구를 둔다.
- **UI-003**: 사용자는 알림 한 건을 눌러 읽음 처리와 함께 대상 화면(대체 장소 화면 또는 진행 화면)으로 이동할 수 있어야 한다. 대상을 볼 수 없으면 그 사실을 문구로 안내한다.
- **UI-004**: 화면 상태는 ui-guidelines 9절을 따른다. `loading`은 1초를 넘길 때만 대기 표시, `empty`는 받은 알림이 없을 때 Figma 빈 상태 형식(아이콘 상자·제목·설명), `error`는 목록 조회 실패 시 `다시 시도하기`와 돌아가기, `content`는 알림 목록이다. 새로고침 중 기존 목록 유지 여부는 plan에서 정한다.
- **UI-005**: 도착·출발 확인 등 진행 알림 문구는 상태와 다음 행동이 드러나는 `~해요` 문장으로 쓰고(ui-guidelines 8절), 장소 변경 제안 문구는 기술 용어가 아니라 방문 판단으로 쓴다(예: "다음 장소 변경을 추천해요").
- **UI-006**: ui-guidelines 10절 접근성 최저선을 지킨다. 알림 행·아이콘 전용 버튼의 터치 영역 48dp 이상·간격 8dp 이상, 아이콘 전용 버튼의 설명 문구, 단독 의미 전달 글자 12sp 이상, 화면 너비 360dp와 시스템 글자 최대 배율에서 가로 스크롤·잘림 없음.
- **UI-007**: 검증은 Compose screenshot(360dp 기본 배율·360dp 최대 배율)으로 알림 목록의 `content`(안 읽음·읽음 혼재)·`empty`·`error` 상태를 남기고, 실제 서버·FCM 연동 검증은 감지 결과 생성→기기 푸시 수신→알림 탭→대체 장소 화면, 도착 후보 생성→푸시 수신→진행 화면까지 확인한다. 실기기 FCM 검증은 G001 환경에 의존한다.
- **UI-008**: 사용자는 감지 결과 목록 화면에서 `ACTIVE` 감지 결과를 시간순·위험순으로 훑어보고 각 항목에서 그 감지의 대체 장소 화면으로 이동할 수 있어야 하며, 변수 데이터가 제외된 항목은 사유를 문구로 안내하고 없는 값을 지어내지 않는다. 화면 상태는 `content`와 `empty`(Figma `VariableMonitorScreen`의 `hasAlerts=false` 형식)를 가진다. 이 화면은 F008 `DETECT-001`(status 필터) 조회 계약만 소비하고 감지 판정을 새로 하지 않는다.

### Key Entities *(include if feature involves data)*

- **알림(notification)**: 한 사용자에게 발생한 알림 한 건. 사용자, 유형, 재조회 식별자(여행, 선택적으로 여행 날짜·일정 항목·감지 결과·진행 전환), 제목, 본문, 중복 방지 키, FCM 발송 시각, 읽음 시각, 생성 시각을 가진다. `docs/design/er-schema.md` 9.1 `notifications` 스키마를 그대로 사용한다.
- **기기 세션의 푸시 토큰**: 기기 세션(`device_sessions`) 한 행에 딸린 현재 FCM 토큰과 플랫폼. 활성 세션의 토큰은 유일하며, 로그아웃·무효 확인 시 비운다. 별도 기기 테이블을 새로 만들지 않는다.
- **장소 변경 제안 알림 설정**: 사용자당 하나의 boolean(`users.replacement_suggestion_enabled`, 기본 true). 별도 설정 테이블을 만들지 않는다.
- **감지 결과(F008 재사용)**: 장소 변경 제안 알림의 생성 계기이자 이동 대상. F011은 `ACTIVE` 생성 이벤트를 소비하고 상태를 바꾸지 않는다.
- **진행 전환(F006/F007 재사용)**: 도착·출발 확인·자동 처리·재질문 알림의 생성 계기이자 이동 대상. F011은 후보 생성·자동 확정 이벤트를 소비하고 상태를 바꾸지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `ACTIVE` 감지 결과가 새로 생성되고 설정이 켜진 사용자에 대해, 장소 변경 제안 알림이 등록된 기기로 전달되고 알림 목록에 1건 적재되는 비율이 100%다.
- **SC-002**: 한 감지 결과·한 확인 후보에 대해 생성되는 알림이 규정 횟수(기본 1건, 도착 재질문은 최대 2건)를 초과하는 사례가 0건이다.
- **SC-003**: 장소 변경 제안 알림을 끈 사용자에게 장소 변경 제안 알림이 전달되거나 알림 목록에 적재되는 사례가 0건이며, 같은 사용자의 도착·출발 확인 알림이 설정 때문에 누락되는 사례도 0건이다.
- **SC-004**: 알림 payload에 도메인 객체 전체나 정밀 위치·토큰 같은 민감정보가 포함되는 사례가 0건이다(재조회 식별자와 짧은 문구만 포함).
- **SC-005**: 한 기기의 FCM 전달 실패나 무효 토큰이 알림 생성·다른 기기 전달·도메인 상태 변경을 실패시키는 사례가 0건이다.
- **SC-006**: 로그아웃한 기기로 이후 알림이 전달되는 사례가 0건이다.
- **SC-007**: 다른 사용자의 알림 조회·읽음·기기 토큰 해제 요청의 100%가 거절된다.
- **SC-008**: 대상이 삭제·무효화된 알림을 포함해 알림 목록 조회가 실패하는 사례가 0건이다.
- **SC-009**: 사용자는 푸시 알림을 눌러 3번 이하의 탭으로 대상 화면(대체 장소 화면 또는 진행 화면)에 도달한다.
- **SC-010**: 알림 목록 화면의 `content`·`empty`·`error` 상태가 360dp·최대 글자 배율에서 잘림 없이 표시된다.
- **SC-011**: 당일 진행이 완료된 뒤 그 날짜에 대한 도착·출발 확인 알림이 생성되는 사례가 0건이다.

## Assumptions

- 알림·기기·설정 API의 경로와 응답 형태는 `docs/design/api-spec.md` 9절(NOTI-001·NOTI-002·DEV-001·DEV-002·PREF-001·PREF-002)을 기준으로 하고, `notifications`·`device_sessions`·`users.replacement_suggestion_enabled` 스키마는 `docs/design/er-schema.md` 4.1·4.2·9.1을 그대로 사용한다. 이 명세는 값을 다시 정하지 않는다.
- 알림 유형 문자열(예: `PLACE_CHANGE_SUGGESTION`, 도착·출발 유형)과 중복 방지 키 구성은 현재 api-spec 예시에 `PLACE_CHANGE_SUGGESTION`만 있고 `notifications.type`은 enum이 정의돼 있지 않으므로, 나머지 유형 값과 `dedup_key` 규칙은 plan 단계에서 확정하고 같은 변경 범위에서 api-spec·er-schema를 동기화한다.
- `NOTI-001` 응답 예시에는 `tripId`·`detectionId`만 나오지만 `notifications` 스키마와 이동 요구(FR-018)에는 `itemId`·`transitionId`·`tripDayId`와 유형 enum이 필요하므로, 응답 필드 확장은 plan 단계에서 확정하고 api-spec을 동기화한다.
- Figma `NotificationsScreen` 헤더의 "모두 읽음"에 대응하는 계약이 현재 `NOTI-002`(단건 읽음)뿐이므로, 일괄 읽음 처리 방식(전용 엔드포인트 또는 파라미터)은 plan 단계에서 확정하고 api-spec을 동기화한다.
- 설정 필드명은 스키마(`users.replacement_suggestion_enabled`)와 API(`placeChangeSuggestionNotificationEnabled`)가 다르다. F011은 둘을 같은 값으로 취급하며, 표기 통일이 필요하면 plan 단계에서 api-spec·er-schema 중 한쪽을 맞춘다.
- `device_sessions` 행은 로그인(AUTH-003) 때 생성된다. `DEV-001`이 세션 행보다 먼저 호출되는 경우, 다기기 토큰 이관, 무효 토큰 확인 주체·시점(`fcm_token`을 null로 되돌리는 흐름)은 계약에 비어 있으므로 plan 단계에서 F001 구현과 대조해 확정한다.
- 도착·출발 확인·자동 확정·재질문의 발생 시점 정의(300m·5분 DWELL, 5분 무응답 자동 확정, 10분 뒤 재질문·최대 2회, 400m EXIT, 마지막 장소 완료 시 종료)는 `docs/planning/requirements.md` PROG-04~PROG-11·LOC-01과 `docs/design/api-spec.md` 6절이 확정한 값을 그대로 따른다. F011은 이 이벤트에 알림을 붙일 뿐 시점을 재정의하지 않는다.
- 확인 후보·자동 확정은 서버가 `progress_transitions`로 관리하며(PROG-003·PROG-004·PROG-001의 `pendingCandidate`·`undoable`), F011이 알림을 생성하려면 "후보 생성"과 "자동 확정" 시점에 호출되는 서버 내부 훅이 필요하다. 이 훅의 유무·형태는 plan 단계에서 F006/F007 구현과 대조해 확정한다. 훅이 없으면 F006/F007 계약에 추가를 요청한다.
- `ACTIVE` 감지 결과 생성 시 알림을 만드는 연결점은 F008 재평가 파이프라인의 감지 결과 생성 지점이다(`api-spec.md` 7.1 "장소 변경 제안 알림은 F011에서 처리한다"). 재평가는 서버 주기 작업이므로 F011의 알림 생성도 같은 서버 처리 안에서 일어난다.
- FCM 실제 전송은 Firebase 프로젝트와 서버 credential에 의존하며, 실기기 전달 검증은 G001 공유 dev/staging 환경(`Firebase·FCM`, `mvp-features.md` G001) 준비 후 수행한다. 그 전에는 전송 계층을 추상화해 mock·계약 테스트로 검증한다.
- 알림 목록 화면의 진입점은 Figma 기준 `MyTripsScreen`과 `ActiveTravelScreen`의 알림 버튼이다(`docs/design/figma-make/src/App.tsx`). F011은 이 두 진입점에서 알림 목록 화면을 열 수 있게 한다.
- 푸시 알림 탭 → 앱 특정 화면 이동(deep link 성격)은 재조회 식별자만으로 대상 화면을 열 수 있어야 한다는 요구로 표현하며, 구체 구현 방식은 plan에서 정한다.
- "장소 변경 제안 알림" 설정은 `users` 단일 컬럼(`replacement_suggestion_enabled`)이다. F012가 소유하는 설정 화면·`PREF-001`·`PREF-002`와 F011의 발송 시 존중은 이 같은 boolean을 공유한다(Clarifications 2026-09-10).
- 도착·출발 확인 알림과 진행 화면 인앱 확인(bottom sheet/배너)은 별개다. 인앱 확인 표현은 F006/F007 또는 별도 Frontend Issue 범위이며, F011은 "앱 밖에서도 알린다"만 책임진다.
- 알림 정리·보존 기간(오래된 알림 삭제, 여행 삭제 시 연결 알림 처리)은 `er-schema.md`에 명시가 없으므로 plan 또는 보안 문서에서 정의한다(constitution V).

## Dependencies

- **F008 여행 변수 감지**(DONE): `ACTIVE` 감지 결과 생성 이벤트와 `DETECT-001`(status 필터) 감지 목록 조회 계약. F011은 감지 생성 시 장소 변경 제안 알림을 만들고, 감지 결과 목록 화면(US6)이 `DETECT-001`을 소비한다.
- **F007 위치 기반 감지**(DONE): 도착·출발 확인 후보 생성 이벤트. F011은 이 시점에 확인 알림을 만든다.
- **F006 여행 진행**(DONE): 확인 후보 자동 확정, 도착 재질문 예약, 당일 완료 시 감지·알림 종료. F011은 이 이벤트에 알림을 연결한다.
- **F001 인증**(DONE): `device_sessions` 기기 세션. F011은 이 행에 FCM 토큰을 붙이고 로그인·로그아웃 흐름에 등록·해제를 건다.
- **F009 대체 장소 추천**(DONE): 알림 탭 시 이동 대상인 대체 장소 화면과 감지 식별자 하나로 여는 진입 계약.
- **F012 사용자 설정**(미착수): "장소 변경 제안 알림" 설정 화면 UI와 `PREF-001`·`PREF-002` 계약을 소유한다. F011은 이 설정 boolean(`users.replacement_suggestion_enabled`)을 발송 시 읽기만 한다(Clarifications 2026-09-10). F012는 F011 없이도 설정 화면을 완결할 수 있어야 한다.
- **G001 외부 연동 검증 Gate**: Firebase 프로젝트·FCM credential과 공유 dev/staging 환경. 실기기 전달 검증 task만 이 Gate에 의존한다.

## Out of Scope
