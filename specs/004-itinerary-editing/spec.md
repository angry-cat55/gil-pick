## Clarifications

### Session 2026-09-05

- Q: F005 경로 계산 이전에 일정 저장·조회 응답의 경로 상태를 어떻게 표현하는가? → A: 경로 상태 값에 `NOT_CALCULATED`를 추가하고 경로 정보는 비워 둔다. 화면은 이 상태에서 도착 시각·구간 소요 시간을 표시하지 않는다. F005가 오면 `READY`·`FAILED`로 확장한다.
- Q: 이동 수단 변경 시트에서 체류 시간도 함께 조절하는가? → A: 조절하지 않는다. 체류 시간은 체류 시간 대화상자에서만 30분 단위로 바꾸고, Figma 시트의 5분 단위 조절 요소는 제거한다.
- Q: 장소 순서는 어떤 조작으로 바꾸는가? → A: 행의 손잡이 끌기와 행별 위·아래 이동 버튼을 함께 제공한다. Figma에 두 조작을 추가해 정본으로 삼는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 날짜별 일정에 장소 추가 (Priority: P1)

인증된 사용자가 자신의 여행에서 날짜를 고르고, F003 장소 검색·상세에서 찾은 장소를 그 날짜의 일정에 추가한다. 장소를 추가하면 내부 카테고리의 추천 체류 시간이 자동으로 채워지고, 사용자는 추가한 장소 목록을 저장한다.

**Why this priority**: 일정에 장소가 있어야 순서·체류 시간·이동 수단 편집(US2)과 이후 경로 계산(F005)·여행 진행(F006)이 성립한다. F003이 만든 `일정에 추가` 요청을 실제로 받아 저장하는 첫 번째 지점이다.

**Independent Test**: 여행 하나와 날짜 하나를 준비해 장소 검색에서 장소를 고르고 `일정에 추가`를 확정한 뒤 저장하면, 그 날짜의 일정을 다시 조회했을 때 같은 장소가 추천 체류 시간과 함께 남아 있는지로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 인증된 사용자가 자신의 여행 상세에 있다, **When** `일정 편집`을 선택한다, **Then** 여행 기간의 날짜 탭과 선택한 날짜의 방문 장소 목록이 표시되고, 장소가 없으면 빈 상태와 `장소 추가` 행동이 표시된다.
2. **Given** 사용자가 일정 편집 화면에서 날짜를 선택했다, **When** `장소 추가`를 선택한다, **Then** F003 장소 검색 화면으로 이동하고, 검색 결과 행의 `+` 또는 상세의 `일정에 추가` 시트에서 이동 수단·체류 시간을 확정하면 선택한 날짜의 일정 끝에 그 장소가 추가된 상태로 편집 화면에 돌아온다.
3. **Given** 사용자가 장소를 추가했다, **When** 시트에서 체류 시간을 바꾸지 않았다, **Then** 추가된 장소의 체류 시간은 F003이 제공한 카테고리 추천 체류 시간(자연 120분, 문화·역사 90분, 음식 60분, 카페 60분, 쇼핑 90분, 기타 60분)이다.
4. **Given** 사용자가 장소를 추가하거나 편집했다, **When** `저장`을 선택한다, **Then** 선택한 날짜의 일정이 저장되고 여행 상세의 날짜별 일정 목록에 반영된다.
5. **Given** 사용자가 저장하지 않은 변경이 있다, **When** 편집 화면을 닫으려 한다, **Then** 저장하지 않은 변경이 사라진다는 확인이 표시되고, `계속 편집`을 고르면 편집 상태가 유지되며 `취소하고 나가기`를 고르면 변경을 버리고 여행 상세로 돌아간다.
6. **Given** 사용자가 F003 시트에서 `취소`를 선택하거나 시트 밖을 눌렀다, **When** 편집 화면으로 돌아온다, **Then** 일정에는 아무것도 추가되지 않는다.
7. **Given** 다른 사용자의 여행이다, **When** 그 여행의 일정을 조회하거나 저장하려 한다, **Then** 요청은 거부되고 일정은 변경되지 않는다.

### User Story 2 - 순서·체류 시간·이동 수단 편집 (Priority: P2)

사용자가 한 날짜의 장소 순서를 바꾸고, 장소별 체류 시간을 30분 단위로 조절하며, 다음 장소까지의 이동 수단(도보·대중교통·자동차)을 정하거나 장소를 일정에서 뺀다.

**Why this priority**: 저장된 순서와 체류 시간·이동 수단이 F005 경로 계산과 F006 ETA 계산의 입력이 된다. 장소 추가만으로는 실제로 쓸 수 있는 일정이 되지 않는다.

**Independent Test**: 장소가 두 개 이상 있는 날짜에서 순서를 바꾸고, 한 장소의 체류 시간을 조절하고, 구간 이동 수단을 바꾼 뒤 저장하고 다시 조회해 세 값이 모두 유지되는지로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 한 날짜에 장소가 두 개 이상 있다, **When** 사용자가 장소의 순서를 바꾸고 저장한다, **Then** 다시 조회한 일정은 바꾼 순서를 그대로 보여 준다.
2. **Given** 사용자가 장소의 체류 시간 조절을 연다, **When** `−`·`+`로 30분씩 조절하거나 60·90·120분 빠른 선택을 누르고 `적용`한다, **Then** 체류 시간은 30분 단위로 30~360분 안에서만 바뀌고 범위를 벗어나는 조절은 적용되지 않는다.
3. **Given** 마지막이 아닌 장소가 있다, **When** 사용자가 `변경`으로 이동 수단 시트를 열어 도보·대중교통·자동차 중 하나를 고르고 `적용`한다, **Then** 그 장소에서 다음 장소로 가는 구간의 이동 수단이 바뀐다.
4. **Given** 사용자가 장소를 마지막 순서로 옮기거나 마지막 장소 뒤의 장소를 삭제했다, **When** 저장한다, **Then** 마지막 장소에는 다음 구간 이동 수단이 없다.
5. **Given** 사용자가 장소 행의 삭제 버튼을 누른다, **When** 저장한다, **Then** 그 장소는 일정에서 빠지고 남은 장소의 순서가 빈틈 없이 다시 매겨진다.
6. **Given** 같은 날짜를 다른 곳에서 먼저 저장했다, **When** 사용자가 이전 버전을 기준으로 저장한다, **Then** 저장은 거부되고 최신 일정을 다시 불러온 뒤 편집하도록 안내된다.
7. **Given** 체류 시간을 사용자가 조절한 장소가 있다, **When** 나중에 같은 카테고리의 추천값이 바뀐다, **Then** 사용자가 조절한 값은 유지된다.

### User Story 3 - 여행 상세에서 날짜별 일정 확인 (Priority: P3)

사용자가 여행 상세에서 여행의 모든 날짜와 각 날짜의 방문 장소, 체류 시간, 구간 이동 수단을 한눈에 확인하고, 일정이 없는 날짜를 알아본다.

**Why this priority**: 편집 없이도 계획을 훑어보는 기본 조회 흐름이며, F006 여행 진행 화면과 F005 경로 확인의 출발점이다. US1·US2가 없으면 보여 줄 내용이 없어 뒤에 둔다.

**Independent Test**: 일정이 저장된 여행과 저장되지 않은 여행의 상세를 열어 날짜별 목록과 빈 날짜 안내가 맞게 나오는지로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 일정이 저장된 여행이다, **When** 사용자가 여행 상세를 연다, **Then** 날짜별로 방문 순서, 장소명, 체류 시간과 구간 이동 수단이 표시되고 각 날짜의 장소 수가 요약된다.
2. **Given** 일부 날짜에만 일정이 있다, **When** 여행 상세를 연다, **Then** 일정이 없는 날짜는 비어 있음이 구분되어 표시되고 `일정 편집`으로 채울 수 있다.
3. **Given** 여행 상세의 일정 목록에서 장소를 선택한다, **When** 화면이 전환된다, **Then** F003 장소 상세가 열리고 뒤로 가면 여행 상세로 돌아온다.
4. **Given** 일정 조회가 실패한다, **When** 여행 상세를 연다, **Then** 여행 기본 정보는 유지되고 일정 영역만 원인과 `다시 시도`를 안내한다.

### User Story 4 - 여행 기간 축소 시 일정 정리 (Priority: P4)

사용자가 F002 여행 수정에서 기간을 줄일 때, 새 기간 밖으로 밀려나는 날짜의 일정 수를 먼저 안내받고, 확인한 경우에만 그 일정이 삭제된다.

**Why this priority**: F002 FR-012는 삭제될 일정 수 안내와 확인 후 삭제를 요구하지만, 일정이 존재하지 않아 F002에서는 항상 0건으로 처리됐다. 일정이 실제로 생기는 F004에서 이 규칙이 비로소 동작해야 한다.

**Independent Test**: 3일 여행의 3일차에 장소를 저장한 뒤 기간을 2일로 줄이는 요청을 보내면 삭제 대상 1건이 안내되고, 확인 없이 보낸 요청은 거부되며 확인한 요청만 3일차 일정을 지우는지로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 새 기간 밖 날짜에 저장된 장소가 있다, **When** 확인 없이 기간을 줄인다, **Then** 저장은 거부되고 삭제될 장소 수가 안내된다.
2. **Given** 사용자가 삭제에 확인했다, **When** 기간을 줄인다, **Then** 기간 밖 날짜의 일정만 삭제되고 나머지 날짜의 일정은 유지된다.
3. **Given** 새 기간 밖 날짜에 저장된 장소가 없다, **When** 기간을 줄인다, **Then** 삭제 확인 없이 저장된다.

### Edge Cases

- 여행 기간 밖의 날짜로 일정을 조회·저장하려 하면 거부하고 여행 기간 안의 날짜만 허용한다.
- 저장 요청의 순서에 빈틈이나 중복이 있거나, 체류 시간이 30분 단위가 아니거나 30~360분을 벗어나거나, 마지막 장소에 이동 수단이 있거나 마지막이 아닌 장소에 이동 수단이 없으면 저장을 거부하고 어떤 값이 잘못됐는지 안내한다.
- 한 날짜의 모든 장소를 삭제하고 저장하면 그 날짜는 일정이 없는 상태가 되며, 여행 상세에서 빈 날짜로 표시된다.
- 같은 장소를 같은 날짜에 두 번 이상 추가할 수 있다. 각 항목은 별개의 방문으로 순서와 체류 시간을 따로 가진다.
- F003에서 받은 장소 참조가 더 이상 조회되지 않아도(제공자에서 사라짐) 이미 저장된 일정 항목은 유지되고 저장된 장소명·주소로 표시된다.
- 저장 도중 연결이 끊기면 입력한 내용은 화면에 유지되고 사용자가 같은 요청을 다시 보낼 수 있으며, 같은 요청이 두 번 도착해도 항목이 중복 생성되지 않는다.
- 장소가 많거나 장소명이 길어도 순서 번호, 장소명, 체류 시간, 삭제·변경 행동이 가려지지 않는다.
- 인증이 만료되면 F001의 재인증 흐름으로 유도하고, 저장하지 않은 편집 내용은 재인증 뒤 다시 입력해야 함을 안내한다.
- 이미 시작된 날짜(F006에서 진행 중이거나 완료된 날짜)의 처리된 장소는 장소와 이동 수단을 바꿀 수 없고 체류 시간·순서만 바꿀 수 있다. 처리된 장소를 삭제하려는 요청은 거부한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 인증된 사용자가 자신이 소유한 여행의 기간 안 날짜별 일정을 조회하도록 허용해야 하며, 다른 사용자의 여행이나 삭제된 여행, 기간 밖 날짜의 일정 조회·저장은 거부해야 한다.
- **FR-002**: 시스템은 F003 `일정에 추가` 시트에서 확정한 장소 참조, 이동 수단, 체류 시간을 받아 사용자가 선택한 날짜의 일정 끝에 새 항목으로 추가해야 한다. 추가는 사용자가 `저장`하기 전까지 화면의 편집 상태로만 존재한다.
- **FR-003**: 시스템은 새 항목의 체류 시간을 F003이 제공한 카테고리 추천 체류 시간으로 자동 입력하고, 사용자가 시트나 편집 화면에서 값을 바꾸면 사용자 조절값으로 구분해 저장해야 한다.
- **FR-004**: 시스템은 체류 시간을 30분 단위로 30~360분 안에서만 허용해야 하며, 범위나 단위를 벗어난 값은 저장을 거부해야 한다.
- **FR-005**: 시스템은 한 날짜 안에서 장소의 방문 순서를 바꾸도록 허용하고, 저장된 순서는 1부터 빈틈 없이 이어지며 중복되지 않아야 한다.
- **FR-006**: 시스템은 마지막이 아닌 장소마다 다음 장소까지의 이동 수단을 도보·대중교통·자동차 중 하나로 저장해야 하며, 마지막 장소에는 이동 수단이 없어야 한다. 새로 추가한 장소는 F003 시트에서 고른 이동 수단을 직전 장소의 다음 구간 이동 수단으로 사용하고, 첫 장소로 추가되면 그 값은 무시한다.
- **FR-007**: 시스템은 사용자가 장소를 일정에서 삭제하도록 허용하고, 삭제 후 남은 장소의 순서를 다시 매겨야 한다.
- **FR-008**: 시스템은 한 날짜의 일정을 한 번의 저장 요청으로 통째로 저장해야 하며, 저장 요청에는 조회 시점의 일정 버전이 포함되어야 한다. 버전이 최신과 다르면 저장을 거부하고 사용자가 최신 일정을 다시 불러오도록 안내해야 한다.
- **FR-009**: 시스템은 같은 저장 요청이 반복 도착해도 항목이 중복 생성되거나 버전이 두 번 오르지 않도록 멱등하게 처리해야 한다.
- **FR-010**: 시스템은 저장이 성공하면 버전이 1 증가한 최신 일정을 돌려주고, 여행 상세와 편집 화면이 그 값으로 갱신되어야 한다.
- **FR-011**: 시스템은 일정에 처음 참조되는 장소의 최소 참조정보(제공자 장소 식별자, 장소명, 내부 카테고리, 원본 관광 분류, 주소, 위치, 대표 이미지, 확정 매칭된 경우의 Google 장소 식별자)를 저장하고, 같은 제공자 장소를 다시 참조하면 새로 만들지 않고 기존 참조를 재사용해야 한다. 평점·리뷰 수·영업시간·외부 API 원문은 저장하지 않는다.
- **FR-012**: 시스템은 여행의 각 날짜에 대한 일정 단위(날짜, 일차, 일정 버전)를 일정이 처음 저장될 때 만들어야 하며, 여행 기간 안의 모든 날짜를 미리 만들 필요는 없다.
- **FR-013**: 시스템은 F002 여행 기간 축소 요청에 대해 새 기간 밖 날짜에 저장된 장소 수를 계산해 안내하고, 사용자가 확인한 요청에서만 그 날짜의 일정 단위와 항목을 삭제해야 한다. 기간 밖 일정이 없으면 확인 없이 진행한다.
- **FR-014**: 시스템은 여행 상세에서 여행의 모든 날짜와 각 날짜의 장소 수, 방문 순서, 장소명, 체류 시간, 구간 이동 수단을 표시해야 하며, 일정이 없는 날짜를 구분해 표시해야 한다.
- **FR-015**: 시스템은 여행 상세와 편집 화면에서 F003 장소 검색으로 들어가는 진입점을 제공해야 하며, 검색·상세에서 확정한 `일정에 추가` 결과가 사용자가 편집 중이던 날짜로 돌아오도록 해야 한다. F003 T035에서 F004로 이관한 진입점 연결이 여기에 해당한다.
- **FR-016**: 시스템은 저장하지 않은 편집 내용이 있을 때 화면을 떠나려 하면 확인을 요구하고, 사용자가 명시적으로 버리기를 선택한 경우에만 변경을 버려야 한다.
- **FR-017**: 시스템은 이미 처리된(도착·완료·건너뜀) 장소에 대해 장소 교체와 이동 수단 변경, 삭제를 거부하고 체류 시간과 순서 변경만 허용해야 한다. 처리된 장소의 상태는 F004 편집으로 바뀌지 않는다. 상태를 바꾸는 흐름은 F006 범위다.
- **FR-018**: F004는 일정 저장까지만 책임진다. 저장·조회 응답의 경로 상태는 F005 이전에 `NOT_CALCULATED`이고 경로 정보는 비어 있으며, 구간별 소요 시간·거리와 도착 예정 시각은 F005·F006이 채운다. F004 화면은 경로 상태가 `NOT_CALCULATED`이면 도착 시각과 구간 소요 시간을 표시하지 않고 지어내지 않아야 한다.
- **FR-019**: 시스템은 일정 조회·저장 실패를 정상적인 빈 일정과 구분해 안내하고, 저장 실패 시 화면의 편집 내용을 유지해 사용자가 다시 시도할 수 있게 해야 한다.
- **FR-020**: 시스템은 일정 저장·삭제와 버전 변경을 여행 소유자 검증을 거친 요청에서만 수행해야 하며, 저장 요청 처리 시각과 버전 전후 값을 추적 가능하게 남겨야 한다.

### UI Requirements *(include if feature contains user-facing UI)*

- **UI-001**: 일정 편집 화면은 닫기 버튼과 `일정 편집` 제목, 여행 기간의 날짜 탭(날짜 숫자와 요일, 선택 탭 강조), `{월} {일}일 방문 장소` 제목과 `{N}일차 · {M}곳` 요약, 방문 장소 카드 목록, 점선 테두리의 `장소 추가` 버튼, 하단 고정 `저장` 주버튼으로 구성한다.
- **UI-002**: 방문 장소 행은 순서 번호 원, 장소명, 체류 시간, 다음 구간 이동 수단과 `변경` 행동, 삭제 버튼을 표시한다. 처리된 장소는 순서 번호 대신 상태(완료 체크, 건너뜀)를 색과 아이콘·문구를 함께 써서 구분한다.
- **UI-003**: 체류 시간 조절은 `{장소명} 체류 시간` 제목, `−`·`+` 원형 버튼과 현재 분 표시, 60·90·120분 빠른 선택, `취소`·`적용` 버튼을 가진 대화상자로 제공한다. 30분 미만·360분 초과로는 조절되지 않는다.
- **UI-004**: 이동 수단 변경은 `이동 수단 변경` 제목과 `{장소명}까지 어떻게 이동하시겠어요?` 안내, 도보·대중교통·자동차 카드(선택 카드 강조와 체크 아이콘), `취소`·`적용` 버튼을 가진 bottom sheet로 제공한다. 체류 시간은 이 시트에서 조절하지 않고 UI-003 대화상자에서만 바꾼다. Figma의 시트 안 5분 단위 체류 시간 조절 요소는 30분 단위 규칙(FR-004)과 충돌해 제거하며, Figma를 같은 방향으로 고친다.
- **UI-005**: 편집 화면을 닫을 때 저장하지 않은 변경이 있으면 `편집을 취소할까요?` 제목, `저장하지 않은 변경 사항은 사라집니다` 설명, `계속 편집` 주버튼과 `취소하고 나가기` 보조 행동을 가진 대화상자를 표시한다. 변경이 없으면 바로 닫는다.
- **UI-006**: 여행 상세는 F002 화면 구조를 유지하면서 `일정 편집` 진입 행동과 날짜별 일정 목록(일차 배지와 날짜, 장소 수, 순서 번호·장소명·체류 시간, 구간 이동 수단)을 추가한다. `오늘 여행 시작`과 총 이동 시간 요약은 F005·F006 범위이므로 F004에서는 값 없이 비활성 또는 `정보 없음`으로 둔다.
- **UI-007**: 여행 상세의 일정 영역과 편집 화면은 `loading`, `empty`, `error`, `content` 상태를 구분한다. 1초를 넘는 조회에만 대기 표시를 띄우고, 빈 날짜에는 `장소 추가` 행동을, 오류에는 원인과 `다시 시도`를 제공한다. 저장 중에는 `저장` 버튼을 비활성화하고 진행 중임을 표시한다.
- **UI-008**: 순서 변경은 장소 행의 손잡이를 끌어서 이동하는 방식과 행별 위·아래 이동 버튼을 함께 제공한다. 끌기를 쓸 수 없는 사용자도 버튼만으로 같은 결과를 얻을 수 있어야 한다. Figma `ScheduleEditScreen`에는 이 조작이 없으므로 손잡이와 이동 버튼을 Figma에 추가한 뒤 그 모양을 정본으로 따른다.
- **UI-009**: 모든 터치 영역은 최소 48×48dp이고 서로 8dp 이상 떨어져야 하며, 아이콘 전용 버튼(닫기, 삭제, `−`·`+`)에는 접근 가능한 설명을 둔다. 순서·상태·선택은 색만으로 전달하지 않고 번호·아이콘·문구를 병기한다.
- **UI-010**: 화면 너비 360dp와 시스템 최대 글자 크기에서 장소명은 줄바꿈하고 순서 번호, 체류 시간, 삭제·변경·저장 행동이 잘리거나 가로 스크롤을 만들지 않아야 한다.
- **UI-011**: 화면의 색·글자·간격·곡률·아이콘은 Figma Make `Design UI from Reference`(https://www.figma.com/make/H7SpIPF8iNYyxb5jPlo7xM)의 `ScheduleEditScreen`과 `TripDetailScreen` 일정 영역을 정본으로 따르고 `com.gilpick.ui.theme` 토큰에서 값을 읽는다. 스크린리더 낭독 대응은 2026-09-05 팀 결정에 따라 범위 밖이며 10절 최저선만 지킨다.
- **UI-012**: 구현 완료 전 편집 화면의 네 상태, 장소 10곳 이상·긴 장소명, 처리된 장소 포함 상태, 360dp·최대 글자 크기를 실제 기기 또는 screenshot으로 확인한다.

### Key Entities

- **일정 단위 (Trip Day)**: 여행 안의 한 날짜에 대한 일정 묶음. 날짜, 일차 번호, 일정 버전을 가지며 여행에 속한다. 진행 상태·시작 시각은 F006이 채운다.
- **일정 항목 (Itinerary Item)**: 한 날짜 안에서 방문할 장소 하나. 방문 순서, 계획 체류 시간(분)과 그 출처(추천·사용자 조절), 다음 구간 이동 수단, 방문 상태(F004에서는 항상 `예정`)를 가지며 장소 참조를 가리킨다.
- **장소 참조 (Place)**: 일정이 가리키는 장소의 최소 저장 정보. 제공자 장소 식별자(TourAPI 또는 Google), 장소명, 내부 카테고리, 원본 관광 분류, 주소, 위치, 대표 이미지. 같은 제공자 장소는 하나의 참조만 가진다.
- **일정 추가 요청 (Add To Schedule Request)**: F003 시트가 만든 이동 수단·체류 시간과 장소 참조. F004가 받아 편집 중인 날짜의 새 항목으로 바꾼다.
- **일정 저장 요청 (Itinerary Save Request)**: 한 날짜의 항목 전체와 기준 버전, 중복 방지 키. 성공하면 버전이 1 오른 최신 일정으로 응답한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 여행 상세에서 장소 검색을 거쳐 일정 저장까지 5분 안에 마칠 수 있다.
- **SC-002**: 정상 연결 환경에서 일정 조회와 저장 응답은 각각 3초 안에 화면에 반영된다.
- **SC-003**: 추가한 장소의 100%에서 사용자가 값을 바꾸지 않은 경우 저장된 체류 시간이 카테고리 추천값과 같다.
- **SC-004**: 저장 후 다시 조회한 일정에서 순서·체류 시간·이동 수단이 저장 직전 화면과 다른 사례가 0건이다.
- **SC-005**: 같은 저장 요청을 두 번 이상 보낸 검증 사례의 100%에서 항목 중복과 버전 이중 증가가 0건이다.
- **SC-006**: 버전이 어긋난 저장 검증 사례의 100%에서 저장이 거부되고 사용자에게 최신 일정 재조회가 안내된다.
- **SC-007**: 기간 축소 검증 사례의 100%에서 확인 없는 요청은 기간 밖 일정을 삭제하지 않고, 확인한 요청은 기간 밖 일정만 삭제한다.
- **SC-008**: 저장 실패 검증 사례의 100%에서 화면의 편집 내용이 유지되고 재시도 행동이 제공된다.
- **SC-009**: 360dp 화면과 시스템 최대 글자 크기 검증에서 핵심 정보와 행동의 잘림·가로 스크롤이 0건이다.
- **SC-010**: 소유자가 아닌 사용자의 일정 조회·저장 시도가 성공하는 사례가 0건이다.

## Assumptions

- F002의 여행 CRUD와 소유권 검증, F003의 장소 검색·상세와 `일정에 추가` 시트를 그대로 사용하고 F004에서 재정의하지 않는다. F001 인증·재인증 흐름도 그대로 따른다.
- 날짜별 일정 단위와 일정 항목, 장소 참조의 저장 구조는 `docs/design/er-schema.md` 5.2~5.4를 따르고, 조회·저장 계약은 `docs/design/api-spec.md` ITIN-001·ITIN-002를 기준으로 하되 plan 단계에서 F004 시점의 경로 상태 표현(FR-018)을 확정해 계약 문서를 동기화한다.
- 한 날짜의 일정은 항목 전체를 한 번에 저장하는 방식이며, 항목 단위의 부분 저장 API는 두지 않는다. 화면의 `저장` 버튼과 취소 확인 대화상자가 이 방식을 전제한다.
- 새로 추가한 장소는 항상 선택한 날짜의 마지막 순서에 붙고, 원하는 위치로는 순서 변경으로 옮긴다.
- 방문 상태는 F004 저장에서 항상 `예정`이며, 상태 전환은 F006이 담당한다. 처리된 장소에 대한 편집 제한(FR-017)은 서버가 검증하고, F006 이전에는 처리된 장소가 존재하지 않는다.
- 여행 상세 Figma의 `오늘 여행 시작`, 총 이동 시간, 장소별 도착 시각, 구간 소요 시간·거리, `변경하면 남은 일정의 도착 시각이 다시 계산됩니다` 안내는 F005·F006 범위이며 F004는 값 없이 자리만 두거나 표시하지 않는다.
- F002의 기간 축소 확인 UI(삭제 대상 수 안내와 동의)는 현재 앱에 없다(#178 검증 기록). F004는 삭제 대상 수 계산과 확인 후 삭제를 서버에서 제공하고, 앱의 확인 UI는 F002 후속 수정으로 처리한다. 이 후속 작업 Issue는 plan 단계에서 식별한다.
- 하루에 넣을 수 있는 장소 수의 상한은 두지 않되, 저장 요청 크기와 화면 성능 확인 기준은 plan 단계에서 정한다.
- 화면 모양의 정본은 Figma Make `Design UI from Reference`이며 저장소 사본은 `docs/design/figma-make`에 있다(2026-09-05 기준). Figma를 바꾸면 이 명세와 구현을 함께 갱신한다.
