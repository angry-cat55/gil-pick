# Feature Specification: 장소 검색

**Feature Branch**: `docs/ts-f003-place-search-spec`

**Created**: 2026-08-30

**Status**: Draft

**Input**: User description: "F003 장소 검색: TourAPI를 중심으로 장소를 검색·상세 조회하고, 음식·카페·쇼핑의 TourAPI 결과가 부족할 때만 Google Places로 보완한다. 동일 장소는 TourAPI 정보를 기준으로 Google 평점·영업정보만 추가하며 장소별 제공자 표시는 하지 않는다. Owner는 ts이고 선행 Feature는 F001(인증)이다."

## Clarifications

### Session 2026-08-30

- Q: 내부 장소 카테고리에서 `문화`와 `역사`를 분리할 것인가? → A: 두 분류를 `문화·역사`로 합쳐 `자연`, `문화·역사`, `음식`, `카페`, `쇼핑`, `기타`의 6개 카테고리를 사용한다. 기존 `functional-spec.md`, ERD와 API 예시를 기준으로 하고 충돌하던 `requirements.md`를 동기화한다.
- Q: F003 장소 상세에서 운영시간 정보를 어디까지 제공해야 하는가? → A: TourAPI가 제공한 운영 안내를 제공 가능한 경우 표시하되, F003에서는 현재 영업 여부나 정확한 마감 시각을 임의로 계산하지 않는다.
- Q: 키워드와 카테고리를 동시에 지정해 검색 결과를 좁힐 수 있어야 하는가? → A: 각각 단독으로 사용하거나 함께 사용할 수 있으며, 둘 다 없을 때만 검색을 거부한다.
- Q: 사용자가 검색어를 입력할 때 언제 TourAPI 검색을 실행하는가? → A: 입력 중에는 자동 호출하지 않고, 검색 버튼 또는 키보드의 검색 동작을 실행했을 때 호출한다.
- Q: 키워드 검색은 공백을 제거한 뒤 최소 몇 글자부터 허용하는가? → A: 2글자 이상이어야 하며, 카테고리가 선택되어 있으면 키워드 없이도 검색할 수 있다.
- Q: TourAPI 호출이 실패했을 때 어떤 경우에 한 번 자동 재시도하는가? → A: 시간 초과와 일시적인 외부 서버 오류만 1회 재시도하고, 잘못된 요청·인증·호출 제한 오류는 재시도하지 않는다.
- Q: 음식·카페·쇼핑 검색에서 TourAPI 결과가 언제 부족하다고 판단하는가? → A: 각 검색 페이지에서 중복 제거한 TourAPI 결과가 요청 `limit`보다 적을 때만 Google Places를 호출하고 부족한 수만 보완한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 장소 검색 (Priority: P1)

인증된 사용자가 키워드 또는 카테고리로 장소를 검색하고, 필요하면 지역을 좁혀 일정에 넣을 후보를 찾는다. 관광지·문화시설·자연·축제·숙박은 TourAPI 결과를 사용하고, 음식·카페·쇼핑은 TourAPI 결과가 요청 `limit`보다 적을 때 Google Places로 부족한 수만 보완한다.

**Why this priority**: 검색 결과가 있어야 이후 F004에서 사용자가 날짜별 일정에 방문 장소를 추가할 수 있으므로 장소 계획 흐름의 출발점이다.

**Independent Test**: 일정 저장 기능 없이도 키워드·카테고리·지역 조건으로 검색하고 결과 목록의 장소명, 분류, 주소, 위치, 대표 이미지, 추천 체류시간을 확인하는 방식으로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 인증된 사용자가 장소 검색 화면에 있다, **When** 유효한 키워드로 검색한다, **Then** 일치하는 관광지가 목록으로 표시된다.
2. **Given** 인증된 사용자가 장소 검색 화면에 있다, **When** 카테고리를 선택해 검색한다, **Then** 해당 내부 카테고리에 매핑된 관광지만 표시된다.
3. **Given** 사용자가 키워드를 입력하고 카테고리를 선택했다, **When** 검색한다, **Then** 키워드와 카테고리를 모두 만족하는 관광지만 표시된다.
4. **Given** 사용자가 검색 조건과 함께 지역을 선택했다, **When** 검색한다, **Then** 선택한 지역에 해당하는 관광지만 표시된다.
5. **Given** 검색 결과가 한 화면에 모두 표시되지 않는다, **When** 사용자가 목록 끝까지 이동한다, **Then** 기존 결과 뒤에 다음 결과가 중복 없이 추가된다.
6. **Given** 검색 조건에 맞는 관광지가 없다, **When** 검색이 완료된다, **Then** 빈 화면 대신 결과가 없다는 이유와 검색어·필터를 바꾸는 다음 행동이 안내된다.
7. **Given** 사용자가 검색어를 입력하거나 검색 조건을 변경하고 있다, **When** 검색 버튼이나 키보드의 검색 동작을 아직 실행하지 않았다, **Then** 새로운 검색 요청은 전송되지 않는다.
8. **Given** 카테고리를 선택하지 않은 사용자가 공백 제거 후 1글자인 키워드로 검색한다, **When** 검색을 실행한다, **Then** 외부 검색을 호출하지 않고 2글자 이상 입력하도록 안내한다.
9. **Given** 음식·카페·쇼핑 검색에서 중복 제거한 TourAPI 결과가 요청 `limit`보다 적다, **When** 검색이 완료된다, **Then** Google Places 후보가 부족한 수만큼 보완된다.
10. **Given** 양쪽 제공자에서 같은 장소가 확정적으로 식별된다, **When** 결과를 조합한다, **Then** 한 건의 TourAPI 장소로 표시하고 Google 평점·영업정보만 추가한다.
11. **Given** Google 후보가 TourAPI 장소와 같은 장소인지 모호하다, **When** 결과를 조합한다, **Then** 중복 노출 위험이 있는 Google 후보는 결과에서 제외한다.
12. **Given** 관광지·문화시설·자연·축제·숙박을 검색한다, **When** TourAPI 결과가 요청 `limit`보다 적다, **Then** Google Places로 보완하지 않는다.

### User Story 2 - 장소 상세 조회 (Priority: P2)

사용자가 검색 결과에서 장소를 선택해 방문 판단에 필요한 상세 정보를 확인한다.

**Why this priority**: 검색 결과만으로 부족한 운영시간, 평점, 입장료, 혼잡도, 날씨를 확인하고 그 자리에서 이동 수단·체류 시간을 정해 일정에 추가할 수 있어야 한다.

**Independent Test**: 검색 결과의 장소 하나를 선택하고 기본 정보와 제공 가능한 상세 정보가 같은 장소를 가리키는지 확인하는 방식으로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** TourAPI 기반 검색 결과가 있다, **When** 사용자가 한 장소를 선택한다, **Then** TourAPI 상세를 기준으로 장소 정보가 표시되고 확정 매칭된 Google 평점·영업정보가 있으면 함께 표시된다.
2. **Given** 외부 제공자가 일부 상세 필드를 제공하지 않는다, **When** 사용자가 상세를 조회한다, **Then** 확인되지 않은 값은 임의 생성하지 않고 해당 정보가 없음을 구분해 표시하며 나머지 정보는 제공한다.
3. **Given** 유효하지 않거나 더 이상 제공되지 않는 장소를 조회한다, **When** 상세 조회가 완료된다, **Then** 장소를 찾을 수 없다는 안내와 검색 결과로 돌아가는 행동이 제공된다.
4. **Given** Google Places로만 보완된 장소가 있다, **When** 사용자가 상세를 조회한다, **Then** Google이 제공한 장소 기본정보·평점·영업정보 중 허용된 필드만 표시된다.
5. **Given** 상세 화면이 표시되어 있다, **When** 사용자가 `일정에 추가`를 선택한다, **Then** 이동 수단(도보·대중교통·자동차)과 체류 시간(30~360분, 30분 단위, 기본값은 추천 체류시간)을 고르는 시트가 열리고, 확정하면 선택값이 일정 추가 흐름(F004)에 전달되며 취소하면 아무것도 전달되지 않는다.

### User Story 3 - 외부 서비스 장애에서 복구 (Priority: P3)

사용자가 관광 데이터 제공 지연이나 장애를 만나도 원인을 이해하고 검색을 다시 시도할 수 있다.

**Why this priority**: 장소 정보는 외부 제공자에 의존하므로 장애를 정상적인 빈 결과처럼 오해하지 않게 하고 사용자가 흐름을 복구할 수 있어야 한다.

**Independent Test**: 외부 제공자의 지연·실패를 재현해 검색과 상세 화면이 빈 결과와 장애를 구분하고 재시도 행동을 제공하는지 확인할 수 있다.

**Acceptance Scenarios**:

1. **Given** 관광 데이터 제공이 제한 시간 안에 완료되지 않는다, **When** 자동 재시도 후에도 실패한다, **Then** 사용자는 지연 사실과 재시도 방법을 안내받는다.
2. **Given** 관광 데이터 제공자가 오류를 반환한다, **When** 자동 재시도 후에도 실패한다, **Then** 장애가 결과 없음으로 표시되지 않고 사용자는 다시 시도할 수 있다.
3. **Given** 기존 검색 결과가 화면에 표시되어 있다, **When** 다음 결과를 불러오는 중 외부 서비스가 실패한다, **Then** 기존 결과는 유지되고 추가 조회 실패와 재시도 행동이 안내된다.
4. **Given** 외부 서비스가 잘못된 요청·인증·호출 제한 오류를 반환한다, **When** 실패를 처리한다, **Then** 자동 재시도하지 않고 오류 종류에 맞는 복구 안내를 제공한다.
5. **Given** Google 보완 또는 보강 호출만 실패한다, **When** TourAPI 결과나 상세는 정상이다, **Then** TourAPI 정보는 유지하고 Google 기반 필드만 제외한다.
6. **Given** TourAPI 검색이 실패한다, **When** 음식·카페·쇼핑 검색이다, **Then** Google 결과만으로 성공한 것처럼 대체하지 않고 TourAPI 장애를 안내한다.

### Edge Cases

- 카테고리 없이 키워드만 검색할 때 앞뒤 공백을 제거한 키워드가 2글자 미만이면 검색을 실행하지 않고 2글자 이상 입력하도록 안내한다.
- 카테고리가 선택되어 있으면 키워드가 없어도 검색을 허용하며, 함께 입력된 키워드가 있으면 앞뒤 공백을 제거한 뒤 같은 2글자 기준을 적용한다.
- 키워드와 카테고리를 함께 지정하면 두 조건을 모두 만족하는 결과만 표시한다.
- 지역 조건에 해당하는 결과가 없으면 외부 서비스 장애와 구분되는 검색 결과 없음 상태를 표시한다.
- 다음 결과를 요청했는데 같은 장소가 다시 포함되면 목록에 중복 표시하지 않는다.
- 장소명·주소가 길거나 대표 이미지·운영시간·입장료·혼잡도·날씨가 누락되어도 목록과 상세의 핵심 정보 및 행동이 가려지지 않는다.
- 인증이 만료되면 F001의 인증 오류 처리에 따라 재인증 흐름으로 유도한다.
- 외부 서비스 제한 횟수 초과는 일반 장애와 구분해 안내하되 credential이나 내부 제한값을 노출하지 않는다.
- TourAPI의 정상적인 빈 결과·`limit` 미만 결과와 TourAPI 장애를 구분하고, 정상 응답일 때만 Google 보완을 실행한다.
- Google 후보는 확정 매칭이면 TourAPI 장소에 병합하고, 비매칭이면 보완 후보로 추가하며, 동일 장소 여부가 모호하면 제외한다.
- Google 전용 장소와 TourAPI 장소는 서로 충돌하지 않는 이름공간 식별자를 사용하며 알 수 없는 식별자 형식은 거부한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 인증된 사용자가 키워드와 내부 카테고리를 각각 단독으로 사용하거나 함께 사용해 장소를 검색하도록 허용해야 한다.
- **FR-002**: 시스템은 검색 조건과 함께 선택적인 지역 조건을 적용하도록 허용해야 한다.
- **FR-003**: 시스템은 키워드와 카테고리가 모두 없는 검색 요청을 거부하고 하나 이상의 검색 조건을 입력하도록 안내해야 한다.
- **FR-003a**: 시스템은 사용자가 검색 버튼 또는 키보드의 검색 동작을 명시적으로 실행한 경우에만 새로운 검색을 시작해야 하며, 검색어 입력이나 조건 변경만으로 자동 검색해서는 안 된다.
- **FR-003b**: 시스템은 키워드의 앞뒤 공백을 제거한 뒤 2글자 이상인지 검증해야 한다. 카테고리만 지정한 검색은 키워드 없이 허용하되, 카테고리와 함께 입력한 키워드도 동일한 길이 기준을 충족해야 한다.
- **FR-004**: 시스템은 검색 결과마다 장소 식별자, 장소명, 내부 카테고리, 원본 관광 분류, 주소, 위치, 대표 이미지와 추천 체류시간을 제공 가능한 범위에서 반환해야 한다.
- **FR-005**: 시스템은 검색 결과를 cursor 기반으로 이어서 조회하도록 지원하고, 같은 조회 흐름에서 장소가 중복 노출되지 않도록 해야 한다.
- **FR-006**: 시스템은 사용자가 검색 결과의 장소를 선택해 대표 이미지, 영업 상태, 이름, 주소, 평점, 운영시간, 입장료, 혼잡도, 날씨 중 제공 가능한 상세 정보를 조회하도록 허용해야 한다. 설명과 연락처는 화면에 표시하지 않는다.
- **FR-007**: 시스템은 외부 제공자가 반환하지 않은 선택 정보와 확인할 수 없는 운영정보를 임의로 생성하지 않고 누락 또는 미확인으로 구분해야 한다. TourAPI 운영 안내에서 현재 영업 여부나 정확한 마감 시각을 계산해서는 안 된다.
- **FR-008**: 시스템은 TourAPI 관광 분류를 `자연`, `문화·역사`, `음식`, `카페`, `쇼핑`, `기타`의 6개 내부 카테고리로 일관되게 변환해야 한다.
- **FR-009**: 시스템은 내부 카테고리에 따라 정해진 추천 체류시간을 검색 결과와 상세의 `일정에 추가` 시트 기본 체류 시간으로 동일하게 제공해야 한다.
- **FR-010**: 시스템은 TourAPI와 필요한 Google Places 데이터를 실시간 조회하고, 각 외부 호출이 5초를 넘기거나 일시적인 외부 서버 오류가 발생하면 최대 한 번 자동 재시도해야 한다. 잘못된 요청·인증·호출 제한 오류는 자동 재시도해서는 안 된다.
- **FR-011**: 시스템은 자동 재시도 후에도 외부 서비스가 실패하면 장애·시간 초과·호출 제한과 정상적인 검색 결과 없음을 구분해 사용자에게 알려야 한다.
- **FR-012**: 시스템은 추가 결과 조회가 실패해도 이미 표시된 검색 결과를 유지하고 사용자가 추가 조회만 다시 시도하도록 해야 한다.
- **FR-013**: 시스템은 외부 서비스 credential, 원본 오류 내용과 내부 운영정보를 사용자 응답이나 화면에 노출하지 않아야 한다.
- **FR-014**: F003의 검색·상세 조회만으로 장소를 일정이나 영구 저장소에 저장해서는 안 된다. `일정에 추가` 시트에서 확정한 이동 수단·체류 시간은 장소 참조와 함께 F004에 전달만 하며, 저장은 F004 범위로 남겨야 한다.
- **FR-015**: 시스템은 관광지·문화시설·자연·축제·숙박 검색과 상세에 TourAPI를 우선 사용하고 Google Places 검색 결과로 이 유형을 보완해서는 안 된다.
- **FR-016**: 시스템은 음식·카페·쇼핑의 각 검색 페이지에서 중복 제거한 TourAPI 결과가 요청 `limit`보다 적을 때만 Google Places를 호출하고 부족한 수만 추가해야 한다.
- **FR-017**: 시스템은 양쪽에서 같은 장소가 확정적으로 매칭되면 TourAPI 장소 식별자와 기본·상세정보를 기준으로 유지하고 Google의 평점·평점 수·영업정보만 선택적으로 병합해야 한다. Google 사진·리뷰는 요청하거나 표시해서는 안 된다.
- **FR-018**: 시스템은 장소명·좌표·주소를 조합한 확정 규칙으로 교차 제공자 중복을 판정하고, 동일 장소 여부가 모호한 Google 후보는 결과에서 제외해야 한다.
- **FR-019**: 시스템은 Google 보완·보강 실패가 TourAPI 결과나 상세를 제거하거나 전체 실패로 바뀌게 해서는 안 되며, TourAPI 실패를 Google 결과로 대체해 성공처럼 표시해서도 안 된다.
- **FR-020**: 시스템은 TourAPI 장소와 Google 전용 장소를 구분하는 안정적인 식별자를 사용해 상세 제공자를 결정해야 하며, 화면에는 장소별 제공자 배지나 출처 문구를 표시해서는 안 된다.
- **FR-021**: 시스템은 Google 제공 평점·영업정보를 표시하는 영역에서 Google의 필수 attribution과 제3자 attribution을 준수해야 한다. 이는 장소별 출처 배지로 사용해서는 안 된다.
- **FR-022**: F003은 상세의 `일정에 추가` 시트(이동 수단·체류 시간 선택)와 검색 결과 행의 `+` 버튼까지만 제공하고, 일정 저장·편집, 지도 경로 계산, 대체 장소 추천은 제공하지 않아야 한다. 상세의 지도 버튼·지도 미리보기와 찜 버튼은 디자인대로 표시하되 동작 연결은 지도·찜 feature에서 한다.
- **FR-023**: 시스템은 상세에 입장료, 혼잡도, 날씨를 제공 가능한 경우 표시하고, 제공자가 주지 않으면 FR-007에 따라 `정보 없음`으로 구분해야 한다. 이 세 값의 API 계약(`PLACE-002` 응답 필드)은 Backend와 합의해 `contracts/places.openapi.yaml`과 `docs/design/api-spec.md`에 추가한다.

### UI Requirements *(include if feature contains user-facing UI)*

- **UI-001**: 검색 화면은 뒤로 가기, `장소 추가` 제목, `장소 이름 검색` 입력(입력 중 지우기 버튼 포함), 카테고리 칩(전체·자연·문화·역사·음식·카페·쇼핑), `검색 결과 N곳` 요약, `거리순` 정렬 표시와 검색 결과 목록을 제공해야 한다. 검색 실행은 키보드의 검색 동작으로 접근할 수 있어야 하며, 입력이 비어 있으면 `어떤 장소를 찾고 계세요?` 안내를 보여야 한다.
- **UI-002**: 검색과 상세 화면은 `loading`, `empty`, `error`, `content` 상태를 구분해야 한다. 1초를 넘는 최초 조회에는 대기 표시를, 빈 결과에는 `'{검색어}' 검색 결과가 없어요` 안내와 `카테고리로 찾기` 행동을, 오류에는 원인과 재시도 행동을 제공해야 한다.
- **UI-003**: 검색 조건을 바꾸거나 새 검색을 실행할 때는 이전 조건의 결과를 새 결과로 오인하지 않도록 교체하되, 다음 결과를 추가 조회하는 동안에는 기존 결과를 유지해야 한다.
- **UI-004**: 검색 결과 행은 60dp 대표 이미지, 장소명, 내부 카테고리, `★` 평점, 영업 상태(`운영 중`·`HH:MM 마감`) 중 제공 가능한 정보를 표시하고, 이미지·본문을 선택하면 상세로 이동하며, 행 끝의 `+` 버튼은 상세와 같은 `일정에 추가` 시트를 연다.
- **UI-005**: 대표 이미지가 없거나 로드에 실패해도 대체 표현을 사용하며 장소명과 선택 행동이 유지되어야 한다. 의미 있는 이미지에는 접근 가능한 설명을 제공하고 장식 이미지는 접근성 탐색에서 제외해야 한다.
- **UI-006**: 오류와 검색 결과 변화는 화면 판독기가 인지할 수 있어야 하며, 화면의 읽기·포커스 순서는 검색 조건 → 결과 요약 → 결과 목록 순서를 따라야 한다.
- **UI-007**: 모든 터치 영역은 최소 48×48dp(보이는 크기가 더 작아도 터치 영역은 확보)를 확보하고, 본문 글자(`#111827`)는 배경 대비 4.5:1을 충족해야 한다. 보조 라벨·설명 글자 색은 디자인 정본의 `#94A3B8`·`#6B7280`을 그대로 따른다.

- **UI-009**: 검색 결과에서 상세로 이동했다가 뒤로 돌아오면 검색어, 선택한 조건, 불러온 결과와 목록 위치가 유지되어야 한다.

### Key Entities

- **장소 검색 결과 (Place Search Result)**: TourAPI를 기준으로 하거나 Google Places에서 보완된 한 장소 후보. 제공자 이름공간 식별자, 장소명, 내부 카테고리, 주소, 위치, 대표 이미지, 추천 체류시간과 선택적인 Google 평점·영업정보를 가진 일시적인 조회 결과다.
- **장소 상세 (Place Detail)**: 특정 검색 결과의 확장 정보. 검색 결과의 기본 정보에 확인 가능한 운영시간과 평점, 그리고 제공 가능한 경우 입장료·혼잡도·날씨가 더해진다. 설명과 연락처는 계약에 남아 있어도 화면에는 쓰지 않는다.
- **일정 추가 요청 (Add To Schedule Request)**: 상세 시트에서 확정한 이동 수단(도보·대중교통·자동차)과 체류 시간(분). F003은 만들어 F004에 전달만 한다.
- **검색 페이지 (Search Page)**: 현재 검색 조건에 해당하는 결과 묶음과 다음 결과를 이어서 조회하기 위한 위치 정보를 나타낸다.
- **장소 매칭 (Place Match)**: TourAPI 장소와 Google 후보가 같은 장소인지 장소명·좌표·주소로 판정한 일시적인 결과다. 확정된 경우에만 Google 필드를 TourAPI 장소에 병합한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Google 보완이 필요 없는 정상 외부 서비스 환경에서 사용자는 검색 실행 후 5초 이내에 결과 또는 결과 없음 안내를 확인할 수 있다.
- **SC-002**: 정상적인 외부 서비스 환경에서 사용자는 검색 결과에서 장소를 선택한 뒤 5초 이내에 상세 정보를 확인할 수 있다.
- **SC-003**: 동일 제공자 식별자와 확정된 교차 제공자 매칭 fixture에 대한 검색·추가 조회 검증에서 중복 노출이 0건이다.
- **SC-004**: 대표 이미지, 운영시간, 입장료, 혼잡도 또는 날씨가 누락된 모든 검증 사례에서 확인되지 않은 값이 사실처럼 표시되는 비율은 0%이고, 제공 가능한 나머지 정보는 계속 확인할 수 있다.
- **SC-005**: 외부 서비스 장애·시간 초과 검증 사례의 100%에서 정상적인 결과 없음과 구분되는 안내 및 재시도 행동이 제공된다.
- **SC-006**: 접근성 검증에서 모든 검색·필터·결과·재시도 조작이 화면 판독기와 키보드 또는 스위치 탐색만으로 완료 가능하다.
- **SC-007**: 360dp 화면과 시스템 최대 글자 크기 검증에서 핵심 정보 및 행동의 잘림과 의도하지 않은 가로 스크롤이 0건이다.
- **SC-008**: 단일 외부 제공자의 timeout 또는 일시적인 서버 오류로 자동 재시도가 발생한 검증 사례에서 사용자는 해당 제공자 호출 시작 후 11초 이내에 최종 결과 또는 실패 이유를 확인할 수 있다.
- **SC-009**: 음식·카페·쇼핑의 TourAPI 결과가 요청 `limit`보다 적은 모든 검증 사례에서 Google의 공급 가능한 후보 범위까지 부족분이 채워진다.
- **SC-010**: 확정된 교차 제공자 매칭 검증 사례의 100%에서 TourAPI 기본·상세정보가 유지되고 Google 평점·평점 수·영업정보 외의 필드는 병합되지 않는다.
- **SC-011**: Google 보완·보강 장애 검증 사례의 100%에서 정상 TourAPI 결과 손실이 0건이고 Google 기반 필드만 제외된다.
- **SC-012**: 검색·상세 화면 검증에서 장소별 제공자 배지·출처 문구는 0건이며 Google 데이터가 표시된 모든 영역은 필수 attribution 기준을 충족한다.
- **SC-013**: 자동 재시도가 없는 Google 보완 검색에서 사용자는 검색 실행 후 10초 이내에 최종 조합 결과를 확인할 수 있다.
