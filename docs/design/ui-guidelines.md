# 길픽 UI 가이드라인

앱 전체에서 반복되는 시각 기준을 정의한다. 기능별 화면 요구사항은 각 feature의 `spec.md`에 두고, 이 문서는 모든 화면이 공유하는 값과 규칙만 담는다.

이 문서가 값의 단일 기준이며, `com.gilpick.ui.theme`의 Compose 토큰이 그 실행 가능한 버전이다. 둘이 어긋나면 이 문서를 고치고 토큰을 맞춘다.

시각 레퍼런스는 `gilpick-design-reference.pen`이다. 이 문서의 값은 레퍼런스에서 추출한 뒤 접근성 기준으로 검증·조정한 결과다.

## 1. 제품 성격과 디자인 방향

길픽은 계획만 하는 앱이 아니라 **이동 중에도 보는 앱**이다. 이 차이가 모든 시각 결정의 기준이다.

> Wanderlog의 조밀하고 편집하기 쉬운 일정 문서 구조에, 이동 중에도 즉시 읽히는 큰 ETA와 신뢰 가능한 실시간 상태 레이어를 결합한다.

**가져올 구조**

- 지도와 하단 일정 문서의 조합
- 날짜별 가로 탐색
- 장소 순서를 보여주는 세로 타임라인 목록
- 낮은 카드 장식과 높은 정보 밀도
- 빠른 장소 추가와 일정 편집

**다르게 만들 것**

- 더 큰 본문과 터치 영역. 야외에서 걸으면서 본다
- 현재 위치·다음 장소·ETA의 강한 시각 계층
- 자동 처리의 남은 시간과 되돌리기 수단을 항상 노출
- 변수 추천에 결론뿐 아니라 이유를 함께
- 팝업 대신 화면 안에서 점진적으로 확장되는 안내
- 계획 모드와 진행 모드를 명확히 구분

## 2. 디자인 원칙

1. **명세가 요구한 동작을 먼저 만족시킨다.** 시각 완성도는 요구된 동작을 가린 채 추가하지 않는다.
2. **강조는 화면당 한 곳에만 둔다.** 주요 행동 버튼 하나가 강조를 가져가고 나머지는 물러난다.
3. **색만으로 의미를 전달하지 않는다.** 상태·오류·성공은 색과 함께 텍스트나 아이콘을 병기한다.
4. **모든 요소를 카드로 감싸지 않는다.** 장소마다 둥근 카드를 반복하면 이동 순서의 연속성이 끊긴다. 일정은 타임라인과 구분선으로 잇는다.
5. **임시 화면은 임시라고 표시한다.** 동작만 구현한 shell을 완료로 간주하지 않고 task와 PR에 명시한다.

## 3. 색상

청록 계열 브랜드색과 따뜻한 중립색을 쓴다. 지도 위에서 색이 경쟁하지 않도록 의미색은 네 개로 제한한다.

### 라이트

| 토큰 | 값 | 용도 |
|---|---|---|
| `background` | `#FAFBF9` | 화면 바탕 |
| `surface` | `#FFFFFF` | 카드, sheet, 앱바 |
| `surfaceVariant` | `#F1F4F2` | 검색창, 필터, 비활성 영역, 예약 항목 |
| `onSurface` | `#18201E` | 제목과 본문 |
| `onSurfaceVariant` | `#64706D` | 주소, 기간, 보조 정보 |
| `primary` | `#0A7268` | 주요 버튼, 선택 상태, 현재 경로, ETA |
| `onPrimary` | `#FFFFFF` | primary 위 텍스트 |
| `primaryContainer` | `#D6F3EE` | 선택된 날짜·칩, 시간 뱃지 |
| `secondary` | `#526A64` | 보조 행동과 아이콘 |
| `onSecondary` | `#FFFFFF` | secondary 위 텍스트 |
| `error` | `#BA1A1A` | 실패, 파괴적 행동 |
| `warning` | `#A15C00` | 영업 종료 임박, 확인 필요 |
| `success` | `#287A47` | 도착, 완료 |
| `info` | `#36618E` | 계획 ETA, 일반 안내 |
| `outline` | `#7F8C88` | 컨트롤 경계, 타임라인 연결선 |
| `outlineVariant` | `#D8DEDB` | 목록 구분선 |

### 다크

역상이 아니라 별도로 설계한다. 다크 팔레트는 아직 확정하지 않았다. 확정 시 이 절에 라이트와 같은 형식으로 값과 검증 수치를 넣는다. 그전까지 다크 테마를 지원한다고 표시하지 않는다.

### 검증된 대비

WCAG 2.x 상대 휘도 공식으로 계산했다. 본문 4.5:1, 컨트롤 경계와 의미 있는 선 3:1이 기준이다.

| 조합 | 비율 | 사용처 |
|---|---|---|
| `onSurface` / `surface` | 16.61:1 | 장소명, 여행명 |
| `onSurface` / `background` | 16.00:1 | 화면 제목 |
| `onSurfaceVariant` / `surface` | 5.15:1 | 기간, 주소 |
| `onSurfaceVariant` / `background` | 4.96:1 | 섹션 라벨 |
| `onSurfaceVariant` / `surfaceVariant` | 4.65:1 | 검색 placeholder |
| `onPrimary` / `primary` | 5.80:1 | 주버튼 라벨 |
| `primary` / `surface` | 5.80:1 | ETA, 길찾기, 경로 최적화 |
| `primary` / `primaryContainer` | 4.95:1 | 칩 라벨, 날짜 선택, 시간 뱃지 |
| `warning` / `surfaceVariant` | 4.69:1 | 변수 경고 |
| `success` / `surface` | 5.30:1 | 완료 표시 |
| `error` / `surface` | 6.46:1 | 실패 안내 |
| `info` / `surface` | 6.45:1 | 계획 ETA |
| `onSecondary` / `secondary` | 5.83:1 | 보조 버튼 |
| `outline` / `surface` | 3.49:1 | 타임라인 연결선 |
| `outline` / `background` | 3.37:1 | 타임라인 연결선 |
| `outline` / `surfaceVariant` | 3.16:1 | 입력창 경계 |

`outlineVariant`는 목록 구분선 전용이며 3:1 대상이 아니다. 컨트롤 경계나 순서를 나타내는 선에는 반드시 `outline`을 쓴다.

### 지도 위 색 사용

지도에서는 핀 종류를 네 가지로 제한한다. 날씨·혼잡·영업시간마다 다른 색을 쓰지 않는다.

| 핀 | 색 |
|---|---|
| 일반 장소 | `primary` |
| 선택된 장소 | `primary` + 확대 |
| 방문 완료 | `success` |
| 주의 필요 | `warning` |

### 출처와 조정 기록

값은 `gilpick-design-reference.pen`에서 가져왔고, 채택 전 아래를 조정했다. 레퍼런스와 skill의 제안은 권고이며 저장소 기준으로 검증한 뒤 쓴다(`AGENTS.md` 9절).

| 조정 | 이유 |
|---|---|
| `primary`를 `#087F73` → `#0A7268` | `primaryContainer` 위에서 4.17:1로 본문 기준 미달. 칩·날짜 선택·시간 뱃지에 쓰이는 조합이다 |
| `outline`을 `#D8DEDB` → `#7F8C88`, 구분선은 `outlineVariant`로 분리 | 단일 값이 1.36:1이었다. 타임라인 연결선은 이동 순서를 나타내는 의미 있는 선이라 3:1 대상이다 |

## 4. 타이포그래피

별도 폰트를 번들하지 않고 시스템 기본을 쓴다. 한글은 기기 기본 폰트로 렌더링된다.

Pretendard 같은 전용 폰트는 숫자 정렬과 조밀함에서 이점이 있으나, APK 용량과 구현 단순성을 우선한다. 도입하려면 별도 결정으로 이 절을 갱신한다.

| 역할 | 크기/행간 | 굵기 | 사용처 |
|---|---|---|---|
| Display | 28 / 36sp | 700 | 로그인, 여행 완료처럼 드문 강조 |
| Screen title | 22 / 30sp | 700 | 내 여행, 9월 12일 |
| Section title | 18 / 26sp | 700 | 다음 장소, 1일차 일정 |
| ETA emphasis | 24 / 30sp | 700 | 오후 2:35 도착 |
| Card title | 16 / 24sp | 600 | 장소명, 여행명 |
| Body | 15 / 22sp | 400 | 안내, 장소 설명 |
| Label | 14 / 20sp | 600 | 버튼, 탭, 필터 |
| Supporting | 13 / 18sp | 400 | 주소, 기간, 이동 정보 |
| Caption | 12 / 16sp | 500 | 거리, 갱신 시각, 상태 뱃지 |

- **12sp 미만을 쓰지 않는다.** 하단 탭 라벨을 포함한다. 이동 중 야외에서 보는 앱이라 Wanderlog보다 한 단계 크게 잡는다.
- 크기를 새로 만들지 않는다. 위 역할 중에서 고른다.
- 행간을 생략하지 않는다. 한글은 라틴 문자보다 넉넉한 행간이 필요하다.
- 시스템 글자 크기 확대에서 잘리지 않아야 한다. 고정 높이 대신 여백으로 처리한다.
- 시각, 거리, 소요 시간처럼 자릿수가 바뀌는 숫자에는 고정폭 숫자를 쓴다.

## 5. 간격과 크기

4dp 배수만 쓴다.

| 토큰 | 값 | 용도 |
|---|---|---|
| `space1` | 4dp | 제목과 설명 사이 |
| `space2` | 8dp | 아이콘과 텍스트 사이 |
| `space3` | 12dp | 텍스트와 행동 사이, 목록 행 세로 여백 |
| `space4` | 16dp | 앱바 좌우, 카드 내부 |
| `space5` | 20dp | 화면 좌우 여백 |
| `space6` | 24dp | 주요 섹션 사이 |

**화면 좌우 여백은 20dp, 앱바 좌우는 16dp다.** 앱바 아이콘이 화면 가장자리에 더 가깝게 붙어 터치하기 쉽다.

| 요소 | 크기 |
|---|---|
| 터치 영역 | 최소 48 × 48dp |
| 주요 CTA 높이 | 52 ~ 56dp |
| 보조 버튼 높이 | 44 ~ 48dp |
| 장소 썸네일 | 64 × 64dp 또는 72 × 72dp |
| 터치 영역 간격 | 최소 8dp |

주요 버튼과 진행 정보는 Wanderlog보다 크게 설계한다. 이동 중에 한 손으로 조작한다.

## 6. 곡률

목록 안에서는 곡률을 거의 드러내지 않고, 화면을 감싸는 큰 컨테이너와 플로팅 요소에만 강하게 쓴다.

| 토큰 | 값 | 용도 |
|---|---|---|
| `radiusXs` | 4dp | 시간 뱃지, 작은 상태 라벨 |
| `radiusSm` | 8dp | 입력창, 작은 버튼, 썸네일, 날짜 항목 |
| `radiusMd` | 12dp | 여행 카드, 추천 카드, 버튼 |
| `radiusLg` | 16dp | bottom sheet, 큰 상태 카드 |
| `radiusXl` | 24dp | 주요 안내 패널, dialog |
| `radiusFull` | 50% | FAB, 칩, 핀, 상태 점 |

- 장소 일정 행은 카드로 감싸지 않는다. 곡률 0dp로 두고 타임라인과 구분선으로 잇는다.
- 지도 bottom sheet는 상단 모서리만 둥글게 한다.
- 그림자는 최소화하고 `outlineVariant` 경계나 `surface` 차이로 계층을 표현한다. FAB와 bottom sheet만 예외다.

## 7. 공통 컴포넌트

`com.gilpick.ui.component`에 두고 모든 feature가 재사용한다. 화면에서 Material 컴포넌트를 직접 조립하지 않는다.

### 버튼

| 종류 | 규칙 |
|---|---|
| 주요 | `primary` 채움, `radiusMd`, 높이 52~56dp, Label 15sp/700. 화면당 하나 |
| 보조 | 외곽선 또는 텍스트, 높이 44~48dp, Label 14sp/600. 주요 버튼보다 시각 무게가 낮아야 한다 |
| 위험 | `error` 사용. 주요 버튼과 공간적으로 분리하고 확인 절차를 붙인다 |
| FAB | `primary`, `radiusFull`, 아이콘과 라벨 병기 |

### 입력창

- 라벨을 항상 보이게 둔다. placeholder를 라벨 대신 쓰지 않는다.
- 오류는 입력창 바로 아래에 원인과 해결 방법을 함께 쓴다.
- 검색창은 `surfaceVariant` 채움에 `radiusSm`, 좌측 아이콘과 8dp 간격.

### 여행 카드

여행명 16sp/600 · 기간 13sp/400 · 상태 pill · 부가 정보 한 줄(D-37, 장소 수). `radiusMd`, 그림자 대신 `surface` 차이.

### 여행 목록 행

썸네일 64dp · 텍스트 3줄 · chevron. 카드로 감싸지 않고 행 사이를 `outlineVariant` 구분선으로 나눈다. 세로 여백 12dp.

### 진행 중 카드

계획용 카드와 확실히 다르게 보여야 한다.

```
[여행 중]  제주 3박 4일 · 1일차
다음 장소
성산일출봉                      ← 18sp/700
오후 2:35 도착   12분 남았어요    ← 24sp/700 primary
⚠ 도착 시간에 비가 올 가능성이 높아요
[도착했어요]  [일정 보기]
```

- `radiusLg`, `surface` 채움
- 상태 pill은 `primary` 채움 + `radiusFull`
- ETA는 화면에서 가장 큰 숫자
- 수동 행동 버튼을 항상 유지한다

### 날짜 선택

가로 스크롤. 날짜 14sp/600과 요일·일차 12sp/500 두 줄. 선택 상태는 `primaryContainer` 배경과 `primary` 글자로 표시한다. 날짜별 상태가 있으면 작은 점을 더한다.

### 장소 일정 행

```
● 1   성산일출봉
      유네스코 세계자연유산. 바다 위로 솟은 분화구 정상에서…
      [09:00]                              [썸네일]
│
│     도보 6분 · 0.4km          길찾기
│
● 2   광치기해변
```

- 번호 핀(`primary`, `radiusFull`)과 세로 연결선(`outline`)이 이동 순서를 담당한다
- 장소명 16sp/600, 설명 15sp/400, 시간 뱃지 12sp/600 `primaryContainer`
- 이동 정보는 두 장소 사이 연결선 옆에 둔다
- 행 전체를 카드로 감싸지 않는다

### 상태 뱃지

색과 텍스트를 함께 쓴다. `radiusFull`, Caption 12sp/500. 색만으로 상태를 구분하지 않는다.

### 하단 탭

최대 5개, 아이콘과 라벨을 함께 표시한다. 라벨은 12sp 이상. 현재 위치를 `primaryContainer` 배경과 `primary` 글자로 표시한다.

### 카카오 로그인 버튼

카카오 브랜드 가이드가 정한 값이며 앱 팔레트와 무관하게 고정이다.

| 항목 | 값 |
|---|---|
| 배경 | `#FEE500` |
| 라벨 | `#191919` |
| 대비 | 13.75:1 |

## 8. 텍스트 작성 방식

계획 화면은 명사 중심으로 짧게, 진행 화면은 상태와 다음 행동을 문장으로 분명히 쓴다.

**계획 화면**

```
2일차 · 경복궁 · 오전 10:00 · 1시간 30분 · 도보 12분 · 장소 추가
```

**진행 화면**

```
경복궁까지 12분 남았어요
오후 2:35 도착 예정
도착하셨나요?
5분 뒤 자동으로 도착 처리돼요
되돌리기 · 4:32
```

**변수와 추천은 기술 용어가 아니라 방문 판단으로 쓴다**

| 쓰지 않는다 | 쓴다 |
|---|---|
| 운영시간 변수 감지 | 도착 전에 문을 닫을 수 있어요 |
| 강수확률 임계값 초과 | 도착 시간에 비가 올 가능성이 높아요 |
| 대체 후보 추천 | 근처의 실내 장소로 바꿔볼까요? |

추천에는 결론뿐 아니라 짧은 이유를 붙인다.

```
실내이고 현재 장소보다 8분 가까워요
평점 4.5 · 도보 6분 · 오후 8시까지 영업
```

## 9. 화면 상태

목록과 상세를 가진 모든 화면은 네 상태를 전부 가진다.

| 상태 | 표현 |
|---|---|
| `loading` | 1초를 넘길 때만 skeleton을 띄운다. 그 전에는 아무것도 표시하지 않는다 |
| `empty` | 왜 비었는지와 다음 행동 버튼을 함께 보여준다 |
| `error` | 원인과 복구 방법을 쓰고 재시도 버튼을 둔다. "오류가 발생했습니다"만 쓰지 않는다 |
| `content` | 실제 내용 |

갱신 중 기존 내용을 유지할지 비울지는 화면마다 다르므로 해당 feature의 `spec.md`에서 정한다.

### 변수 경고

모달을 남발하지 않는다. 화면 안 배너나 bottom sheet 확장 상태를 쓴다.

```
영업 종료 임박
도착 예정 시각은 오후 5:40이고, 이 장소는 오후 6시에 문을 닫아요.

[기존 일정 유지]  [다른 장소 보기]
```

실시간 데이터를 근거로 안내할 때는 **출처와 갱신 시각**을 함께 표시한다. 반복 tooltip과 부정확한 영업시간 안내는 신뢰를 빠르게 떨어뜨린다.

## 10. 접근성 최저선

| 항목 | 기준 |
|---|---|
| 본문 텍스트 대비 | 4.5:1 이상 |
| 컨트롤 경계·의미 있는 선·아이콘 대비 | 3:1 이상 |
| 최소 글자 크기 | 12sp |
| 터치 영역 | 48 × 48dp 이상 |
| 터치 영역 간격 | 8dp 이상 |
| 아이콘 전용 버튼 | `contentDescription` 필수 |
| 장식용 아이콘 | `contentDescription = null` |
| 색 단독 의미 전달 | 금지. 텍스트나 아이콘 병기 |
| 시스템 글자 확대 | 최대 배율에서 잘림 없음 |
| 포커스 표시 | 키보드·스위치 접근 시 보이는 포커스 링 |

- 화면 너비 360dp에서 가로 스크롤이나 잘림이 없어야 한다.
- 자동 도착 처리처럼 시간이 걸리는 동작에는 남은 시간과 취소 수단을 함께 노출한다.
- 지도 위 정보는 지도를 못 보는 사용자를 위해 목록으로도 제공한다.

## 11. Compose 구현 규칙

**소유 위치**

| 경로 | 내용 |
|---|---|
| `com.gilpick.ui.theme` | 색상·타이포·간격·곡률 토큰, `GilpickTheme` |
| `com.gilpick.ui.component` | 공통 컴포넌트 |

feature 패키지(`com.gilpick.auth`, `com.gilpick.trip` 등)가 아니라 중립 위치에 둔다. 특정 feature가 소유하면 다른 feature가 쓸 근거가 없어진다.

**Material 3에 있는 값**

`background`, `surface`, `surfaceVariant`, `onSurface`, `onSurfaceVariant`, `primary`, `onPrimary`, `primaryContainer`, `secondary`, `onSecondary`, `error`, `outline`, `outlineVariant`는 `ColorScheme`에 대응 역할이 있다. 그대로 매핑하고 `MaterialTheme.colorScheme`에서 읽는다.

**Material 3에 없는 값**

`warning`·`success`·`info`와 간격·곡률 토큰은 `ColorScheme`·`Shapes`에 자리가 없다. `CompositionLocal`과 data class로 `GilpickTheme` 안에서 제공한다.

```kotlin
data class GilpickColors(val warning: Color, val success: Color, val info: Color)
data class GilpickSpacing(val space1: Dp, /* … */ val space6: Dp)

val LocalGilpickColors = compositionLocalOf<GilpickColors> { error("GilpickTheme 밖입니다") }
val LocalGilpickSpacing = compositionLocalOf<GilpickSpacing> { error("GilpickTheme 밖입니다") }
```

- 기본값을 주지 않고 `error(...)`로 둔다. 테마 밖에서 쓰면 조용히 잘못된 색이 나오는 대신 즉시 실패한다.
- 화면에서는 `LocalGilpickColors.current.warning` 형태로 읽는다.

**공통 규칙**

- 화면 코드에 색상 리터럴(`Color(0xFF...)`)을 쓰지 않는다.
- 간격·곡률도 리터럴 `dp` 대신 토큰을 쓴다. 예외는 토큰으로 표현할 수 없는 일회성 조정이며, 그 경우 주석으로 이유를 남긴다.
- 다크 테마는 `colorScheme`과 `CompositionLocal` 값 교체로만 처리한다. 화면에서 `isSystemInDarkTheme()`로 분기하지 않는다.
- dynamic color(Material You)는 쓰지 않는다. 기기 배경색에 따라 브랜드색이 바뀌면 3절의 검증된 대비가 무효가 된다.
- 이 규칙을 지키면 나중에 색상 방향을 바꿀 때 `Theme.kt` 한 파일만 고치면 된다.

구현 시 `.claude/skills/compose-expert`의 `references/theming-material3.md`와 `references/atomic-design.md`를 참고한다.

## 12. 변경 절차

- 이 문서의 값을 바꾸면 같은 PR에서 `com.gilpick.ui.theme`를 함께 갱신한다.
- 대비에 영향을 주는 색상 변경은 수치를 다시 계산해 3절 표를 갱신한다.
- 토큰에 없는 색이나 크기가 필요하면 화면 코드에 직접 쓰지 말고 이 문서에 먼저 추가한다.
- 화면 구현이 이 문서와 어긋나면 임의로 해석하지 말고 차이를 Issue나 PR에 기록해 결정을 받는다.
