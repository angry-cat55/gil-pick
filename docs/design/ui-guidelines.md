# 길픽 UI 가이드라인

앱 전체에서 반복되는 시각 기준을 정의한다. 기능별 화면 요구사항은 각 feature의 `spec.md`에 두고, 이 문서는 모든 화면이 공유하는 값과 규칙만 담는다.

이 문서가 값의 단일 기준이며, `com.gilpick.ui.theme`의 Compose 토큰이 그 실행 가능한 버전이다. 둘이 어긋나면 이 문서를 고치고 토큰을 맞춘다.

## 1. 디자인 원칙

1. **명세가 요구한 동작을 먼저 만족시킨다.** 시각 완성도는 요구된 동작을 가린 채 추가하지 않는다.
2. **강조는 화면당 한 곳에만 둔다.** 주요 행동 버튼 하나가 강조를 가져가고 나머지는 물러난다.
3. **색만으로 의미를 전달하지 않는다.** 상태·오류·성공은 색과 함께 텍스트나 아이콘을 병기한다.
4. **임시 화면은 임시라고 표시한다.** 동작만 구현한 shell을 완료로 간주하지 않고 task와 PR에 명시한다.

## 2. 색상

방향 `노트`를 채택했다. 먹색을 주색으로 두고 호박색 강조 하나만 쓴다. 여행 상태가 늘어나도 색이 서로 경쟁하지 않게 하기 위한 선택이다.

### 검증된 대비

WCAG 2.x 상대 휘도 공식으로 계산했다. 본문은 4.5:1, 컨트롤 경계는 3:1이 기준이다.

| 조합 | 라이트 | 다크 |
|---|---|---|
| 본문 / 배경 | 16.74:1 | 15.06:1 |
| 본문 / 카드 | 17.49:1 | 13.73:1 |
| 보조 텍스트 / 카드 | 7.63:1 | 6.52:1 |
| 주버튼 라벨 | 14.68:1 | 13.93:1 |
| 보조버튼 라벨 | 5.02:1 | 10.48:1 |
| 강조 텍스트 / 카드 | 5.02:1 | 9.87:1 |
| 오류 텍스트 / 카드 | 6.47:1 | 8.68:1 |
| 컨트롤 경계 / 카드 | 4.80:1 | 3.52:1 |
| 포커스 링 / 카드 | 14.68:1 | 9.87:1 |

`outlineVariant`는 장식용 구분선이라 3:1 대상이 아니다. 컨트롤의 경계를 나타낼 때는 반드시 `outline`을 쓴다.

### 색을 새로 추가할 때

토큰에 없는 색이 필요하면 화면 코드에 직접 쓰지 말고 이 문서에 토큰으로 추가한 뒤 `Theme.kt`에 반영한다. 추가 전에 라이트·다크 양쪽에서 대비를 계산해 이 표에 넣는다.

## 3. 타이포그래피

Material 3 type role을 그대로 쓴다. 별도 폰트를 번들하지 않고 시스템 기본을 사용한다. 한글은 기기 기본 폰트로 렌더링된다.

| Role | 크기 | 용도 |
|---|---|---|
| `headlineSmall` | 24sp | 화면 제목 |
| `titleLarge` | 22sp | 앱바 제목 |
| `titleMedium` | 16sp | 카드 제목, 여행명 |
| `bodyLarge` | 16sp | 본문 |
| `bodyMedium` | 14sp | 보조 설명, 날짜 |
| `labelLarge` | 14sp | 버튼 라벨 |
| `labelMedium` | 12sp | 상태 뱃지 |

- 본문 최소 크기는 14sp다. 12sp는 뱃지처럼 짧은 라벨에만 쓴다.
- 크기를 새로 만들지 않는다. 위 role 중에서 고른다.
- 시스템 글자 크기 확대에서 잘리지 않아야 한다. 고정 높이 대신 `wrapContentHeight`와 여백으로 처리한다.

## 4. 간격과 모양

4dp 배수만 쓴다.

| 토큰 | 값 | 용도 |
|---|---|---|
| `space1` | 4dp | 아이콘과 라벨 사이 |
| `space2` | 8dp | 카드 안 요소 사이 |
| `space3` | 16dp | 화면 좌우 여백, 카드 안쪽 여백 |
| `space4` | 24dp | 섹션 사이 |
| `space5` | 32dp | 화면 상단·하단 여백 |

| 토큰 | 값 | 적용 |
|---|---|---|
| `radiusCard` | 12dp | 여행 카드, 다이얼로그 |
| `radiusButton` | 12dp | 버튼, 입력창 |
| `radiusBadge` | 999dp | 상태 뱃지 |

고도(elevation)는 카드 1dp, 다이얼로그 3dp, 그 외 0dp로 제한한다. 그림자를 계층 표현 이외의 장식으로 쓰지 않는다.

## 5. 공통 컴포넌트

`com.gilpick.ui.component`에 두고 모든 feature가 재사용한다. 화면에서 `Button`, `Card` 같은 Material 컴포넌트를 직접 조립하지 않는다.

| 컴포넌트 | 규칙 |
|---|---|
| 주요 버튼 | `primary` 채움. 화면당 하나. 높이 48dp 이상 |
| 보조 버튼 | 외곽선 또는 `secondary` 텍스트. 주요 버튼보다 시각 무게가 낮아야 한다 |
| 위험 버튼 | `error` 사용. 주요 버튼과 시각적으로 분리하고 확인 절차를 붙인다 |
| 입력창 | 라벨을 항상 보이게 둔다. placeholder를 라벨 대신 쓰지 않는다. 오류는 입력창 바로 아래 |
| 여행 카드 | 상태 뱃지 → 여행명 → 기간 순. 카드 전체가 터치 대상 |
| 상태 뱃지 | 색과 텍스트를 함께. 색만으로 상태를 구분하지 않는다 |
| 앱바 | `surface` 배경. 제목은 `titleLarge` |
| 카카오 로그인 버튼 | 아래 고정값 |

## 6. 화면 상태

목록과 상세를 가진 모든 화면은 네 상태를 전부 가진다.

| 상태 | 표현 |
|---|---|
| `loading` | 1초를 넘길 때만 skeleton을 띄운다. 그 전에는 아무것도 표시하지 않는다 |
| `empty` | 왜 비었는지와 다음 행동 버튼을 함께 보여준다 |
| `error` | 원인과 복구 방법을 쓰고 재시도 버튼을 둔다. "오류가 발생했습니다"만 쓰지 않는다 |
| `content` | 실제 내용 |

갱신 중 기존 내용을 유지할지 비울지는 화면마다 다르므로 해당 feature의 `spec.md`에서 정한다.

## 7. 접근성 최저선

모든 화면이 아래를 만족해야 한다.

| 항목 | 기준 |
|---|---|
| 본문 텍스트 대비 | 4.5:1 이상 |
| 컨트롤 경계·아이콘 대비 | 3:1 이상 |
| 터치 영역 | 48dp × 48dp 이상 |
| 터치 영역 간격 | 8dp 이상 |
| 아이콘 전용 버튼 | `contentDescription` 필수 |
| 장식용 아이콘 | `contentDescription = null` |
| 색 단독 의미 전달 | 금지. 텍스트나 아이콘 병기 |
| 시스템 글자 확대 | 최대 배율에서 잘림 없음 |
| 포커스 표시 | 키보드·스위치 접근 시 보이는 포커스 링 |

- 화면 너비 360dp에서 가로 스크롤이나 잘림이 없어야 한다.
- 라이트와 다크를 각각 확인한다. 한쪽만 보고 다른 쪽을 추정하지 않는다.

## 8. Compose 구현 규칙

**소유 위치**

| 경로 | 내용 |
|---|---|
| `com.gilpick.ui.theme` | 색상·타이포·간격 토큰, `GilpickTheme` |
| `com.gilpick.ui.component` | 공통 컴포넌트 |

feature 패키지(`com.gilpick.auth`, `com.gilpick.trip` 등)가 아니라 중립 위치에 둔다. 특정 feature가 소유하면 다른 feature가 쓸 근거가 없어진다.

**규칙**

- 화면 코드에 색상 리터럴(`Color(0xFF...)`)을 쓰지 않는다. `MaterialTheme.colorScheme`에서 읽는다.
- 간격도 리터럴 `dp` 대신 토큰을 쓴다. 예외는 토큰으로 표현할 수 없는 일회성 미세 조정이며, 그 경우 주석으로 이유를 남긴다.
- 다크 테마는 `colorScheme` 교체로만 처리한다. 화면에서 `isSystemInDarkTheme()`로 분기하지 않는다.
- 이 규칙을 지키면 나중에 색상 방향을 바꿀 때 `Theme.kt` 한 파일만 고치면 된다.

## 9. 변경 절차

- 이 문서의 값을 바꾸면 같은 PR에서 `com.gilpick.ui.theme`를 함께 갱신한다.
- 대비에 영향을 주는 색상 변경은 라이트·다크 양쪽 수치를 다시 계산해 2절 표를 갱신한다.
- 화면 구현이 이 문서와 어긋나면 임의로 해석하지 말고 차이를 Issue나 PR에 기록해 결정을 받는다.

## 10. 관련 문서

- 적용 절차: `AGENTS.md`
- API 계약: `docs/design/api-spec.md`
