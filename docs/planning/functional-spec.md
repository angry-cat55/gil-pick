# 길픽 기능 명세서

## 1. 기능 구성

| 영역 | 핵심 기능 |
|---|---|
| 인증 | 카카오 로그인, 토큰 재발급, 현재 기기 로그아웃 |
| 여행 | 여행 생성·목록·상세·수정·논리 삭제 |
| 일정 | 장소 검색, 날짜별 편성, 체류시간·순서·이동수단 편집 |
| 경로 | 날짜별 경로 조회, 남은 경로 재계산 |
| 진행 | 여행 시작, 도착·출발, 건너뛰기, 상태 수정, 되돌리기 |
| 감지 | 혼잡·날씨·운영시간 평가와 알림 |
| 대체 | 후보 추천·검색, 경로 미리보기, 승인·거절·되돌리기 |
| 설정 | 장소 변경 제안 알림 ON/OFF, 약관·개인정보처리방침·로그아웃 |

## 2. 여행과 일정

### 2.1 여행 관리

- 여행명은 2~30자이고 중복을 허용한다.
- 여행 기간은 최대 7일이다.
- 목록 상태는 KST 날짜로 산정한다.
- 목록 정렬은 여행 중, 가까운 예정, 최근 완료 순이다.
- 여행명 검색과 상태 필터는 cursor 기반 무한 스크롤과 함께 동작한다.
- 기간을 줄이면 삭제 대상 일정 수를 먼저 표시하고 확인 후 삭제한다.
- 삭제는 논리 삭제이며 일반 목록과 상세에서 보이지 않는다.

완료 조건:

- 다른 사용자의 여행과 다른 여행의 일정이 섞이지 않는다.
- 동일한 생성·수정 요청을 재전송해도 중복 데이터가 생기지 않는다.
- 기간 축소 확인 전에는 일정이 삭제되지 않는다.

### 2.2 장소와 체류시간

- 장소 검색·상세는 TourAPI를 기준 원천으로 사용한다.
- 관광지·문화시설·자연·축제·숙박은 Google Places 검색 결과로 보완하지 않는다.
- 음식·카페·쇼핑은 각 검색 페이지에서 중복 제거한 TourAPI 결과가 요청 `limit`보다 적을 때만 Google Places로 부족분을 채운다.
- 양쪽의 동일 장소가 확정 매칭되면 TourAPI ID와 기본·상세정보를 유지하고 Google 평점·평점 수·영업정보만 병합한다. 모호한 Google 후보는 제외한다.
- 화면에는 장소별 제공자 배지를 표시하지 않되 Google 데이터가 표시되는 영역에는 정책상 필수 attribution을 제공한다. Google 사진·리뷰는 사용하지 않는다.

| 내부 카테고리 | 추천 체류시간 |
|---|---:|
| 자연 | 120분 |
| 문화·역사 | 90분 |
| 음식 | 60분 |
| 카페 | 60분 |
| 쇼핑 | 90분 |
| 기타 | 60분 |

- 추천값은 장소 추가 시 자동 입력한다.
- 사용자는 30분 단위로 증감하며 최종값은 30~360분이어야 한다.
- 미처리 장소는 장소·순서·체류시간·이동수단을 수정한다.
- 처리된 장소는 상태·체류시간·순서를 수정한다.
- 장소를 교체하더라도 기존 진행 상태를 유지한다.

완료 조건:

- 저장된 순서와 지도 경로 순서가 같다.
- 진행 중 체류시간이나 순서가 바뀌면 영향받는 이후 ETA만 다시 계산한다.
- 경로 계산이 실패해도 일정 편집 결과는 보존되고 실패 상태가 표시된다.

## 3. 여행 진행

### 3.1 여행 시작과 ETA

- `오늘 여행 시작` 요청을 받은 서버 시각을 `actualStartedAt`으로 한 번만 저장한다.
- 시작을 다시 요청하거나 앱을 재개해도 기존 시각을 바꾸지 않는다.
- 유효한 현재 위치가 있으면 `시작 시각 + 현재 위치에서 첫 장소까지 이동시간`으로 첫 ETA를 계산한다.
- 현재 위치가 없으면 계획된 장소 간 경로와 체류시간으로 ETA를 계산하고 실시간 위치 보정은 생략한다.
- 다음 ETA는 `이전 장소 ETA + 계획 체류시간 + 다음 구간 이동시간`이다.

완료 조건:

- 여행 시작 전에는 ETA 기반 변수 감지를 실행하지 않는다.
- 여행 시작 후 남은 일정만 ETA와 변수 감지 대상이 된다.
- 위치 권한 거부나 위치 실패가 수동 진행을 막지 않는다.

### 3.2 도착 처리

1. 일정 순서상 다음 장소의 300m 영역에서 5분 DWELL을 충족한다.
2. 정확도 100m 이하이며 2분 이내인 이벤트만 도착 후보로 사용한다.
3. 사용자에게 도착 여부를 묻는다.
4. `도착했어요`는 즉시 `ARRIVED`, `아직이에요`는 후보 취소다.
5. 5분간 무응답이면 자동 `ARRIVED`로 확정한다.
6. 자동 확정 후 5분간 되돌리기를 제공한다.
7. `아직이에요` 뒤에는 10분 후 한 번만 재알림한다.

완료 조건:

- 같은 장소의 도착 알림은 최초 알림을 포함해 최대 2회다.
- 중복 지오펜스 이벤트는 하나의 상태 전이만 만든다.
- 자동 도착 되돌리기는 서버 시각으로 만료를 판정한다.

### 3.3 출발 처리

- 사용자가 `다음 장소로 출발`을 누르면 현재 장소를 완료하고 다음 장소를 이동 중으로 즉시 바꾼다.
- 수동 출발에는 전용 5분 되돌리기가 없지만 일반 상태 수정은 가능하다.
- 자동 감지는 현재 장소의 400m 영역 EXIT로 후보를 만든다.
- EXIT 후 5분간 무응답이고 재진입하지 않으면 자동 출발한다.
- 자동 출발 후 5분간 되돌리기를 제공한다.
- `아직 머무는 중`을 선택하면 해당 장소의 자동 출발 감지를 중단한다.

완료 조건:

- EXIT 후 재진입이 있으면 자동 출발하지 않는다.
- 출발 확정 시 완료·건너뜀 장소를 제외하고 남은 ETA를 다시 계산한다.
- 수동 버튼이 위치 정확도나 지오펜스 상태와 무관하게 동작한다.

### 3.4 상태 수정과 예외

- 기본 상태 흐름은 `PLANNED → EN_ROUTE → ARRIVED → COMPLETED`다.
- 모든 상태에서 `SKIPPED`로 변경할 수 있고 완료·건너뛰기를 취소할 수 있다.
- 수동으로 특정 장소를 `ARRIVED`로 바꾸면 이후 장소를 `PLANNED`로 초기화하고 ETA와 감지를 다시 계산한다.
- 다음 장소가 가까워 이전 장소 EXIT 없이 DWELL이 발생하면 이전 완료와 다음 도착을 한 트랜잭션으로 처리한다.
- 위 복합 전환을 되돌릴 때 두 장소와 ETA·감지 상태를 함께 복원한다.
- 마지막 장소 도착 확정 시 해당 날짜를 완료하고 모든 진행 작업을 종료한다.

## 4. 변수 감지

### 4.1 실행 대상

- 시작된 당일 일정의 남은 장소를 10분마다 평가한다.
- ETA가 바뀌면 혼잡·날씨·운영시간도 다시 평가한다.
- 같은 장소에 변경 제안을 보낸 뒤 사용자가 승인·거절하기 전까지 같은 제안을 중복 전송하지 않는다.

### 4.2 판단 기준

| 변수 | 기준 | 데이터 없음 |
|---|---|---|
| 혼잡 | 장소 500m 이내 서울시 지원지역의 ETA 예보와 카테고리 민감도 | 변수 제외 |
| 날씨 | 강수확률 70% 이상, 1mm/h 이상 또는 비·눈·소나기·뇌우 | 변수 제외 |
| 운영시간 | ETA가 폐점 이후면 방문 불가, 폐점 30분 이내면 임박 | 변수 제외 |

- 혼잡 민감도 높음: 쇼핑·음식·카페
- 혼잡 민감도 중간: 자연·문화·역사·기타
- 날씨 페널티는 실외와 실내·실외 미상 장소에 적용한다.
- 확인 가능한 임시휴업은 방문 불가이며, 확인할 수 없으면 운영 중으로 가정한다.

## 5. 대체 장소와 일정 변경

### 5.1 후보 생성

- 기존 장소를 기준으로 0.5km, 1km, 2km 순서로 탐색한다.
- TourAPI 분류를 내부 카테고리로 변환하고 소분류, 중분류, 대분류 순으로 비교한다.
- Google Places는 50m 이내 좌표, 장소명, 주소를 조합해 매칭하며 모호하면 사용하지 않는다.
- 운영 종료 장소는 제외한다.

### 5.2 점수와 정렬

- 거리 35%, 베이지안 보정 평점 30%, 혼잡 20%, 날씨 15%
- 누락 변수는 제외하고 나머지 가중치를 비례 재분배한다.
- 상위 10개를 반환한다.
- 동점은 거리 짧은 순, 보정 평점 높은 순, 리뷰 수 많은 순이다.
- 표시 점수만 정수로 반올림하고 내부 비교는 원점수를 사용한다.

### 5.3 변경 적용

1. 사용자가 추천 후보 또는 직접 검색 결과를 선택한다.
2. 서버는 실제 일정을 바꾸지 않고 변경 경로 미리보기를 만든다.
3. 사용자가 승인하면 일정 장소·경로·변경 이력을 한 트랜잭션으로 저장한다.
4. 사용자가 거절하면 기존 일정과 후보 탐색 맥락을 유지한다.
5. 승인 후 30초까지 되돌릴 수 있다.
6. 승인 뒤 후속 일정 변경이 생기면 이전 되돌리기는 비활성화한다.

완료 조건:

- 후보 선택과 미리보기만으로 일정 DB가 변경되지 않는다.
- 승인 시 일정 버전, 후보 운영 여부, 경로 유효성을 다시 검증한다.
- 승인이나 되돌리기 일부만 성공하는 상태가 생기지 않는다.

## 6. 알림과 설정

- FCM payload에는 `tripId`, `itemId`, `detectionId`, `transitionId` 등 재조회 식별자만 전송한다.
- 장소 변경 제안 알림 전체 ON/OFF를 제공한다.
- 도착·출발 확인 알림은 여행 진행을 위해 별도로 동작한다.
- 설정 화면에는 이용약관, 개인정보처리방침, 로그아웃을 제공한다.

## 7. 실행 환경과 배포 준비

### 7.1 G001 공유 dev/staging 환경

- 실제 callback, App Link 또는 외부 API 검증이 필요한 Feature는 종단간 검증 전에 공유 dev/staging 환경을 사용한다.
- 환경은 HTTPS Backend, PostgreSQL·PostGIS, 환경별 secret 주입과 필요한 외부 서비스 callback·domain 등록을 제공한다.
- local test secret은 개인 local 환경에만 허용하고 공유 환경의 secret은 승인된 secret 저장소 또는 배포 환경변수로 주입한다.
- F001은 실제 Kakao test app과 Android App Link 검증 전에 준비한다. 이후 외부 API credential은 F003·F005·F008·F009·F011의 실제 연동 검증 전에 각각 준비한다.
- 환경 준비가 완료되지 않아도 mock·local test가 가능한 task는 진행할 수 있다. 실제 연동 task만 환경 Issue에 의존한다.

완료 조건:

- 실제 endpoint와 secret이 repository, test output과 screenshot에 노출되지 않는다.
- 해당 Feature가 요구하는 callback·domain·credential로 정상·실패 종단간 흐름을 재현할 수 있다.
- 환경 준비 Issue와 이를 기다리는 Feature task의 선행 관계가 GitHub에 기록되어 있다.

### 7.2 G002 MVP 운영환경

- MVP 전체 종단간 검증과 배포 후보 확정 전에 Backend 실행 환경과 운영 PostgreSQL·PostGIS를 구성한다.
- HTTPS domain·TLS, secret 관리, 인증 application log 30일 보존과 Backend 운영 계정 접근 제한, backup·restore, monitoring을 구성하고 검증한다.
- 배포 방식은 build, test, DB migration, 배포, 실패 시 중단과 rollback 순서를 재현 가능하게 문서화한다.
- AWS의 구체 서비스, 환경 수와 비용 상한은 별도 인프라 Issue에서 팀 합의로 결정한다.

완료 조건:

- 배포된 Backend가 운영 DB와 외부 서비스에 secret 노출 없이 연결된다.
- migration과 애플리케이션 배포의 순서 및 rollback 절차가 검증된다.
- 인증 로그의 30일 보존과 Backend 운영 계정 접근 제한을 실제 설정으로 확인한다.
- backup 복구 절차와 핵심 monitoring·장애 확인 경로가 문서화된다.
